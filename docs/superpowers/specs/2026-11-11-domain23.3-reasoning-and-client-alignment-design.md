## 1. 背景与范围

### 1.1 23.3 在 agent 会话流程中的位置

一次模型调用的完整链路：

```
用户输入 → ReAct 循环
  react_model_call.go:382  WithInvokeExtra(extraKVPairs)      ← 消费方手动注入 thinking/extra_body
  → OpenAIModelClient.Invoke/Stream  (openai/client.go:78/253)
      → BaseClientEmbed.BuildRequestParams (base_client.go:300)
          model_config.Extra 平铺进 params
      → 【插入点 A】reasoning plan 解析 → 写入 sdk_params + extra_body
      → AdjustParamsForOpenAI / HandleExtraBody
      → BuildHTTPRequestWithAuth → 厂商
  ← 响应 reasoning_content → parse_stream_chunk.go → chat.reasoning → 前端 ThinkingBlock
```

配置侧：

```
config.yaml 模型条目（reasoning_level / extra_body / thinking / enable_thinking）
  → models.upsert / session.selection RPC（27.4，Go 侧尚无 config_panel）
  → 【插入点 B】reasoning_level → ReasoningConfig → ModelRequestConfig.Reasoning
  → 构造客户端 → 插入点 A
  → 【插入点 C】能力目录 get_reasoning_capability（前端选档位用）
```

**作用**：把用户选的一个档位（`off`/`on`/`low`/`high`/`xhigh`/`max`）翻译成各厂商不同的线上参数——OpenAI 用 `reasoning_effort`、Anthropic 用 `thinking.type`+`budget_tokens` 或 `output_config.effort`、DashScope 用 `enable_thinking`+`thinking_budget`、OpenRouter 用 `reasoning{effort,enabled,max_tokens}`、DeepSeek 用 `thinking.type`+`reasoning_effort`、ModelArts/GLM/Kimi/MiniMax 各有变体；同时处理两类兼容回退。

### 1.2 为什么本批同时做「架构对齐」

23.3 的 `_provider_key()` 判断 provider 的第一顺位是 `endpoint_profile`。而 Go 侧没有 `normalize_model_client_config`，`endpoint_profile` 无人写入——不先补别名归一，23.3 的 provider 判定就落不了地。

同时，上游是「1 个 `OpenAIModelClient` + 别名归一」，Go 是「每 provider 一个客户端包」（2.x 节早期产物）。两者不能共存：引入归一后 `DashScope`/`SiliconFlow`/`InferenceAffinity` 三个包将永远收不到请求，按规则 8 必须同批删除。

用户裁决：**全部塞进 23.3 一次做完，严格对齐 Python。**

## 3. 数据结构

### 3.1 `ReasoningConfig`（`schema/reasoning_config.go`）

上游 `schema/config.py:59-66`，3 字段且 `extra="forbid"`：

```go
// ReasoningConfig 厂商中立的思考/推理请求意图。
// Python: schema/config.py:59-66 ReasoningConfig（extra="forbid"，不允许额外键）
type ReasoningConfig struct {
    // Mode 思考模式，缺省 auto；取值 auto/enabled/disabled
    Mode string `json:"mode"`
    // Effort 强度档位（厂商自定义取值，如 low/medium/high/xhigh/max）
    Effort *string `json:"effort,omitempty"`
    // BudgetTokens 思考预算（token），nil 表示未设置；不得为负
    BudgetTokens *int `json:"budget_tokens,omitempty"`
}
```

`Mode` 用 `string` 而非 Go 枚举：上游 `Literal` 校验在 `model_validate` 时抛错，Go 的校验点在 `Validate()`，需产出与上游一致的错误消息。

**零值陷阱**：Python 默认 `mode="auto"`，Go 零值是 `""`。`NewReasoningConfig()` 必须把 `Mode` 初始化为 `"auto"`，否则 `resolve_reasoning_plan` 的分支会走错（`mode == "auto" and not effort and budget is None` 的三条件早返回）。

### 3.2 `ModelRequestConfig.Reasoning`（单字段 `any`）

上游 `schema/config.py:272-275` 是 `Optional[Union[ReasoningConfig, dict[str, Any]]]`。

Go 采用单字段 `any`：

```go
// Reasoning 思考/推理请求意图。
// 可能是 *ReasoningConfig（代码内构造，对应 Python isinstance 分支），
// 也可能是 map[string]any（从 JSON/YAML 反序列化，键集合决定新式或遗留）。
// Python: ModelRequestConfig.reasoning: Optional[Union[ReasoningConfig, dict[str, Any]]]
Reasoning any `json:"reasoning,omitempty"`
```

**必须是 `ModelRequestConfig` 的正式字段，不得塞进 `Extra`。** 依据：上游 `base_model_client.py:644-655` 的 `model_dump(exclude={..., "reasoning"})` 明确排除它；Go 侧 `base_client.go:335` 把 `Extra` 全量平铺进请求参数，塞进 `Extra` 会误发给厂商。

### 3.3 `coerceReasoningConfig`

Python `reasoning.py:255-265`，5 分支：

| 输入 | 输出 | Python 行 |
|------|------|----------|
| `nil` | `(nil, nil)` | `if value is None or value is UNSET_REASONING` |
| `*ReasoningConfig` | `(value, nil)` | `isinstance(value, ReasoningConfig)` |
| 无法转 map | `(nil, nil)` | `raw is None` |
| 键集 ⊆ `{mode, effort, budget_tokens}` | `(cfg, nil)` | `set(raw).issubset(_NEW_REASONING_KEYS)` |
| 否则 | `(nil, raw)` | `return None, raw` |

```go
// coerceReasoningConfig 判断 reasoning 属于新式配置还是遗留裸 dict。
// Python: reasoning.py:255-265 _coerce_reasoning_config
func coerceReasoningConfig(value any) (cfg *ReasoningConfig, raw map[string]any)
```

**判定时机与 Python 一致：每次 `resolve_reasoning_plan` 调用时判定，不在反序列化时定死。** 这是选择 `any` 而非双字段的核心理由——若在反序列化时定死形态，则在「新式 dict 多出一个键」的场景下 Python 会切成遗留格式而 Go 不会，行为漂移。

### 3.4 `ReasoningIntent`（双态）

Python 用 `UNSET_REASONING = object()` 哨兵区分「未传」与「传了 None」：

```go
// ReasoningIntent 区分「未显式传 reasoning」与「显式传了 reasoning（值可为 nil）」。
// Python: reasoning.py:33 UNSET_REASONING 哨兵 + reasoning.py:300-306 _explicit_reasoning_value
type ReasoningIntent struct {
    // Set 是否显式传入 reasoning
    Set bool
    // Value 传入的值；Set=true 且 Value=nil 表示显式传了 null
    Value any
}
```

### 6.5 工具碎片聚合：不做

上游 `_coalesce_tool_call_fragments`（`compat_patch.py:123-139`）职责是同一 chunk 内多个 tool_call 片段、后者无 id/name 时拼接到前一个 arguments。

## 7. disabled-thinking 回退

### 7.1 三道闸门

上游 `openai_model_client.py:1383-1410`：

```
闸门一：not is_disabled_thinking_fallback_allowed() → 直接发，任何失败都不重试
闸门二：_apply_disabled_thinking_cache(params) → 已知拒绝该模型的，先剥掉
闸门三：_retry_params_without_disabled_thinking(params, exc) 返回 nil → 原样抛出
        否则记入缓存 + 重试一次（不套 try，失败直接抛）
```

**默认行为是失败即失败**，只有显式进入 `disabled_thinking_fallback_scope()` 才重试。上游生产唯一开启点是 `symphony/shared/fingerprint/extractor.py:324`。

### 7.2 错误判据四层

`_is_disabled_thinking_rejection`（`:1349-1370`）+ 常量（`:133-150`）：

| 层 | 判据 | 常量 |
|----|------|------|
| 1 | `status_code ∈ {401,403,408,429}` 或 `>= 500` → **不重试** | `_DISABLED_THINKING_NON_RETRY_STATUSES` |
| 2 | `"1210" in error_text` → 立即认 | 硬编码 |
| 3 | 必须提到 `thinking` / `reasoning` / `思考` | — |
| 4 | 必须含 `_UNSUPPORTED_DISABLED_THINKING_MARKERS`（9 条）**且**（含 `_DISABLED_THINKING_VALUE_MARKERS` 或 `"parameter"` 或 `"参数"`） | 两个 marker 表 |

`_exception_text` 递归遍历异常链（`__cause__`/`__context__`）并拼接所有属性文本（含 `response.body`/`code`/`type`/`param`）。Go 用 `errors.Unwrap` 循环 + 属性提取。

### 7.3 scope 传递

Python `request_context.py` 用 `ContextVar[bool]` 默认 False。Go 用 `context.Context` value（D-2）：

```go
// WithDisabledThinkingFallback 返回允许 disabled-thinking 兼容回退的 ctx。
// Python: request_context.py:22-28 disabled_thinking_fallback_scope()
func WithDisabledThinkingFallback(ctx context.Context) context.Context

// IsDisabledThinkingFallbackAllowed 判定当前请求是否允许回退。
// Python: request_context.py:17-19 is_disabled_thinking_fallback_allowed()
func IsDisabledThinkingFallbackAllowed(ctx context.Context) bool
```

`BuildRequestParams` 已有 ctx 参数可传。
