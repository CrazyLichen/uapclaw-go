## 1. 在 agent 会话中的流程位置与作用

### 1.1 调用链

```
宿主启动一次 agent 会话（web / chat / team 任一入口）
  │
  ├─ 单 Agent 路径（本仓 Go 已通，25.1a 已交付）：
  │    DeepAgentSpec.build() → DeepAgent.Invoke / RunStreaming → _run_task_loop 自驱
  │    ❌ 不经过 harness_protocol
  │
  └─ 外部 CLI 成员路径（领域十五要新建，当前 Go 全缺）：
       spawn_teammate(external_cli)                        ← 15.16 / 15.13
         → HarnessProvider.Create(config)                  ← 15.5
         → harness.Start(HarnessContext)                   ← 15.1 ✅
         │    ├─ card.ValidateHost() 协商 host_capabilities
         │    │   交互面 5 项：TOOL_APPROVAL / USER_INPUT / MCP_ELICITATION /
         │    │                 DYNAMIC_TOOL_CALL / PROVIDER_INTERACTION
         │    │   钩子面 1 项：HOOKS
         │    └─ ⭐ context.Interactions / context.Hooks 在此被注入   ← 15.3（本节）
         → harness.Send(HarnessInput) → SendReceipt        ← 15.1 ✅
         → ⭐ 工具执行前 / 后：hooks.before_tool / after_tool          ← 15.3（本节）
         → ⭐ 子进程举手：interactions.handle(...) → 应答 → 子进程      ← 15.3（本节）
         → turn_events() / events() 事件流                  ← 15.2 ✅
         │    ⚠️ HookObservedEvent 只是钩子调用的观测镜像，
         │       不得用于权限决策（hooks.py:132-133 / README.md:83）
         → TurnResult（终态）                              ← 15.1 ✅
         → checkpoint                                      ← 15.4
```

### 1.2 三个平面（`openjiuwen/harness_protocol/README.md:96-103`）

| 平面 | 方向 | 是否阻塞 harness | 本节归属 |
|---|---|---|---|
| observation | Harness → `events()` → host consumer | 否 | 15.2 ✅ |
| **interaction** | Harness → handler → response → Harness | **是**（子进程原地等） | **15.3** |
| **hooks** | Harness → lifecycle hook → policy result → Harness | **是** | **15.3** |

`SPEC.md:185-187` 明文：「这些请求不能发到 events 后等待 event consumer 回写，否则会造成死锁、审批丢失和多消费者竞态。」这是 15.3 必须与 15.2 严格分离的根本原因。

### 1.3 会话内的具体落点

| 时点 | 15.3 负责什么 | Python 依据 |
|---|---|---|
| 子进程要执行工具前（请求授权） | `ToolApprovalRequest`（call_id / tool_name / arguments / deadline_at）→ 宿主 `ALLOW` / `ALLOW_FOR_SESSION` / `DENY` / `ABORT` | `interactions.py:66-88, 174-190` |
| 子进程缺信息 | `UserInputRequest`（prompt / choices / deadline_at）→ `COMPLETED/DECLINED/CANCELLED/FAILED` + content | `:90-108, 192-205` |
| MCP server 要结构化输入 | `McpElicitationRequest`（server_name / schema）→ values | `:110-130, 207-220` |

| provider 自定义扩展 | `ProviderInteractionRequest`（provider / request_type / schema_version）→ payload | `:154-172, 239-250` |
| 撤销 / 中止 | `cancel(request_id, reason)` 幂等；**turn abort 与 stop 返回前必须取消全部 pending** | `:331-338`；`SPEC.md:178` |

### 1.4 作用

1. **安全闸门**：外部 CLI 会真的 `rm -rf`、真的调 MCP。没有 15.3，宿主只能事后看事件、无法拦截。`SPEC.md:180-184`：「optional 能力缺失时，具体请求必须安全 decline/fail，**不能默认授权**」。
2. **死锁边界**：interaction 是「子进程原地等宿主」的同步应答，绝不可走事件流（`SPEC.md:185-187`）。
3. **请求/应答配对**：`ValidateInteractionResponse` 强制「同 request_id + 类型必须配对」（`interactions.py:273-288`），5×5 错配一律 `HarnessProtocolError`。
4. **宿主策略注入点**：hooks 是 OpenJiuwen 统一工具策略（沙箱 / 只读区 / 预算 / 参数改写）作用到第三方 CLI 的唯一入口。

## 3. 已确认的设计决策（brainstorming 九轮结论）

| # | 议题 | 决策 |
|---|---|---|
| Q1 | 是否拆 15.3a（interactions）/ 15.3b（hooks） | **A：合一节**，26 导出符号一次投出，`interactions.go` + `hooks.go` 两文件 |
| Q2 | 15.1 自造的 `Enabled()` / `Pending()` | **A：删除**，接口完全按 Python 重写（4 方法 / 2 方法） |
| Q3 | 两个 5 分支 union 的 Go 表示 | **1：接口 + 5 具体结构体** + `requestKind()` / `responseKind()` 标记方法；`Handle(ctx, HarnessInteractionRequest) (HarnessInteractionResponse, error)` |
| Q4 | hooks 零生产调用方 | **A：只落契约、不造调用点**，§1.5 登记缺口 |
| Q5 | 类型配对映射表 | **3（由方案 1 改选）**：给请求类型加 `expectedResponseKind()` |

### 3.1 各决策的理由与已消除的风险

- **Q1**：规则 9 一文件对一文件；上游 `__init__.py:48-77` 也是同时导出两者；15.3 是纯契约层，两文件均零行为零调用方，分开投会让契约面在计划上割裂。
- **Q2**：规则 12.1-4「成员集合不得自改」。`Enabled()` / `Pending()` 在 Python 侧 AST 核对无对应物（`hooks.py` Protocol = 4 钩子方法；`interactions.py` Protocol = `handle` + `cancel`）。Python 侧「有没有注册」的等价判断是零值 nil 比较（`base.py:718` `context.interactions is not None`），不需要协议方法。保留会让协议面永久留一个无法逐符号对照的成员。
- **Q3**：与 15.2 `HarnessEventPayload`（spec B3）完全同构，已实证可用；`requestKind()` 同时为 15.4 codec 提供 discriminator。方案 2（单一大结构体平铺）会让「ToolApprovalRequest 没有 prompt 字段」这类构造期约束无法表达，且无法做请求-应答配对；方案 3（返回 `any`）违反 15.1「禁 any 承载协议值」。
- **Q4**：上游 `harness_providers/` 内零 hooks 调用点。自造「Go 版调用点」= 与上游结构漂移，且 `before_tool` 返回值优先级、`ASK` 如何转审批均无上游定义，必然写错语义。
- **Q5 / Q5b**：期望应答类型本质是请求自身的属性，挂请求接口语义正确；`ValidateInteractionResponse` 收敛为「kind 比较 + switch 取错误文案」。
- **Q6**：消除「11 个形参 + 4 个连续 `*string` 易传反」的调用点风险；同时保持同一 dataclass 内「必填必显式、可选有名字」的直觉。
- **Q7**：`_validate_request_common` 是全节**唯一**明确区分「`None` 放行 / `""` 拒绝」的地方（`interactions.py:26-28`），照抄才保持语义。与 15.2 B4（`HarnessEvent` 信封空串=未提供）不冲突 —— 那里 Python 本来就不拒绝空串。
- **Q8**：`Cancel` 是接口方法，variadic options 能表达「可省略」，且零参时填 Python 的默认值 `PROVIDER_WITHDREW`（**不是**「零值再映射」）。方案 3（拆 `Cancel` / `CancelWith`）会自增成员集，正是 Q2 否掉的自改。
- **Q9**：形参 / Options 拆分是**调用便利性**划分，不是校验顺序划分；`__post_init__` 本就是「先冻结、再互相校验」两段，Go 照排即可。

func ValidateInteractionResponse(
	request HarnessInteractionRequest,
	response HarnessInteractionResponse,
) (HarnessInteractionResponse, error) {
	// 步骤 1：request_id 必须一致
	if requestIDOf(request) != responseIDOf(response) {

## 7. 数据流与错误处理

- **interaction 请求路径**（15.5 实现调用）：provider 构造 `NewToolApprovalRequest(...)` → `handler.Handle(ctx, request)` → 宿主应答 `NewToolApprovalResponse(...)` → `ValidateInteractionResponse(request, response)` → 返回给 provider。任一环节坏值在构造期被挡。
- **interaction 撤销路径**：`handler.Cancel(ctx, requestID, NewCancelOption(reason))` 幂等；turn abort 与 stop 前须批量取消（Go 侧 `_fail_pending` 等价物属 15.5）。
- **hooks 路径**（本节只定契约）：harness 在 `before_prompt` / `before_tool` / `after_tool` / `on_stop` 四个边界 await 对应方法；`ToolDecision` 的 `REWRITE` 必带参数、`ASK` 转 interaction、`PROVIDER_POLICY` 交 provider。
- **异常路径日志**（规则 3）：`interactions.py` / `hooks.py` **零 `logger.` 调用**（`grep -c` = 0 / 0），故 Go 侧**不新增日志**；校验失败统一返回 `&HarnessProtocolError{Msg: ...}`，由 15.5+ 的调用方决定是否记录。
- **错误分类**：
  - 构造期非法 → `HarnessProtocolError`（等价 `ValueError`）
  - 请求-应答错配 / id 不匹配 → `HarnessProtocolError`（同上，对齐 `:280-286`）
  - 未知请求类型（`requestIDOf` 的 default） → `HarnessProtocolError{Msg: "unsupported interaction request type"}`（Python 侧 `_EXPECTED_RESPONSE_TYPE[type(request)]` 会抛裸 `KeyError`，Go 收敛为协议错误 —— 见 §6 未列，此处记为**收紧**）
