## 1. 概述

### 1.1 一句话

成员团队状态投递（25.0b/c）依赖两条框架通道：**① 附件"先投递后 commit"的时序**与 **② 一次模型调用吸收多少条 steering 积压**。这两条通道在 Go 侧都只通了半条，25.0a 把它们补齐，不涉及任何 team 语义。

### 1.4 在 agent 会话中的流程位置

```
Agent 一次 invoke（一轮）
├─ BEFORE_INVOKE
├─ 准备 modelCtx / 取工具
├─ ReAct 迭代循环（每轮 = 一次模型调用）
│   ├─ ① consume force_finish
│   ├─ ② ★ drain steering batch        ← 本 spec 的 ② 通道：先 fire，再按 limit 取
│   ├─ ③ ★ 消费输入批次 → 写历史        ← on_user_message 的 parts 载体（本 spec 打通）
│   │      · fire(ON_USER_MESSAGE)，rails 可插入 / 丢弃 / 改写整条输入
│   │      · ★ syncPromptAttachments   ← 本 spec 的 ① 通道：成功后逐条执行 commit 回调
│   │      · add UserMessage(join(parts))
│   ├─ before_model_call → LLM → after_model_call
│   ├─ before_tool_call → 工具 → after_tool_call
│   └─ after_react_iteration
├─ AFTER_INVOKE
└─ 持久化 / 清洗
```

**作用（不做会怎样）**

| 机制 | 解决什么 | 不做的后果 |
|---|---|---|
| ① commit 回调 | 附件车道是「当前状态」通道：每次边界比对注册区与历史哈希。必须等 `Sync` **真正写进历史**后，才能把 tracker 基线推进到"已送达" | tracker 以为已宣告、历史里却没有 → 成员永久看不到身份/名册/策略，且**不自愈**（基线已推进） |
| ② steering 批上限 | 忙碌成员攒下的 mailbox 消息会一次性挤进同一轮 | 25.0c 的 `steer_batch_size` 无处安放；成员一次吃十几条，任务板序列糊成一坨 |
| parts 载体 | 25.0c 的"前插 `<team-context>`"与"丢弃被 superseded 的任务板"都发生在**输入还是列表的时候** | `on_user_message` 只能拿到已 join 的 Query，前插/丢弃无处下手；一旦写完历史就只能靠位置回改（compaction 会重写历史，位置不可靠） |

## 2. 流程与数据

### 2.1 ① 附件提交回调

```
调用方（on_user_message 边界 / 两个迭代内边界）
  └─ syncPromptAttachments(ctx, manager, hc, cbc)
       ├─ manager==nil 或 hc==nil → 返回 ok=true（无车道，不消费回调）
       ├─ manager.Sync(...) 失败 → warn；返回 ok=false（**不 pop、不执行**）
       └─ Sync 成功 → ok=true
            └─ 调用方：if ok { runCommitCallbacks(cbc) }
                 └─ pop(ctx.extra[CommitCallbacksExtraKey]) → 逐条执行
                      ├─ 单条返回 error 或 panic → warn（recover），继续下一条
                      └─ 全部执行完（列表已被 pop，不会重复）
```

**为什么拆成"返回 ok + 显式 run"而不是在函数内部一把做完**：现有三处调用点拿到的 `hc` 有三个不同来源，其中 `react_model_call.go:153` 与 `react_invoke.go:485/738` 只在 `modelCtx != nil` 时调用；若把"pop + 执行"塞进函数体，则失败路径与"无车道"路径的分支会分散在三处调用点重写一遍——上游三处调用都指向同一函数，Go 也保持"一个函数判成败，调用方一行执行"，pop 点只有 1 个。

### 2.2 ② steering 批上限

```
迭代内（react_invoke.go，原 :737）
  └─ msgs := drainSteeringBatch(ctx, cbc)
       ├─ cbc.SteeringQueue()==nil 或 !cbc.HasPendingSteering() → nil（**不发事件**）
       ├─ prev := cbc.Inputs()
       ├─ cbc.SetInputs(&SteeringDrainInputs{Pending: cbc.SteeringPendingCount()})
       ├─ err := cbc.Fire(ctx, CallbackBeforeSteeringDrain)
       ├─ limit := cbc.Inputs().(*SteeringDrainInputs).Limit；finally 还原 prev
       └─ cbc.DrainSteering(limit)
  └─ if len(msgs) > 0:
       admitUserMessage(ctx, modelCtx, msgs, source="steering", prefix="[STEERING] ")
```

`DrainSteering(limit *int)`：

```
take := 0（0 表示不限）
if limit != nil && *limit > 0 { take = *limit }
for take==0 || len(msgs) < take:
     select <-ch → append; default → return
```

- `limit=nil` → 排空全部（与当前行为一致，不破坏既有调用）
- `limit<=0` → 视作不限（上游 `max(1, limit)` 的等价物：无论 rail 写什么，非空队列**至少取 1 条**，否则 `HasPendingSteering` 会让循环空转）
- 剩余留在 channel 原位（Go channel 天然 FIFO 保留，无需 lookahead buffer）

### 4.2 类型定义

```go
// SteeringDrainInputs BEFORE_STEERING_DRAIN 事件输入。
//
// 只在"有积压的模型调用前"触发；空队列不发事件。
//
// Python: SteeringDrainInputs (openjiuwen/core/single_agent/rail/base.py L402-427)
type SteeringDrainInputs struct {
    // Pending 当前排队条数（只读上下文，供"只压大批次"的 rail 参考）
    Pending int
    // Limit 本次最多吸收几条；nil 表示全部（rails 按优先级依次写，最后生效）
    Limit *int
}

// UserMessageInputs ON_USER_MESSAGE 事件输入。
//
// 一批即将被 join 成一条 UserMessage 的输入，按最旧在前排列。
// rails 原地编辑 Parts：丢弃被后续条目取代的、或 insert(0, ...) 前插上下文。
//
// Python: UserMessageInputs (openjiuwen/core/single_agent/rail/base.py L378-399)
type UserMessageInputs struct {
    // Parts 排队输入列表（可变，rails 原地增删）
    Parts []string
    // Source 批次来源：query / steering / resume
    Source string
}
```

`Limit` 用 `*int` 而非 `int`：向上游 `int | None` 对齐，"没人表态"与"表态为 0"必须可区分（0 在 `max(1,limit)` 下等价于 1，而 nil 是全部——两者语义不同）。

### 4.3 commit 回调执行

```go
// runCommitCallbacks 执行并清空 ctx.extra 中的投递成功回调。
//
// Python: _sync_prompt_attachments 尾段（react_agent.py L1169-1182）
func runCommitCallbacks(cbc *interfaces.AgentCallbackContext) {
    raw, ok := cbc.DeleteExtra(prompts.CommitCallbacksExtraKey)
    if !ok { return }
    callbacks, ok := raw.([]func() error)
    if !ok { return }
    for _, f := range callbacks {
        runOneCommitCallback(f)   // 内含 recover，单条失败只 warn
    }
}
```

- **pop 语义**：`DeleteExtra` 一次取出即移除。取出的类型不是 `[]func() error`（例如团队侧塞了别的形态）→ 直接丢弃，不再执行（对齐上游 `if not isinstance(callbacks, list): return`）。
- **panic 隔离**：`recover` → `logger.Warn(message="prompt attachment delivery callback panicked")`，不阻断本轮模型调用（上游只捕 `Exception`，Go 需显式 recover 才等价）。
- **异步回调**：上游允许回调返回 awaitable，Go 侧约定回调为同步 `func() error`；需要异步的回调自行起 goroutine 并自担错误处理（登记 D-2）。

### 4.5 `admitUserMessage` 统一助手

```go
// admitUserMessage 把一批已消费的输入 join 成一条 UserMessage 写入历史。
//
// Python: _admit_user_message (react_agent.py L917-955)
func (a *ReActAgent) admitUserMessage(ctx, cbc, modelCtx, parts []string, source, prefix string) error
```

对齐 P4 的**步骤顺序**（禁止合并）：

1. `prev := cbc.Inputs()`
2. `cbc.SetInputs(&UserMessageInputs{Parts: parts, Source: source})`
3. `defer func(){ cbc.SetInputs(prev) }()`（等价 `try/finally`）
4. `cbc.Fire(ctx, CallbackOnUserMessage)`
5. `if len(parts)==0 { return }`（rails 全丢 → 不写历史、**不 Sync**）
6. `syncPromptAttachments` → 成功则 `runCommitCallbacks`
7. `modelCtx.AddMessages([UserMessage(prefix + join(parts,"\n"))])`

**注意事项**：第 3 步的还原必须在第 4 步之后立即生效（用闭包 defer），且**第 4 步 panic 也要还原**——rails 里 panic 时 `cbc.inputs` 若停在 `UserMessageInputs`，后续 `before_model_call` 会拿到错误类型直接崩。这是 Python `try/finally` 的等价物，必须显式写。

### 4.6 steering 批

```go
// drainSteeringBatch 取本次模型调用可以吸收的那部分 steering 积压。
//
// Python: _drain_steering_batch (react_agent.py L964-1000)
func drainSteeringBatch(ctx context.Context, cbc *interfaces.AgentCallbackContext) ([]string, error)
```

1. 无队列 / 无积压 → `nil, nil`（**不发事件**）
2. `prev := cbc.Inputs()`；`SetInputs(&SteeringDrainInputs{Pending: cbc.SteeringPendingCount()})`
3. `err := cbc.Fire(ctx, CallbackBeforeSteeringDrain)`；读回 `Limit`；`SetInputs(prev)`（同样的 defer 保护）
4. `return cbc.DrainSteering(limit), err`

`Fire` 返回 error 时：**仍执行 drain**（否则积压永不消费、循环空转），错误向上抛由调用方决定（当前 `react_invoke.go` 的循环对 rail 错误一律上抛，保持该行为）。上游 `fire` 不返回值；Go 的 `Fire` 有 error，此处按"消费优先、错误照抛"处理，登记为 D-4。

## 6. 已知偏差（须用户确认）

| ID | 偏差 | 理由 | 回收条件 |
|---|---|---|---|
| D-1 | 回调类型为 `[]func() error`，不支持 awaitable | Go 无 await；异步回调自行起 goroutine | 不回收（语言约束） |
| D-2 | 回调 panic 由框架 `recover` 兜住 | 上游只捕 `Exception`，Go 的 panic 不 recover 会掀掉整个 invoke | 不回收 |
| D-3 | `DrainSteering(limit *int)` 用指针而非 `(limit int, hasLimit bool)` | 与上游 `int \| None` 同形，调用点最少改动 | 不回收 |
| D-4 | `Fire` 出错时仍执行 drain，错误照抛 | 不 drain 会让积压永不消费、ReAct 循环空转（上游 fire 不返回值，无此分支） | 不回收 |
| D-5 | `source="resume"` 不接 | Go 中断恢复不走 `_admit_user_message` | 领域十五中断恢复对齐时 |
| D-6 | `_input_parts` 走 `Extra` 传递，不经 JSON 序列化 | `normalizeInputs` 已把 `_` 前缀 key 收进 `Extra`；内部路径直接传 Go 值 | 不回收 |
| D-7 | `SteeringDrainInputs.Limit` 不做 `max(1,limit)` 的语义伪装 | 上游在 `drain_steering` 里做 `max(1,limit)`，Go 在 `DrainSteering` 里做，位置不同语义相同 | 不回收 |
