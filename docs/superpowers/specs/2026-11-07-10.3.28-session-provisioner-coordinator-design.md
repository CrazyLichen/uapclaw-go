## 1. 概述

### 1.1 一句话

会话的"建 / 切 / 分叉 / 删"目前散落在 `handle_session.go` 的四个 handler 里各写一遍，删除甚至是"调一下 `runner.Release` 就 `os.RemoveAll`"。本 spec 按上游把四条路径收进一套**可提交、可回滚的两阶段事务**，并补齐它依赖的**执行账本**（协调器）——没有账本就无法回答"这个会话现在还有没有人在跑"，删除也就无从确认清场。

### 1.2 在 agent 会话中的流程位置

```
Gateway ──E2A──► AgentServer.dispatch
                    │
                    ├─ session.create ──┐
                    ├─ session.switch ──┤   ★ 10.3.28b：prepare → commit/abort 两阶段
                    ├─ session.fork  ───┤
                    └─ session.delete ──┘   ★ 10.3.28c：delete_session 七阶段事务
                              │
                              │  删除需要"确认清场"，即问协调器：
                              ▼
                    ★ 10.3.28d：RuntimeSessionCoordinator（谁在跑 / 第几代 / 停没有）
                              │
                              ▼
                         chat.send ──► ReAct 任务循环 ──► LLM
                              ▲
                              └─ ★ 10.3.28d 顺带把这里改为经协调器登记执行
                                 （原经 server/session.SessionManager）
```

**作用（不做会怎样）**

| 机制 | 解决什么 | 不做的后果 |
|---|---|---|
| 两阶段事务（租约） | "建会话"由多步组成（写 metadata、认领预热、绑项目、派发 KVC、切换团队归属），中途失败必须能回滚 | 失败留半成品：metadata 写了但项目没绑、或切换了一半 |
| 删除七阶段事务 | 删会话前必须"停业 → 清场 → 拆房"，且拆到一半失败要能回滚或标记需恢复 | 目录删了但后台还在跑；或后台停了但目录没删，且无法重试 |
| 执行协调器 | 一个会话可同时有多个执行（chat 轮 + cron + 团队轮），删除要逐个等它们真退出 | 只能"一刀切"，超时不知道是谁没停，`recovery_required` 无从判定 |

## 2. 核心概念

### 2.1 两个 chan 不是两个状态

这是本项目最容易误读的一点，先钉死：**`SessionExecutionHandle` 只有一个状态字段 `state`，`terminal` 与 `done` 都是 channel，表示"两件事分别做完了"，不是两个状态。**

| 事件 | 含义 | 谁做完（close 责任方） | 与 `state` 的关系 |
|---|---|---|---|
| **`terminal`** | 业务结果已定（成功 / 失败 / 取消） | `registry.markTerminal` | close 后 `state` 已是终态且**不再变** |
| **`done`** | 收尾做完了（关流、清引用、刷会话状态、终态标记入队），执行方可以退出 | 执行方自己（`produce`/`tracked` 的 defer 最后一行） | 与 `state` 无关，可能已终态很久 |

**顺序恒为 `terminal` 先关、`done` 后关**，但没有任何代码依赖这个顺序。

### 2.2 三者对照表

| 场景 | `terminal` | `done` | `state` |
|---|---|---|---|
| 刚创建 | 未关 | 未关 | `QUEUED` |
| 开始跑 | 未关 | 未关 | `RUNNING` |
| 业务成功 / 失败 | **关** | 未关 | `SUCCEEDED` / `FAILED` |
| ↑ 其 defer 跑完 | 关 | **关** | 不变 |
| 业务被取消 | **关** | 未关 | `CANCELLED` |
| ↑ 其 defer 跑完 | 关 | **关** | 不变 |
| 排队中被摘掉（未开跑，无 defer） | **关** | **关**（同时） | `CANCELLED` |
| 取消超时未停 | 未关 | 未关 | **保持原样**（不标 CANCELLED） |

### 2.3 谁等哪个

| 等待者 | 关心什么 | 等哪个 | 不等另一个的理由 |
|---|---|---|---|
| `close_session` / `cancel_handles` / `_wait_for_handles` | 执行方是否真的退出（收尾已做完） | `done` | 等 `terminal` 会提前返回，此时 defer 还在跑，删目录会撕碎未收干净的流 |
| `_run_unary(waitForTerminal=true)` | 业务结果是否已定 | `terminal` | 等 `done` 要等完整个收尾，白等 |

**"清场"等 `done`，"收结果"等 `terminal`。** 两者用途正交。

### 2.4 Go 与 Python 的字段映射

| Python | Go | 说明 |
|---|---|---|
| `handle.task: asyncio.Task` | `cancel context.CancelFunc` + `done chan struct{}` | Task 的"能取消"+"能等"两个能力拆开 |
| `handle.terminal_event: asyncio.Event` | `terminal chan struct{}` | Event 只 set 一次，chan 只 close 一次 |
| `asyncio.Event` 的 `set()` 幂等 | `sync.Once`（`terminalOnce` / `doneOnce`） | Go 的 `close` 重复即 panic |
| `contextvars.copy_context()` | `context.Context` 的 Value | Go 的 ctx 同时承载取消与值 |
| `task.cancel()` 硬取消 | `ctx.Done()` 协作式取消 | Go 侧 adapter→agent→LLM 全链必须传 ctx 且检查 |

### 2.5 generation

`session_id` 可以反复重建（切模式、断线重连、fork 回来），每次 `RegisterSession` 时代次 +1。所有针对会话的操作都带 `generation` 参数，不匹配则不匹配即返回"无此会话"，避免误伤上一代残留。

`_generations` 是**单调计数器**（`dict[str]int`），即使 `_sessions` 里记录被 CLOSED 清掉，重新注册也是 `旧值+1` 而非从 1 开始。

### 4.3 `SessionExecutionHandle` 的字段（Go 形态）

```go
type SessionExecutionHandle struct {
	ExecutionID          string
	SessionID            string
	RequestID            string
	Generation           int
	WorkKind             SessionWorkKind
	ChannelID            string
	Team                 *TeamExecutionDetails
	ParentExecutionID    string
	RootWorkKind         SessionWorkKind
	RootRequestID        string
	WaitingControlIDs    map[string]struct{}
	State                SessionExecutionState
	CreatedAt            float64
	StartedAt            *float64
	FinishedAt           *float64
	Error                string
	CancellationRequested bool
	RetainOwnerTask      bool

	// ── Go 增量：等价的 asyncio.Task 与 asyncio.Event ──
	// Cancel 等价 handle.task.cancel()
	Cancel context.CancelFunc
	// Done 等价 "await handle.task"；由执行方 defer 最后一行 close
	Done chan struct{}
	// Terminal 等价 handle.terminal_event；由 registry.markTerminal close
	Terminal chan struct{}
	// Agent 等价 handle.agent（TypeAny，仅执行期持有）
	Agent any

	terminalOnce sync.Once
	doneOnce     sync.Once
}
```

**与上游的差异**（记入 §8）：

- Python `handle.task` 一个字段承载"取消 + 等待 + 生命周期标记"；Go 拆为 `Cancel` + `Done` + `doneOnce`。
- Python `terminal_event` 是 `asyncio.Event`；Go 用 `chan struct{}` + `terminalOnce`。
- Python `agent: Any` 无类型约束；Go 用 `any` 并在 `markTerminal` 里置 nil。

### 7.4 `_run_stream` 的 Go 形态（关键）

```go
	// ⑦ schedulerExisted, schedTimeouts = scheduler.CloseSession(sid, generation, waitTimeout)
	// ⑧ !schedulerExisted ⇒ active 中未结束的 scheduled 项入 settling
	// ⑨ settlingTimeouts = waitForHandles(settling, waitTimeout)
	// ⑩ 合并三类超时；对非超时且未终态的 active 标 CANCELLED
	//    有超时 ⇒ {Existed:true, TimedOut:[...]} 且 record 保持 QUIESCING（不置 CLOSED）
	//    无超时 ⇒ record.state = CLOSED，{Existed:true, TimedOut:[]}
}
```

**`_request_direct_cancel` 的两批语义**（不可简化）：

```go
pending := handles 中 CancellationRequested==true
fresh   := handles 中 CancellationRequested==false
for _, h := range fresh { h.CancellationRequested = true }
cancelledTimeouts := cancelDirectHandles(fresh, waitTimeout)   // 先 cancel 再等
pendingTimeouts   := waitForHandles(pending, waitTimeout)      // 已请求过，只等
return append(cancelledTimeouts, pendingTimeouts...)
```

**等待用 `done` 而非 `terminal`**（D20 + §2.3）：

```go
select {
case <-h.Done:                    // 执行方退出
case <-time.After(waitTimeout):   // 超时
	timedOut = append(timedOut, h.ExecutionID)
}
```

### 7.6 `cancel_execution` 的分流

```go
handles := registry.Select(...)
handles = withDescendants(handles)                     // 展开子执行
handles = 排除 excludedExecutionIDs
direct  := handles 中 RequiresDirectCancel
work    := handles 中 WorkKind.Scheduled()
for _, h := range handles { if !in(direct) { h.CancellationRequested = true } }
schedTimeouts  := scheduler.CancelHandles(work, waitTimeout)
directTimeouts := requestDirectCancel(direct, waitTimeout)
// 合并；非超时且未终态 ⇒ markTerminal(CANCELLED)
// refreshSessionState
return CancelExecutionResult{Matched, Cancelled, TimedOut}
```

```go
func requiresDirectCancel(h *SessionExecutionHandle) bool {
	if h.WorkKind == SessionWorkKindSessionMessage { return true }
```
