## 1. 背景与章节范围

9.87 交付了「会话级常驻调度器」（supervisor + 双队列 + 输出租约），9.88 交付了「Goal 域模型」（`goal/` 五文件 + `GoalManager`/`GoalEvaluator`/`GoalRecord` + `sections/goal.go` 的 task-query 四函数）。两者目前**没有接在一起**：`GoalManager` 无生产构造方（`Start()` 内 `// ⤵️ #9.89` 留白），`TaskCompletionRail` 只有普通轮分支，goal 工具全仓 0 命中。

9.89 就是那根接线：让 goal 从「有域模型」变成「有可运行闭环」——一次尝试 → 评估 → 续排下一轮 / 结案。

**本章范围（替代 2026-11-05「S2 = 9.88+9.89 一份 spec」决策，2026-11-06 9.88 已单章交付）**：9.89 只做 goal_protocol 附件、transcript assessor 提示词、两个 goal 工具、`TaskCompletionRail` 的 goal 分支、`GoalManager` 的构造与注入。task-query 四函数 9.88 已落，不重写。

**本批同时承载两项上游 parity 前置对齐**（见 §3），它们是 9.89 的硬依赖，无独立验收价值，故并入本 spec 而非另立章节。

## 3. 前置对齐（并入本批，TDD 第一批）

### 3.1 缺口 A：executor 失败路径补 after_task_iteration

**现状**：`task_loop/executor.go` 失败分支（`invokeErr != nil`）只发 `task_failed` chunk 就 `return`，**不触发** `after_task_iteration`。Python `task_loop_event_executor.py` L310-331 在失败分支补一次 `AFTER_TASK_ITERATION`，带 error-shaped result + `ctx.exception`，并用 `after_fired` 守卫保证成功/失败路径只触发一次。

**修法**：照 Python 三件套 + 守卫——
1. 声明 `after_fired`（成功路径触发后置位）；
2. 失败分支：`iterInputs.Result = {"result_type":"error","error":err}` + `cbCtx.SetException(err)` + 触发 `CallbackAfterTaskIteration`（回调出错只 log 不掩盖原错误）；
3. `after_fired` 守卫防重复触发。

**why 写 error result 但 Go 当前无消费者**：Python 这是「per-round cleanup rail 对称性」契约，snapshot/otel span close 等 cleanup rail 依赖它；Go 当前消费 `after_task_iteration` 的三个 rail（TaskPlanningRail 同步 todo / SkillCreateRail 阈值提议 / TeamSkillEvolutionRail 空实现）均不读 Result，但 `_extract_goal_round_error`（本批 rail）读 `ctx.exception`。写 error result 是对齐上游形状，非冗余。

### 3.2 缺口 B：TaskIterationInputs 补 run_kind / run_context

**现状**：`single_agent/interfaces/callback.go` 的 `TaskIterationInputs` 缺 `RunKind`/`RunContext` 字段（Python `rail/base.py` L361-373 有，executor L192-193 从 task metadata 回填）。导致 `TaskCompletionRail._get_run_kind` 的三级回退链（`inputs.run_kind` → `inputs.metadata.run_kind` → `ctx.extra["run_kind"]`）在 Go 断了两级，只剩 `cbc.extra` 兜底。

**修法**：`TaskIterationInputs` 增 `RunKind RunKind` / `RunContext *RunContext` 两字段；`executor.go` 构造 `iterInputs` 时从 `task.Metadata["run_kind"]`/`["run_context"]` 回填（与 `effective` 的写入同源）。

## 5. 已知偏差（须用户确认）

1. **transcript assessor 模型解析收敛为单源**：Python 两级回退（deep_config.model / 现场构造）在 Go 收敛为 `modelSwitcher.GetLLM()` 一条，因为 `config.Model` 已由 DeepAgent 注入内层 ReActAgent，现场构造反而造第二实例。理由已记入 §4.5。
2. **executor error result 当前无消费者**：写 error result 是为对齐上游形状（§3.1），Go 仓当前只有本批 `_extract_goal_round_error` 读 exception。若后续 cleanup rail（snapshot/otel）回填，此形状即被消费。
3. **`validateGoalState` 的 revision 判据**：Python 用 `expected_revision is not None` 独立判断，Go 的 `int` 无法表达 `None`，故以 `expectedGoalID != ""` 作为「goal_id 与 revision 都参与比较」的开关。当前调用链中两者恒同源于 `RunContext`（9.87 定义），不会出现「一个有一个无」；若将来引入独立 revision 来源，需改为 `*int` 参数。回收条件：出现 goal_id 有值但 revision 未设置的真实场景。
4. **`Init` 的工具注册幂等保护**：`Start` 在 `bindLiveGoalManager` 后二次 `Init`（对齐 Python `init_rail`），但 `ResourceMgr.AddTool` 对已存在资源返回 error、`AbilityManager.Add` 对重名返回 `Added=false`，故 `Init` 开头用 `len(r.goalTools) > 0` 短路，避免重复注册刷日志。
