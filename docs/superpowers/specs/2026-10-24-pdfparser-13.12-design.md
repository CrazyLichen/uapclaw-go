## 1. 背景与定位

Agent 会话流程位置（KB 入库管线第一站的具体解析器实现，非会话主循环内）：

```
【入库管线】用户向知识库添加 PDF 文件
  → KnowledgeBase.parse_files（KB 层，后续章节）
  → AutoParser 路由（13.11，按扩展名分发）
    └─ .pdf → PDFParser（★ 本节）
         ├─ 文本通道：逐页抽取文本（pdfplumber.extract_text 对应物）
         ├─ 图片通道：逐页提取图片落盘 images/（page.images + crop + to_image(300) 对应物）
         ├─ Captioner：图片 LLM 视觉描述（13.15 已交付）
         └─ Document(text=文本+caption 拼接)
  → Chunker（13.5-13.9 ✅）→ ComputeChunkEmbeddings（13.4 ✅）→ Indexer（13.2/13.3 ✅）
  → 【会话侧】检索工具查库 → PDF 内容（含图片描述）注入上下文
```

作用：PDF 是知识库最常见的二进制文档格式，双通道（文本+图片 caption）弥补"图表内容无法作为文本抽出"的检索盲区——图表经 LLM 视觉描述转成可检索文本。

## 2. 已确认的设计决策（讨论结论）

| # | 决策点 | 结论 | 备选否决理由 |
|---|--------|------|-------------|
| 1 | 图片通道库选型 | **路线A：pdfcpu（图片）+ ledongthuc/pdf（文本）** | 否决 unipdf：需 license key（AGPL 社区许可也要申请+运行时配置密匙；无 key 运行属 EULA 违约），且与既有 ledongthuc 形成 PDF 双库并存；语义最优但运营摩擦与合规风险不成比例。pdfcpu Apache-2.0 零密匙零申请 |
| 2 | AGPL 政策 | **项目开源，AGPL 依赖可接受**（决策 1 独立结论，留后续选型参考） | 商业 EULA 仍不可、无 key 运行不采用——只走合规路径 |
| 3 | 图片语义路径 | **抽嵌入对象（XObject）原生字节**，非渲染页面区域 | 渲染等价物需 PDFium（C++，go-pdfium 要 CGO）；抽对象产出语义等价（图片→captioner→caption 并入 content）。4 项偏差归档 §8 |
| 4 | 图文关联 | **img.PageNr 页码分桶 + 文件命名 + content 追加顺序**——字面复刻 Python 的"同页+追加序"关联（Python 本就无更细的图文位置关联） | 无备选（这就是 Python 原始语义） |
| 5 | 范围 | **仅 13.12 本体**：pdf_parser.go + test；图片提取为本文件私有函数 | 否决带出公共层：Python 侧 PDF/Word 各自实现 _extract_images_*，docx 图片机制（OOXML 内嵌）与 PDF（XObject）本就不共享代码，抽公共=过度设计 |
| 6 | 真实 VLM 用例 | `//go:build llm` 隔离 | 项目惯例（规范 3.2），无 key 单测走 nil client 禁用态语义 |

## 4. 类型与接口设计

### 4.1 pdf_parser.go

```go
// PDFParser PDF 文档解析器（嵌入 BaseParser，仅覆写 ParseContent；
// Parse/LazyParse/Process/Supports 继承默认——13.10 模板）。
type PDFParser struct{ *BaseParser }

// NewPDFParser 构造（零参数，对齐 __init__(**kwargs): pass）。
func NewPDFParser() (*PDFParser, error)

// init 注册 .pdf/.PDF（对齐 @register_parser([".pdf", ".PDF"]) import 时执行；
// .PDF 被 first-wins 小写归一跳过——13.16 既定语义）。
func init()

// ParseContent 双通道解析（对齐 _parse(file_path, llm_client)）：
//  1. os.ReadFile 读入（双通道共享字节）
//  2. extractImagesByPage 一次性提取全部图片按页分桶（独立软失败）
//  3. ledongthuc 逐页 GetPlainText；非空入 content
//  4. 该页图片落盘 images/{basename}__page_{n}__img_{i}.{FileType}
//  5. CaptionImages(该页图片) → 非空 caption 紧随该页文本入 content
//  6. "\n".join(过滤空行)；空串返回（对齐 "result if result else None"）
//  7. 整体软失败：err → Error 日志 + ("", nil)（对齐 except → return None）
// Python: pdf_parser.py PDFParser._parse
func (p *PDFParser) ParseContent(ctx context.Context, doc string, llmClient *llm.Model) (string, error)

// extractImagesByPage pdfcpu 提取全部图片按页分桶（对齐 _extract_images_from_pdf_page 的产出面）。
// 回调内 io.ReadAll 取解码字节；按 img.PageNr 分桶；页内序=回调序（对象号升序）。
// 失败 → Error 日志 + 空 map + nil error（图片通道独立软失败，文本通道继续）。
func extractImagesByPage(ctx context.Context, pdfBytes []byte, outputDir, filename string) map[int][]string
```

### 4.2 主循环骨架

```go
content := []string{}
imgByPage := extractImagesByPage(ctx, pdfBytes, savedImageDir, filepath.Base(doc))
// savedImageDir="images" 复用 13.15 captioner.go 常量（Python pdf_parser 同名 output_dir="images"）

r, err := pdf.NewReader(bytes.NewReader(pdfBytes), int64(len(pdfBytes)))
// ledongthuc：NumPage + 逐页 GetPlainText（fonts map 跨页累积，read_file.go 先例）

captioner := NewImageCaptioner(llmClient)   // 单次构造（Python 每页重建但状态无变化，等价）
for pageNr := 1; pageNr <= numPages; pageNr++ {
    pageText, err := page.GetPlainText(fonts)
    if pageText != "" { content = append(content, pageText) }
    captions := captioner.CaptionImages(ctx, imgByPage[pageNr])
    for _, c := range captions { if c != "" { content = append(content, c) } }
}
result := strings.Join(filterNonBlank(content), "\n")
if result == "" { return "", nil }
```

### 4.3 对齐细节

- Python `captions = await image_captioner.caption_images(...)` 每页重新赋值、仅当页图片的 caption 入 content——Go 逐页局部变量同语义
- Python `if image_captioner:` 恒真（实例对象）残留判断——Go 直接调用（偏差 §8-6）
- Python `_extract_images_from_pdf_page` 是 static method + 逐页调用——Go 一次性批量后分桶（pdfcpu 回调天然按页序，等价重组；偏差 §8-5 部分）
- Python crop(strict) warn 重试链路不复存在——抽对象路径无渲染无裁剪（偏差 §8-5）
- 落盘命名 `{filename}__page_{pdf_page_num}__img_{img_index}.png` 的 filename 取 `os.path.basename(file_path)`（Python 实测），img_index 为页内序号；扩展名按 img.FileType（偏差 §8-3）

## 8. 偏差归档（对齐 Python 的已知差异）

| # | 偏差 | 理由 |
|---|------|------|
| 1 | 图片=嵌入对象原生字节（JPEG 原质量）vs Python 300DPI 页面区域渲染快照 | 渲染等价物需 PDFium（C++/CGO）；抽对象产出语义等价（图片→captioner→caption）。用户拍板路线A |
| 2 | 识别面=资源字典声明面 ⊇ Python 内容流绘制面（声明未绘制的图会多提） | pdfcpu 机制差异；极端 PDF 罕见，多提图片 caption 语义不算错 |
| 3 | 落盘=原生扩展名（img.FileType）vs Python 恒 .png | 原生字节配原生扩展名更保真；Python 的 .png 是渲染路径产物 |
| 4 | 页内多图序=对象号升序 vs Python 绘制序 | pdfcpu 回调确定性顺序；同页多图时 caption 顺序可能不同，页间顺序/图文关联完全一致 |
| 5 | 无 crop(strict) warn 重试链路；_extract_images_from_pdf_page 从逐页 static method 改为一次性批量+分桶 | 渲染路径不存在则无裁剪；pdfcpu 回调天然页序遍历，批量+分桶与逐页调用产出等价 |
| 6 | `if image_captioner:` 恒真残留判断 → Go 直接调用；ImageCaptioner 从每页重建改为单次构造 | Python 实测恒真分支；构造无状态副作用（仅 warn 日志），单次构造等价且 warn 单遍 |
