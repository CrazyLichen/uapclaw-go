## 1. 这一节解决什么问题

### 1.1 现状（25.0c 之前）

成员每轮模型调用时，团队状态（我是谁 / 这个团队是什么 / 还有谁）走**提示词附件**：

```
每轮 BeforeModelCall
  → teamBackend 查 DB（GetTeamUpdatedAt / GetMembersMaxUpdatedAt）
  → mtime 变了就全量重建 section（team_info / team_members）
  → builder.AddSection()  ← 进系统提示词前缀
```

三个问题：

1. **恒定内容每轮重编码**：身份块一次不变，却每次模型调用都重新编码一遍。
2. **永远无法命中 KV 缓存**：附件挂在窗口尾部，不写进历史，所以"永远在读、永远不缓存"。
3. **全量重建**：名册只是"bob 加入了"，却要把整张名册重渲一遍。

### 1.2 25.0c 之后

```
状态首次出现 → 一次性写进对话历史（<team-context> / <team-event>）
之后每轮     → 只比对四个探针，没变就什么都不做
名册变化     → 只播 join/leave/changed 的差量
基线         → 持久化到成员子 AgentSession（键 team_prompt_context）
```

**关键点：rail 每轮重建，所以基线不能放在内存**。`TeamPolicyRail` 在每轮结束时被销毁、下一轮重新构造（native harness 轮末终止），内存基线会每轮重播全部状态。基线必须落在成员自己的子 `AgentSession` state 里——与对话历史同一个 checkpoint bucket，`pre_run` 时一起恢复，两者永不漂移。

### 1.3 在 agent 会话流程中的位置

```
成员一轮处理
└─ ReActAgent.admitUserMessage(parts, source, prefix)          ← 25.0a
     ├─ cbc.Fire(CallbackOnUserMessage)                         ← 25.0c 钩子 ①
     │    └─ TeamPolicyRail.OnUserMessage
     │         ① _drop_superseded(parts)     非 leader 丢弃被取代的任务板
     │         ② parts.insert(0, <team-clock>)  时间锚点
     │         ③ fold_task_outcomes            三兄弟（F_119/F_129）
     │         ④ 附件车道注册 team.context
     │         ⑤ 兜底：tracker.pending_text → 前插 → commit
     ├─ syncPromptAttachments → runCommitCallbacks(cbc)        ← 25.0a
     └─ modelCtx.AddMessages(<user 消息>)

每轮模型调用
└─ cbc.Fire(CallbackBeforeModelCall)
     └─ TeamPolicyRail.BeforeModelCall                          ← 25.0c 钩子 ②
          ① builder.AddSection(静态 section)（保留）
          ② _announce_unattached_state  轮中出现的状态（build_team）无处搭车时投递
```

## 2. 讨论裁决（4 项 + 2 项采纳）

| 编号 | 问题 | 裁决 | 理由 |
|---|---|---|---|
| Q1 | 任务表新列怎么加 | **只改 `createTaskTableDDL`，不写迁移** | 任务表是每 session 一张动态表（`team_task_<suffix>`），随会话生命周期 drop；老会话读到零值 (`reviewers()` 空 = 无验收门，`revision=0` = 无编辑)，而编辑功能 25.4 才落，老会话本就没有编辑数据 |
| Q2 | `reviewer` 两种 JSON 格式 | **只写新对象格式**，解析侧对字符串元素宽松接受 | Go 是全新实现、无历史数据；旧格式永远不会有；生成侧只写 `[{"reviewer_id":...}]` |
| Q3 | `message_template.py` 落多少 | **拆两步**（详见 §4.4） | 全落 560 行会顺带吃掉 25.4 十二列 schema + 6 个 DAO 方法、25.2/25.3 的 47 个模板、25.6 的消息投递；且 `expand_message` 在 25.0c **零调用方** |
| Q4 | `UpdateTask` 要不要 bump revision | **要** | 否则 `TaskRevisionTracker` 本节只有单测；bump 只做"计数 + 记一笔"，不动状态机，不侵犯 25.4 |
| A | 三兄弟做多少 | **全做** + 任务表 4 列最小补齐 | 换来 25.3/25.4 不再回头改 rail 接线与测试 |
| 顺序 | 静态 section 缺口 | **维持 25.0c 优先**，`team_dispatch`/`team_task_state`/`team_bridge` 挂新 **25.0g** | tracker 是主线；静态缺口单列一节，25.2 之前补 |

### 2.1 必须记录的沉没成本

`TaskOutcomeTracker` 与 `TaskRevisionTracker` 的**生产数据源在本节落地后仍可能为空**：

- `reviewer` 列的**写入方**是 `add_task` 的 reviewer 参数 → 属 25.3（verify gate）。本节期间没有任务带 reviewer，`TaskOutcomeTracker` 只能靠单测造数据验证。
- `revision` 的写入方在 Q4 已落（`UpdateTask` bump），所以 `TaskRevisionTracker` **可以端到端验证**。

用户已明确接受这一点。

```go
sessionID := ctx.Session().GetSessionID()
hasSnapshot := manager.HasHistorySnapshot(modelCtx, sessionID)
text, _ := tracker.PendingText(sess)
lastText := tracker.LastDeliveredText(sess)
if !hasSnapshot { content = tracker.SnapshotText() } else if text != "" { content = text } else { content = lastText or SnapshotText() }
if content == "" { return true }   // 车道拥有投递权，但无内容

    hprompts.AttachmentRuntime, "agent_core.team_policy_rail", 80)
```

`DeliverText` 已存在（`attachment_rail.go:51`，`coding_memory_rail` 在用），签名与上游 `writer.add_section` 等价。
