# 30.5 WS 文件分帧通道 设计

> 日期：2026-11-28 · 状态：设计定稿（brainstorming 逐项拍板）

## 1. 范围

- 新增 kb 分帧方法族（kb.doc.upload / kb.file.upload_chunk / kb.file.upload_complete / kb.doc.download / kb.doc.cancel_upload）
- gateway 注册 kb.* 方法并薄映射到既有 file.* 协议（B1 双层复用）
- server 侧 kbadmin 上传槽位管理 + hash 校验 + KB 暂存目录落盘（复用 `attachments/upload_storage`）
- 反向流式下载（分帧回前端，前端聚合 blob URL——UI 归 30.8）
- 上传护栏：50MB 上限、upload_id TTL 清理、断连清理分片

**本批不做（X 边界拍板）**：触发解析（⤵️30.2，本批不留骨架挂点）、KB config 可调上限读取（⤵️30.2，本批固定 50MB）、前端切帧/blob URL UI（⤵️30.8）、解析任务链（30.2 独立批，本批不关注 30.2）。

## 2. 已拍板决策

| 决策点 | 结论 |
|---|---|
| 分帧通道路线 | **方案 B1（B 外壳 + A 内核）**：对外（前端↔gateway）用 kb.* 独立方法族，协议面独立（将来可按 KB config 独立调上限/背压，不动 27.x）；gateway→server 薄映射到既有 file.upload_chunk / file.read_upload_chunk 协议，server 落盘/消毒/去重/50MB 护栏全部复用 `upload_storage`，零重复建设 |
| 批次关系 | **方案 ①**：30.2→30.3→30.4 维持独立批次（各批独立提交独立绿），30.5 不涉及解析链 |
| 30.5/30.2 边界 | **方案 X**：30.5 止步于「文件安全落盘 + 反向流式下载」；upload_complete 成功即返回文件标识，不触发解析、不留骨架挂点，30.2 开工时自行加挂点，30.5 代码不动 |
| 单测入口 | gateway 层驱动：单测经 gateway 方法注册表发起 kb.* 全链（真实管线，禁窄接口/替身），映射正确性作为链路自然结果被覆盖 |

## 3. 方法族与协议面

| kb 方法 | 方向 | 职责 |
|---|---|---|
| `kb.doc.upload` | 控制面 | 发起上传：kb_id + file_name + size + file_hash；校验 KB 存在 + 大小上限（本批固定 50MB）；返回 upload_id |
| `kb.file.upload_chunk` | 数据面 | 分帧传输：upload_id + seq + data；gateway 薄映射 |
| `kb.file.upload_complete` | 控制面 | 收尾：服务端复算 hash 比对，不一致返回 `UPLOAD_HASH_MISMATCH` 并清理分片；一致返回文件落盘标识（**不触发解析**） |
| `kb.doc.download` | 下载 | 按 doc_id/file 标识反向分帧拉取，前端聚合 blob URL |
| `kb.doc.cancel_upload` | 护栏 | 取消/中断清理临时分片 |

**协议映射（B1）**：gateway 注册以上方法，全部不做 kb 业务；数据面把 `kb.file.upload_chunk` 翻译为既有 `file.upload_chunk` 协议字段转发（sessionProxyForward 同款），控制面带 kb_id/upload_id 走 E2A。kbadmin 落盘目标目录为 KB 暂存区 `kb_uploads/{upload_id}`；消毒 `SafeUploadFilename`、同名去重槽位、`MaxFileBytes` 50MB 全部复用既有实现；hash 算法沿用 upload_storage 既有口径（sha256，spec 落地时核对一致）。

## 4. 两侧改动点

**gateway 侧**（`web_handlers` 注册，比照 `registerWorkspaceFileProxies` 惯例）：
- 注册 5 个 kb 方法：控制面转发 E2A；数据面翻译协议字段薄转发；`kb.doc.download` 反向代理分帧回前端
- 零独立 HTTP 路由，全部走既有 WS 方法注册机制；对 27.x 域零改动（既有协议与 handler 不动）

**server 侧**：
- kbadmin 包新增 `handle_kb_file.go` 分发入口：upload/cancel 走 KBService（校验 KB 存在、登记 upload 槽位）；upload_chunk 复用 `attachments/upload_storage.go` 落盘链（目标目录指向 `kb_uploads/`）；upload_complete 复算 sha256 比对

**清理策略**：cancel 或 WS 断连清理临时分片；upload_id 带 TTL（超时未 complete 自动清理，防泄漏）。

## 5. 错误码（复用 E2A envelope 分流）

- `KB_NOT_FOUND`：upload 发起时 KB 不存在
- `FILE_TOO_LARGE`：超 50MB（本批固定值）
- `UPLOAD_HASH_MISMATCH`：complete 时 hash 不符（附预期/实际值）
- `UPLOAD_CHANNEL_BUSY`：同 upload_id 并发帧/乱序保护
- `KB_UPLOAD_NOT_FOUND`：chunk/complete 引用不存在的 upload_id（如超时清理后）

## 6. 测试策略

- **单测（gateway 层入口驱动）**：经 gateway 方法注册表发起 `kb.doc.upload` → `kb.file.upload_chunk`（粘包/乱序/断包场景）→ `upload_complete` / `cancel_upload` 全链真实管线（真实内存 SQLite + 真实 `upload_storage`，禁窄接口/替身）；错误路径（KB 不存在/超限/hash 不符/upload_id 失效）同链覆盖
- **集成测试**（随本批交付，30.1 先例，不等 30.9）：WS → gateway 薄映射 → agentserver → upload_storage 落盘 → hash 校验全链，小真实文件（txt/md），跨 ≥3 internal 子系统过双层审计门禁；下载反向流式端到端聚合还原比对
- 覆盖率 ≥85%
