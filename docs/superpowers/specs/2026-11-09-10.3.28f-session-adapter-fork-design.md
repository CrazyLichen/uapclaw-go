## 1. 概述

### 1.1 一句话

Go 的 `DeepAdapter` 只有**一个** `instance`，所有会话共用一个 DeepAgent 与一套 rail/context engine。Python 的 `JiuWenSwarmDeepAdapter` 是**双形态单类**：根只做路由与模板持有，每个会话由 `type(self)()` 造一个 child 独享 DeepAgent。本节把 Go 补齐到这个结构，并把根退化成纯路由器。

### 1.2 在 agent 会话中的流程位置

```
Gateway ──E2A──► AgentServer.dispatch
                    │
                    ├─ chat.send ──► AgentRuntime.Stream                    ★ 已有
                    │                   └─ agent.ExecuteMessageStream / ProcessMessageStream
                    │                        └─ UapClawSwarm → ensureAdapter → uc.adapter
                    │                             └─ AgentAdapter.ProcessMessageStreamImpl
                    │                                  │

### 1.3 作用（不做的后果）

| 目标（用户定的优先级） | 不做的后果 | 本节怎么达成 |
|---|---|---|
| **① 为 25.8 铺路** | `stop_subagent_runtimes`（R-2）**没有可操作对象**——`_subagent_controls` 挂在 DeepAgent 上，Go 只有一个 DeepAgent 服务全部会话，"该会话的子代理运行时"无处可寻 | `entries` 存真 child，`GetLiveSessionInstance(sid)` 返回该会话在跑的 DeepAgent |
| **② 内存回收** | `CleanupSessionAdapter` 恒返回 false（`entries` 无生产写入方），会话删了 DeepAgent 不释放；Python 的 TTL 2h 空闲淘汰整层缺失 | 重写 `CleanupSessionAdapter` + `evictIdleSessionAdapters` |
| **③ 运行时隔离** | 一个会话切模型 / 切 rail，`applyModelToReactAgent` 与 `UpdateAgentRails` 改的是**共享**的 ReAct 图与 rail 表，另一个会话跟着变 | child 各自 `CreateInstance` + `UpdateAgentRails`，rails / tools / context engine 全在各自 instance 上 |

### 1.4 为什么 rails / tools / context engine 不需要"搬迁"

核实结论（`deep_agent.go:597-627`）：`DeepAgent.RegisterRail` 把 rail 挂到 **`d.registeredRails` + 该 agent 的 callbackManager**，并对 rail 执行 `r.Init(ctx, d)`（`d` 是那个 DeepAgent）。同理 `tools` 与 `reactAgent.context_engine` 都挂在 instance 上。

`DeepAdapter` 里 `taskPlanningRail` / `subagentRail` / `streamEventRail` 等字段只是**防重复注册的记账指针**，不是归属。child 是全零值的 `DeepAdapter`，九个 `ensure*Rail` 会因为字段为 nil 而各跑一遍、注册到 child 自己的 instance 上 —— **这正是 Python 的行为**。

因此本节**不需要搬运任何 rail/tool/contextEngine 代码**，只需要把分流头插进去，让方法体内的 `d` 变成 child。

### 2.3 `CodeAdapter` 无 child 的后果（核实记录）

Python `JiuwenSwarmCodeAdapter` **不覆写** `_new_session_scoped_adapter`，靠 `type(self)()` 天然造出完整 CodeAdapter，20+ 覆写方法（`_build_agent_rails` / `_get_tool_cards` / `_build_configured_subagents` / `_update_rails_for_mode` / `_update_runtime_config`）全部保留。

Go 是**两个类型 + 组合**，`c.deep` 不知道自己属于 `CodeAdapter`。若 child 取 `*DeepAdapter`：
- `buildCodeAgentRails` 方法不存在 → `UpdateAgentRails` 跑 deep 版本 → **注册 LspRail/ProjectMemoryRail/CodingMemoryRail 失败，静默降级成 deep 模式，不报错**。

因此 child 工厂必须返回**完整的新 CodeAdapter**，不能从现有对象里"提取 deep"。用户确认的解法：复用现成的 `CreateAdapter("harness", mode)`。

#### 4.3.1 `getOrCreateSessionAdapter` 骨架

对齐 `:3921-4434` 的**骨架**，保留锁与顺序，7 组重建判据留位。步骤：

2. sid := sessionAdapterKey(sessionID)
3. lock := d.sessionAdapters.locks[sid]（不存在则建）    // 对齐 :3949
4. lock.Lock(); defer lock.Unlock()
5. existing := entries[sid]                              // 对齐 :3951

#### 4.3.3 `CleanupSessionAdapter`（重写）

对齐 `:3642-3755`，步骤：

```
1. sid := sessionAdapterKey(sessionID)
2. if heartbeatService.shouldRetainSession(sid) → return false   // :3650-3656
3. if d.isSessionScoped {                                        // :3658-3667
       if parentSessionID != sid → return false
       if hasLiveRootPermissionOwner(sid) || isSessionActive(sid) || isDeepAgentExecutingForSession(sid) → return false

4. lock := locks[sid]                                            // :3668-3690

   a. adapter := entries[sid]

**Go 化偏差**：Python 用 `lock.locked()` + `_waiters` 内省判断"是否有人在等"，Go 的 `sync.Mutex` 无此能力。改用 `sessionAdapterGuard{mu sync.Mutex, waiters int32}` 包一层，`Lock` 时 `waiters++`（见 §8 D-3）。

### 4.7 状态一致性（DEC-4）

对齐 Python 的两条机制：

**机制 1：改运行态必先取正在跑的 instance**

| RPC | Python | Go |
|---|---|---|
| plan 状态写 | `plan.py:106` → `get_live_session_instance` + `resolve_live_agent_session`；取不到再 `ensure_live_session_instance`（:119） | `PlanModeController` 侧改为先取 live instance（Go 的 plan 同步在 `runtime/plan.go`，本轮补） |
| `session.plan_status`（只读） | 同上，取不到回退 metadata（`handlers/session.py:212`） | 同上 |
| 压缩 / 用量 / 摘要 | **根分流 → child**（`compress_context` :21834 等） | §4.4 分流头已覆盖，**不需要**额外汇总调用方 |

**关键修正**：上一轮讨论中我提出"Go 的 context engine 在 ReAct 图里，所以压缩要走根自己的 instance"——**错误**。Python 的 `compress_context` 第一行就是根分流；对齐后 `d.instance.react_agent.context_engine` 自动是 child 的。因此**不需要把压缩/用量/摘要列入"取 live instance"范围**，它们由分流头解决。

**机制 2：`defer` 守卫只给 plan 状态**

对齐 `plan.py` 的 `may_hold_state` + `_active_sessions`：会话活跃时 plan 状态写入排队/延迟。压缩、切换模式等**不加 defer**（与 Python 严格度一致）。
