## 1. 背景与定位

11.25 是 uapclaw 接入 ACP（Agent Client Protocol）生态的网关对端。10.6.24d 已交付 Agent 侧全链（AcpOutputManager/acp_output_tools、handleACPToolResponse、AgentManager ACP 分支、权限确认桥、AcpStdioClient），10.2.9/10.2.10 已交付 E2A↔ACP 适配器与 protocol.go 构造器，11.9 已交付 GatewayServer 多路由本体——但整条链路断在 Gateway：`acp.output_request` 出站没有桥转发 IDE，IDE 的工具响应没有入口回流，`/acp` 路由未装配。本节补上这段，ACP 全链闭环。

流程位置：

```
IDE / Agent Client（Zed、VSCode ACP 插件等）
   │ ① ACP JSON-RPC over stdio          │ ② ACP JSON-RPC over WebSocket
   ▼                                     ▼
AcpChannel（stdio 桥）              GatewayServer /acp 路由（19001）
   │  WS 客户端转发 type=req 帧          ├─ 入站 handleJsonrpcRequest：6 方法 JSON-RPC → Message
   └────────────────────────────────────┤  入站 InboundIntercept：工具响应 → acp.tool_response
                                        ├─ 出站 Send() acp 分支 → sendMessage：
                                        │  chat 事件流 → session/update 通知
                                        │  final+idle → prompt result(end_turn)
                                        └─ 出站 OutboundIntercept：acp.output_request 原样转发 IDE
   ▼
InboundGatewayServer → MessageHandler（ACP 别名链：外会话 ↔ 内部会话）
   ▼ E2A 协议（transport byte 管道）
AgentServer（AgentManager ACP 分支 + acp_output_tools + handleACPToolResponse，已就绪）
```

## 3. 架构总览（双模式）

```
模式一（默认，uapclaw acp 无 --gateway-url）——进程内自举 + 本地回环：
┌────────────────────────── 同一进程 ──────────────────────────┐
│ AgentServer(goroutine) ←ChannelTransport→ AgentClient        │
│        ↓ E2A                                                  │
│ MessageHandler(别名链) → ChannelManager                       │
│        ↓ Send()                                               │
│ GatewayServer :19001 ——— /acp 路由 ←—— AcpGatewayBridge      │
│        ↑ WS 回环（本地）          AcpChannel（stdio 桥本体）   │
│ IDE ⇄ stdin/stdout JSON-RPC ←—— AcpChannel                    │
└──────────────────────────────────────────────────────────────┘
自举序：复用 runAppCmd 步骤 1-6（workspace/logger/env/crypto/config/extensions）
       + AgentServer + AppGatewayServer（含 /acp 装配）+ AcpChannel

模式二（--gateway-url ws://…/acp）——远端桥进程，Python jiuwenswarm-acp 1:1：
┌── 桥进程 ──┐            ┌──── 远端 uapclaw app/gateway 进程 ────┐
│ AcpChannel │── WS 客户端 →│ GatewayServer /acp → AcpGatewayBridge │
│ IDE ⇄ stdio│            │   → MessageHandler → E2A → AgentServer │
└────────────┘            └────────────────────────────────────────┘
```

关键架构含义：
- AcpChannel 的 WS 客户端逻辑是唯一传输路径；Python `_dispatch_message` 三分派（on_message_cb 回调 / WS / 总线 publish）中 ①③ 分支 Go 侧为死代码（Python 里同样从未被 jiuwenswarm-acp 入口使用），偏差归档 §9-1
- `/acp` 路由无冲突：模式一里 AcpChannel 是 WS 客户端、GatewayServer 是服务端各占一头；ChannelManager 的 acp 槽位归 GatewayServer（RegisterExternalChannel("acp")），AcpChannel 不注册 BaseChannel（对应 Python 两入口从不共存同一进程）
- 模式一 19001 端口被占时自举失败：错误信息引导用 --gateway-url 指向已有实例（Go 扩展边界，偏差 §9-6）

### 4.2 gateway/acp_bridge.go（AcpGatewayBridge）

职责：GatewayServer /acp WS 路由协议对端。入站收 IDE JSON-RPC 请求（6 方法）与响应（工具结果回流），出站把 chat 事件流转成 session/update 通知与 prompt result。

```go
type AcpGatewayBridge struct {
    onMessageCb       func(ctx, *schema.Message) bool  // dispatchOnMessage（InboundGatewayServer 链）
    bindSessionClient func(sessionID string, ws *websocket.Conn)
    channelID         string                            // "acp"
    idleFinalizeSecs  func() float64                    // Python 值/可调用双态 → 统一 func，默认 3.0
    mu                sync.Mutex                       // 保护五表
    requestCtxByReqID map[string]*acpGatewayRequestCtx
    activePromptBySession map[string]string
    knownSessions     map[string]struct{}
    pendingRPCCountBySession map[string]int
    pendingRPCSessionByID   map[string]pendingRPCEntry // {sessionID, ws, createdAt}
}

type acpGatewayRequestCtx struct {  // Python AcpGatewayRequestContext
    jsonrpcID any          // str|int 双形态保留（NormalizeJsonrpcID 先例）
    sessionID, userMessageID string
    state    AcpSessionUpdateState
    pendingStopReason string
    sawChatFinal, sawProcessingIdle bool
    clientWS  *websocket.Conn
    idleFinalizeTimer *time.Timer
}
```

- 六方法分派（handleJsonrpcRequest）：initialize（AcpDefaultCapabilities+clientCapabilities 合并）/session/new（`acp_`+12hex 生成+bindSession）/session/prompt（extractPromptText→CHAT_SEND、mode=agent.plan、metadata 带 jsonrpc_id）/session/cancel/session/list/session/load 拒绝（-32601）
- 三拦截器：InboundIntercept（JSON-RPC response 识别→BuildACPToolResponseMessage→dispatch→未知/迟到回 accepted=false+ignored=true）；OutboundIntercept（event_type=acp.output_request→raw jsonrpc 原样发+pending 注册+60s 清扫）；Cleanup（按 ws 清 pending）
- SendMessage 出站转换（GatewayServer.Send acp 分支调用）：delta→update+usage；reasoning/tool 系/todo/subtask→update；chat.final→final text+end_turn 三态；error→-32603；processing_status→idle 计数+finalize 调度
- 时序辅助：markStreamActivity（流活动重置 idle）/shouldWaitForFinalTextBeforeEndTurn（等迟到 final text）
- 注入方式（R1 拍板）：`SetAcpBridge()` setter + `InstallDefaultAcpHooks()`（对齐 _install_default_route_hooks）；acp_bridge.go 与 GatewayServer 同包零依赖问题

### 4.3 gateway/channel_manager/protocol/acp/（AcpChannel）

职责：IDE 进程侧对端。stdin 逐行 JSON（E2A envelope 或 JSON-RPC），stdout 逐行 JSON-RPC。per-request ctx（e2a/jsonrpc 双 response_mode）、会话上下文合并、pending RPC、stdin EOF 5s 宽限。

```go
type AcpChannel struct {
    cfg        AcpChannelConfig  // enabled/channelID/defaultSessionID/metadata
    gatewayURL string            // 空 = 进程内自举模式
    gwConn     *websocket.Conn
    onMessageCb func(*schema.Message) bool  // 死代码归档 §9-1
    mu         sync.Mutex                  // 四表 + stdout 写互斥（§9-2）
    requestCtx map[string]*acpRequestCtx   // 含 responseMode/sequence
    sessionCtx map[string]map[string]any   // session/new params，prompt 时 setdefault 合并
    activePromptBySession map[string]string
    pendingRPCSessionByID map[string]pendingRPCEntry
    stdout     io.Writer    // os.Stdout 固定句柄（对应 _ACP_STDOUT = sys.__stdout__）
}
```

- 入站三路由（handleRawLine）：JSON-RPC request（六方法，响应写 stdout）→ JSON-RPC response（BuildACPToolResponseMessage→dispatch→maybe finalize）→ E2A envelope（session/prompt→CHAT_SEND 双键 content/query；未知 method 报错 -32603）
- WS 客户端：ensureGatewayConnection（12 次×0.15s×2ⁿ 封顶 2s）→ gatewayReaderLoop（handleGatewayFrame：jsonrpc request→stdout 直写+pending 注册；type=res/event→messageFromGatewayResponse/Event 重建 Message→自身 Send 链）。模式一与模式二唯一区别是 gatewayURL 指向，代码路径零分叉
- 双模式出站链（Send→jsonrpc 模式 sendJsonrpcMessage）：delta/reasoning/tool 系/todo/subtask→session/update 通知；final/error/interrupt_result→result/error+ctx 清理；res.ok accepted 吞掉；processing_status idle 三态。E2A 模式（messageToE2aResponse）完整复刻：sequence 递增、五种 response_kind、provenance converter 串改 Go 路径名

## 5. 数据流与关键时序

### 5.1 一次 session/prompt 生命周期（模式一 jsonrpc）

```
IDE → AcpChannel：session/prompt id=1 sid=s1
  extractPromptText → reqID=acp_{12hex} → requestCtx/activePrompt 登记
  → WS type=req chat.send（content/query/session_id/mode=agent.plan）
→ GatewayServer /acp：forward_methods 命中 + acp early-return → onMessageCb
→ InboundGatewayServer → MessageHandler：
  prepareAgentDispatch：resolveAcpInternal(s1)
    → session.create RPC → aliases[s1]=acp_xx → msg.session_id 改写
  → E2A chat.send → AgentServer
← server_push e2a.chunk ×N → ChunkToMessage → PublishRobotMessages
← ChannelManager.Send(channel=acp) → 桥 sendMessage
  chat.delta → session/update(agent_message_chunk)
  → GatewayServer 定向发（requestKey/sessionKey）
← AcpChannel WS reader → messageFromGatewayEvent → activePrompt 反查
  → Send() → jsonrpc 模式 → stdout session/update
← processing_status idle + chat.final → prompt result(end_turn) → stdout result 帧
  → ctx 清理
```

### 5.2 end_turn 收尾三态与 idle finalize

```
chat.final 到达 → sawChatFinal=true
  ├─ sawProcessingIdle=false → 等后续 idle 触发收尾
  └─ sawProcessingIdle=true → 收尾判定
processing_status(idle) 到达 → sawProcessingIdle=true → 收尾判定
收尾判定（两处共用）：
  pending RPCs > 0 → pendingStopReason="end_turn" 挂起
  shouldWaitForFinalText?（sawChatFinal=false 且 assistantText/messageID 非空）
    是 → 调度 idleFinalizeTimer(3s)
         ├─ 3s 内 chat.final 到 → cancel timer + 补发 final text 再走收尾
         └─ 超时 → 直发 result(end_turn)（缺尾部文本既有语义）
    否 → 直发 result(end_turn) + ctx 清理
触发解除：delta/tool 系事件 → markStreamActivity（idle=false+cancel timer）
挂起解除：工具响应回流 → resolvePendingRPC → count-- → 0 时
         maybeFinalizeDeferredPrompts → 上框收尾判定
```

timer 并发模型：`*time.Timer` + 回调首行校验 `ctx.idleFinalizeTimer == 自己`（Python current_task 比对同构，防 superseded 误收尾）。

### 5.3 pending RPC 生命周期

```
注册：OutboundIntercept 捕获 acp.output_request
  → pendingRPCSessionByID[jrpcID]={session,ws,now} → count++ → 60s 清扫
  → raw jsonrpc 原样发 IDE
回流：InboundIntercept 捕获 response → pop → BuildACPToolResponseMessage
  → dispatch → AgentServer.handleACPToolResponse（已就绪）
  → resolvePendingRPC → maybeFinalizeDeferredPrompts
兜底：未知/迟到 → accepted=false+ignored=true+reason；断连 cleanup(ws) 按 ws 清
```

### 5.4 会话别名（双向）

```
入站：external → resolveAcpInternal（双检锁）
  ├─ aliases 命中直返
  └─ isKnownSessionID?（12 前缀 sess_/tui_/acp_/cron_/feishu_/wechat_/xiaoyi_/
     dingtalk_/wecom_/telegram_/discord_/whatsapp_ 或 :: 5/6 段全非空）
     是→desired=原样；否→desired=GenerateChannelSessionID("acp")
  → session.create(desired) → resolved（三级回落）→ aliases 登记
出站：resolved → resolveAcpExternal：metadata["acp_original_session_id"]
     优先 → aliases 反查 → 原样
豁免：initialize/session.create 与非 acp 渠道直通
```

## 6. 错误处理矩阵

| 层 | 错误源 | 处理 |
|---|---|---|
| AcpChannel 入站 | stdin 行 JSON 解析失败 | stdout 写 E2AResponse failed 帧（-32603），继续循环 |
| AcpChannel 入站 | 不支持的 E2A method | -32603 错误帧 |
| 桥/通道 JSON-RPC | params 校验失败 | -32602 |
| 桥/通道 JSON-RPC | 未知方法/session/load | -32601 |
| 桥/通道 JSON-RPC | 内部异常 | -32603 + Error 日志（含 method） |
| 出站事件 | chat.error | -32603（error→content→"Agent error" 兜底）+ ctx 清理 |
| MessageHandler | session.create 失败 | 错误上抛（不静默） |
| AcpChannel WS | 连接失败 | 12 次指数退避 → 进程退出非零 |
| AcpChannel | stdin EOF | 5s 宽限等 pending 清空 → 退出 |
| GatewayServer 模式一 | 19001 被占 | 错误引导 --gateway-url（§9-6） |

日志同步（规则 3）：Python 全部 logger 调用逐条对齐（[ACP] stdio inbound failed / pending RPC entry expired / ignoring unknown/late client rpc response / gateway connect attempt N/M failed 等），字段结构化，ComponentGateway，文案英文。
