## 2. 组件设计（落点 `internal/swarm/server/kbadmin/`）

新增文件（对齐既有命名风格，同步更新 doc.go）：

```
kbadmin/
├── worker.go       # ParseWorker：固定池 + channel 唤醒 + 启动轮询恢复
├── pipeline.go     # pipelinePlans 声明式步骤计划 + 执行骨架
├── progress.go     # progressSink 观察者：台账写入 + 事件发布 + 停滞扫描
├── doc_service.go  # DocService 真实现（D-30-1-2 回填）
└── （task_dao/doc_dao/kb_dao/store.go 按列扩展）
```

| 组件 | 职责 |
|---|---|
| ParseWorker | N 个常驻 goroutine，空闲阻塞唤醒 channel；启动轮询：`pending` 重新入队、`processing` 标 cancelled(server_restart)——只认确切信号，不推断中途进度 |
| pipelinePlans | SimpleKB = {parse, chunk, embed}；GraphKB = {parse, chunk, embed, triple}；每 step `{name, run func(ctx, job) error}` |
| stage 步骤 | parse=`parser.Process`；chunk=`chunker.ChunkDocuments`→落台账（id 对齐向量库）；embed=`indexManager.BuildIndex`（IndexConfig 构造与 `database_name` extra 同 AddDocuments）；triple=`TripleExtractor.Process`+triple 索引 |
| progressSink | 观察者：每步完成/失败写 `kb_task.progress`+`kb_doc.stages_json/last_activity_at`，并经既有事件通道发布事件；周期扫 `last_activity_at` 超阈值标 `stall_state=suspected`（仅展示+cancel 入口，不自动取消，对齐 WeKnora） |
| DocService | `SubmitParseTask`（upload 挂点：hash 去重 DOC_DUPLICATE 判定）、reparse、cancelParse（per-task `context.WithCancel`）；extracting 登记未实现分支 |
| KBService 扩展 | create/delete 三库类型编排：graph 装配 TripleExtractor；MultiKB 落聚合配置、无文档操作、delete 级联子库引用检查 |
| kb.task 通信面 | progress（拉全量）/ subscribe（推送）注册进 kbadmin 分发 |

**架构不变量**：kbadmin 是编排层，retrieval 保持纯组件（吃 ctx 返回结果，零回调注入）；上报走观察者、取消走 ctx（13.x 组件已普遍吃 ctx）、编排归 worker。观察者不得反向伸进 retrieval。

## 3. 状态机与数据流

```
pending ──worker认领──▶ processing ──全部 stage 成功──▶ completed
   ▲                        │ │ │
   │                        │ │ └─cancel(ctx)──▶ cancelled（可 reparse）
   │                        │ └───stage 失败──▶ failed（标 parse/index，可 reparse）
   └──reparse（新任务行）    └───启动期发现──▶ cancelled(reason=server_restart)
```

- reparse：不复活旧行，新建 `kb_task` 行 + `kb_doc.parse_status` 回 pending、`retry_count+1`；旧行保留作历史
- `stages_json` 每阶段 `{stage, started_at, finished_at, error}`；extracting 对两类库均落占位、不进 processing（⤵️30.4）
- 失败分级：parse/chunk 失败 → `failed(parse)`；BuildIndex/triple 失败 → `failed(index)`；LLM 二阶段失败 → `enhance_failed` 独立标记（⤵️30.4 本批不动）
- 认领：CAS `UPDATE ... WHERE status='pending'` 保证双 worker 单认领
- 取消：DAO 标 cancelling → `taskCancelFn(taskID)()` → 组件 ctx 检查点退出 → worker 收尾标 cancelled、回滚（本任务已写 chunks 先删向量库再删台账）
- 一致性固定顺序：向量库先行（难回滚侧）→ DAO 跟写 → 失败回滚

## 4. 错误处理（复用 E2A envelope 错误码族）

| 场景 | 处理 |
|---|---|
| 同 KB content_hash 命中 completed 文档 | `DOC_DUPLICATE`，建任务前拒绝 |
| 文件超上限（KB config 可调，无配置回退 50MiB） | `FILE_TOO_LARGE`（挂点侧判定） |
| 不支持的格式 | `failed(parse)` + error_msg，不重试 |
| BuildIndex/triple 失败 | `failed(index)` 可 reparse；已写部分按 doc 维度清理 |
| 认领竞争 / DB 写失败 | Error 日志（ComponentAgentServer，含上下文字段）+ 任务回 pending 或 failed，不 panic |
| extracting 执行 | 唯一未实现分支：`KB_NOT_IMPLEMENTED` 式登记错误，状态机照常运转（测试断言不误伤主链） |

## 6. 测试策略（≥85%，真实链路纪律——禁窄接口/替身，替身仅限网络边界）

### 单测覆盖点（全部讨论点）

- 状态机：全状态×事件转移表驱动（真实 SQLite 内存库 + 真实 worker）
- pipeline：声明式计划表（SimpleKB/GraphKB 各 step 序列断言）；真实 parser/chunker（txt/md 小文件真链）；embedding 用本地固定向量服务（httptest 边界）；triple 用真实 extractor + stub LLM 端点
- 并发：双 worker CAS 认领竞争（断言单认领）；ctx 取消中途退出（逐 stage 断言）；停滞标记扫描
- hash 去重 / DOC_DUPLICATE；extracting 未实现分支不误伤主链；configJSON 透传断言
- CAS 单认领、孤儿恢复（processing 行 → cancelled(server_restart)、pending 行重新入队）

### 集成测试（`tests/integration/kbadmin` 扩展，走完整 gateway 链路，禁 agentserver 层短路直调）

1. **上行全链**：WS 请求（kb.kb.create / kb.doc.upload 发起 / kb.doc.reparse / kb.doc.cancelParse）→ gateway 薄转发 → E2A → agentserver `kb.` 分发 → DocService/KBService（比照 11.9/11.25 既有 gateway 多路由先例：真 gateway 实例 + 真 WS client）
2. **解析全链**：upload 挂点接管 → pending → worker 认领 → 真 parser/chunker → embedding（本地固定向量服务）→ completed → 台账与向量库 id 对齐断言
3. **下行推送全链**：progressSink 事件 → 事件通道 → WS 推回 → 测试客户端从 gateway 侧收到 progress/终态帧断言；断线重连调 kb.task.progress 拉全量对齐
4. **取消/恢复全链**：cancelParse 经 gateway 下发 → cancelled 推送可达；kbadmin 域重建触发孤儿恢复
5. **回填回归**：30.5 分帧上传经 gateway 全链（D-30-5-1 上限可调 + D-30-5-2 挂点触发）；30.5 既有测试全绿不动

## 9. Provider 分派（2026-12-08 追加拍板，方案②）

KB config 新增 `store` 段，kbadmin factory 按 provider 分派 collection/indexer 构造，缺省 chroma：

```json
{"store": {"provider": "sqlite", "milvus_uri": "", "milvus_token": ""}}
```

| provider | collection | indexer | 备注 |
|---|---|---|---|
| chroma（默认） | ChromaVectorStore 本地持久化（30.1 现状） | ChromaIndexer | 语义检索 ✅（显式向量）；稀疏半边受限（见下） |
| sqlite（D-25-7 私有 provider） | SQLiteVectorStore（FTS5 bm25 + sqlite-vec） | **SQLiteIndexer（本批新增）** | 真混合检索；Add 为 UPSERT 幂等 |
| milvus | 无独立 collection 构造（索引器建表时创建） | MilvusIndexer（13.3 现成复用） | 需 config 给 milvus_uri/token |

### chroma 稀疏半边限制登记（13.x 遗留，本批显性化）

- 官方无 BM25 关键词排序检索（Python chroma_store.py:308 注释原文）；`where_document $contains` 官方支持但只是子串过滤
- 本地模式 `SparseSearch` 走 query_texts 依赖 collection 的 embedding function；为规避 chroma-go v2 强制 ONNX 默认 EF（CI SIGSEGV），挂了 ConsistentHash 伪 EF → **稀疏半边为伪语义，Hybrid 质量被拖累**
- 影响面：默认 chroma KB 的 kb.search.test（30.6）混合检索结果受影响；sqlite/milvus provider 不受影响
- 回收条件：chroma 官方引入 BM25，或 ONNX EF 部署路径可控后换真 EF

### SQLiteIndexer 与 ChromaIndexer 的语义差异（登记偏差）

- 去重：chroma 走 collection.Get 查重跳过；sqlite Add 为 UPSERT 同 id 覆写（幂等等价，重解析先删后建语义不变）
- DeleteIndex：sqlite Delete 仅支持 id 过滤 → 新增 `SQLiteVectorStore.IDsByDoc` 按 docID 取 chunk id 再删

## 10. ChromaBleveStore：chroma 域稀疏半边扩展（2026-12-08 追拍，方案①）

**定位**：chroma 域的扩展实现（与 chroma.go 同在 vector_store 包），kbadmin 的 chroma provider 路径换用；13.x `ChromaVectorStore.SparseSearch` 保持 Python 对齐原样不动。

**结构**：`ChromaBleveStore` 包装 `*ChromaVectorStore`（向量半边原样透传）+ 独立 Bleve 倒排索引（BM25 关键词排序，替代伪 EF 的 SparseSearch 路径）；配套 `ChromaBleveIndexer`（indexer 包，构建在 ChromaBleveStore 之上——单一写入咽喉，双写一致性收口到 store 层）。

| 方法 | 实现 |
|---|---|
| Search(queryVector) | 透传 chroma（真向量语义不动） |
| SparseSearch(queryText) | Bleve 检索（scorch BM25 打分，按关键词排序） |
| HybridSearch | chroma 向量 + Bleve 稀疏 → `utils.RRFFusion`（sqlite 同款） |
| Add | chroma 先写（难回滚侧先行）→ Bleve 后写；Bleve 失败上抛（调用方回滚 chroma） |
| Delete(ids) | Bleve 先删（可重建侧）→ chroma 删；Bleve 失败上抛不动 chroma |
| DeleteByDocID(docID) | 扩展方法（非接口面）：Bleve 按 doc_id 字段删 + chroma 按 filter 删——重解析先删后建消费 |
| DeleteTable / TableExists / Close | passthrough + Bleve 索引目录清理/关闭 |

**登记限制**：① Bleve 半边不支持 chroma QueryExpr filter（现状 sparse 调用方传 nil；非 nil 时 Warn 忽略）② chroma 去重语义改由编排层「先删后建」保证（kbadmin 全链唯一调用形态）③ Bleve 异常中断后的索引重建兜底 ⤵️（首版不做，启动检测 chroma 有数据/Bleve 空时从台账重建）④ 分词用 bleve 内置 cjk analyzer（中英混合）。
