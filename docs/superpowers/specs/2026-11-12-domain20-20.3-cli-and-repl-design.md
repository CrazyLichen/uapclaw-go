## 一、定位：这条流程在 agent 会话中的位置与作用

### 1.1 在链路中的位置

20.2 只做「读一份 JSON → 跑一次 Runtime → 吐 JSONL → 退出码」的机器面，**没有任何人类入口**——没有参数解析、没有 CLI 主入口、没有 TTY 交互。20.2 的 `ExecuteSource` 至今在 `cmd/` 里零调用方（`grep` 仅命中 `machine_entry.go` 自身）。

20.3 是**把 20.2 的机器面接上人类入口的三层**：

```
终端用户
  │
  ├─(A) uapclaw-process ... "任务"     ──→ 20.3-①参数层 → 20.3-②单命令生命周期 ─→ 20.2 machine 面
  ├─(B) uapclaw-process ...            ──→ 20.3-①参数层 → 20.3-③交互外壳 → fork 子进程回到 (A)
  ├─(C) --run-json / --run-jsonl        ──→ 20.3-①参数层 ───────────────────────→ 20.2 ExecuteSource
  ├─(D) --query-json                    ──→ 20.3-①参数层 → 【新】query_entry ─────→ 20.2 RunQuery
  └─(E) --list-sessions / --latest-session
                                        ──→ 20.3-①参数层 → 【新】session_entry → fork 出 (D)
                                               ↑ 全程包在【diagnostics】里
```

三层完整展开：

```
┌─ 20.3-① 参数层  main.go(← main.py 478)
│    buildParser()              21 个 flag + 5 个隐藏内部 flag

│    ┌ 分支 A  --run-json / --run-jsonl ──→ 20.2 ExecuteSource()
│    ├ 分支 B  --query-json ────────────→ 20.2 RunQuery()（经 query_entry）
│    ├ 分支 C  --list-sessions / --latest-session ─→ session_entry（不起 Runtime）
│    ├ 分支 D  prompt 非空 ─────────────→ app.Run()   ★单命令

└─────────────────────────────────────────────
   ▼
```

### 1.2 四条作用（按重要性）

**① 给已完成的机器面配上人类入口**

20.2 的 `ExecuteSource` 与 `RunQuery` 至今零生产调用方。20.3 是它们唯一的调用者，也是 20.8 SDK 之外的第二类消费者（人类 vs 程序）。

**② 把「一条命令 = 一个进程 = 一个 Runtime 生命周期」定死**

`app.Run()` 的 `finally` 三段清理（`CleanupSession` → `Close` → `FlushSessionWrites`）保证退出前落盘不丢；`repl` 的「一条指令 fork 一个 worker」保证跨轮次会话靠磁盘与 `worker-result.json` 续，而不是共享内存。

**③ 把交互能力从「过程式 CLI」里剥出来**

人类面（TTY、颜色、宽度、spinner、East-Asian 宽度截断）与机器面（JSONL 独占 stdout）互不污染——这正是 20.2 `protocolStdout()` 的地基价值。`code.normal` 这类展示态文案永远不出现在 JSONL 里。

**④ Read-only 查询与任务执行分离**

`--list-sessions` / `/status` / `/model` / `/permissions` 走**独立子进程 + 独立 Runtime**，不进主会话执行链（`queryRuntime` 每次调用都 fork 一个 `--query-json` 子进程）。这保证「查状态」不会污染正在跑的会话，也不会因为查状态而延长主体生命周期。

### 1.3 与 20.2 的准确分界

| 维度 | 20.2（已完成） | 20.3（本批） |
|---|---|---|
| 入口形态 | 机器 JSON / JSONL（stdin 或文件） | **人类 CLI**（参数 + REPL） |
| stdout 用途 | JSONL 独占 | 人类可读文本（JSONL 仅 `--output jsonl` 时用） |
| 交互能力 | 无（交互即失败） | **完整**（问人、权限确认、实时补充输入） |
| 会话续聊 | 单次（跨进程靠 session_id） | **REPL 内多轮**（fork 子进程 + worker-result 回执） |
| 输出美化 | 无 | **有**（颜色/宽度/spinner/思考分段/工具展示） |
| 共用 | `protocol/`（一份 schema）、`machine*.go`、`client.go` | 同左 + 新增 17 个文件 |

### 1.4 「非交互」不是 20.3 的对立面

20.2 定义的「非交互」= 协议无 TTY 依赖。20.3 的 REPL 才是「给人用的」。两者**共用同一套 `protocol/`**（`schema.json` 里 `run` / `query` / `control` / `event` / `result` 是一份 schema），区别只在渲染层与是否有 worker fork。

### 7.3 关键语义（三条，逐条对齐）

#### `ChineseArgumentParser` 的错误翻译（`main.py:84-151`）

5 条正则，逐条复刻：

| 上游 argparse 消息 | 中文 |
|---|---|
| `argument X: invalid choice: V (choose from C)` | `参数 X 的值无效：V（可选值：...）` |
| `the following arguments are required: A` | `缺少必需参数：A` |
| `unrecognized arguments: A` | `无法识别的参数：A` |
| `argument X: expected one argument` | `参数 X 需要一个值` |
| `argument X: invalid T value: V` | `参数 X 的值无效：V` |

`format_usage` 替换 `usage:` → `用法：`；`format_help` 替换 4 处标签。`error()` 输出 `{prog}: 错误：{翻译消息}\n` 并 `exit(2)`。
