# 10.3.28c / 10.3.28d 缺口补齐 设计

> 上游对齐目标：`jiuwenswarm/runtime/{session_provisioner.py, session_lifecycle.py, session_delete.py, team_session_lifecycle.py, session_input.py}` + `jiuwenswarm/runtime/session/{model.py, execution_registry.py, work_scheduler.py, coordinator.py, session_manager.py}` + `jiuwenswarm/server/runtime/session/{lifecycle.py, session_archive.py}` + `gateway/common/{protocol_ids.py, interrupt_resume.py}`
>
> 状态：2026-11-09 定稿。全部范围与实现形态决策已由用户逐条拍板，见 §3。

## 1. 概述

### 1.1 一句话

10.3.28c/d 已把"删 / 建 / 切 / 分叉"收进两阶段事务和执行账本，但**删除事务的第⑥步 dispose 是空实现**、**团队删除控制面从未装配**、**异步删除与崩溃可恢复整层缺失**；同时 10.3.28d 基于一条错误事实（"上游没有 `session_manager.py`"）删掉了门面层会话队列，**造成真实的调度能力丢失**。本 spec 按上游补齐这三类缺口。

### 1.2 在 agent 会话中的流程位置

```
Gateway ──E2A──► AgentServer.dispatch (handle_message.go)
                    │
                    ├─ chat.send ──► Runtime 主流程
                    │                 │
                    │                 ├─ uses_session_runtime(req)?
                    │                 │    ├─ true  → agent.ExecuteMessage()  → 协调器 RunUnary/RunStream/RunTeamStream
                    │                 │    │                                        ★ 10.3.28d
                    │                 │    └─ false → agent.ProcessMessage()  → SessionManager.SubmitAndWait
                    │                 │                                          ★ 本 spec P1b/P1c 恢复
                    │                 │
                    │                 └─ session_input 判定（本 spec P1a）
                    │                      SessionInputMode = steer / follow_up
                    │                      → 协调器 StreamSessionInput（需要 parent 执行匹配）
                    │
                    └─ session.delete ──► [P2] SessionArchiveService.Session()
                                              ├─ 接受阶段（快）：过安检 → 落 lifecycle 操作记录
                                              │                  → fence_writes → mailbox 屏障
                                              │                  → 返回 {accepted, finalizing, stop_pending}
                                              └─ 后台 finalizer（可重试 5 次）
                                                   └─ runtime.DeleteSession → provisioner 七阶段事务
                                                        ★ 10.3.28c
                                                        ├─② BeginSessionDelete(trajectory)     → 桩 R-8
                                                        ├─③ BeginSessionDelete(lifecycle)      → 桩 R-4
                                                        ├─④ quiesce ──► coordinator.QuiesceSession
                                                        │                + CloseSession(gen, 10s)  ★ 10.3.28d
                                                        ├─⑤ ReleaseResources(participants)
                                                        ├─⑥ dispose ──► 三步编排（本 spec P1c 接真）
                                                        │      ① PromptSuggestionForks.SessionDeleted  → R-1
                                                        │      ② StopSubagentRuntimes                  → R-2
                                                        │      ③ CleanupSessionRuntime                  → R-3
                                                        └─⑦ rmtree → commit 观察者 → commit_session_delete
```

### 1.3 作用（不做的后果）

| 机制 | 解决什么 | 现状 |
|---|---|---|
| dispose 三步 | 删完会话但内存里的建议生成 task / 子代理 / 会话运行时没回收 | **空实现**，只打 Debug 日志 |
| 团队删除控制面 | 团队删除需先 quiesce 整队、再 `DeleteAgentTeam(force)` | `TeamExecutionController` **从未装配**，`handleTeamDelete` 是 stub |

| 异步删除 + 崩溃恢复 | 删除中途失败/进程崩了，要能续做 | **整层缺失**，现在是同步阻塞到 rmtree |

### 3.1 核实记录：两层队列是"互斥"而非"串联"（决定 A 而非 B 的依据）

`jiuwenswarm/runtime/service.py:1873`：

```python
if self.uses_session_runtime(request):
    response = await agent.execute_message(request)   # schedule_session=False
else:
    response = await agent.process_message(request)   # schedule_session=True → submit_and_wait
```

- `uses_session_runtime` = `session_work_kind(request) is not None`；
- `SessionManager` 与协调器**同一请求只会走一条**，不存在重复排队；
- 因此"两套排队器并存"的顾虑不成立 → 选 A（原样恢复）而非 B（只补丢失能力）。
