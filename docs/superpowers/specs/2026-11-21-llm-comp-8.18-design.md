## 1. 流程位置与作用

LLMComp 是工作流中「调用一次 LLM 并格式化输出」的业务节点，8.18-8.26 组件族第一节。调用链：

```
Runner.RunWorkflow → Workflow.executeWithTimeout → Pregel 图调度
  → Vertex(8.11) → 节点函数 → WorkflowComponent 基类(8.17) → LLMComp(8.18)
```

构图期由 `LLMComponent`（ComponentComposable）注册，运行期由 `LLMExecutable`（ComponentExecutable）执行。是 8.23 IntentDetection / 8.24 Questioner / 8.26 React 的同目录邻居与基建提供者（但本节不做它们）。

职责边界（已核实）：
- LLM 调用面只做「构造/取得 Model 实例 + invoke/stream 转手」，SSE 解析、多 provider 分发、首 token/idle 超时全部复用 foundation/llm.Model，本节零 SSE 代码
- 调 Model 时不传 tools——纯单轮文本进出，无工具调用（工具调用属 8.26 ReactComponent 内部 ReActAgent 链路，互不调用）
- `extractContent` 只取 `.content`，reasoning/usage 字段逐字对齐即丢弃（下游消费方在回调链/context engine，不属组件职责）

## 4. 构造期校验链（LLMExecutable 构造，顺序一比一）

`validateConfig(config)`：
1. `validateTemplate`（llm_comp.py:443-472）：system_prompt_template/user_prompt_template 任一非 nil 或 template_content 空则短路返回；否则逐元素——role=system 元素做 SystemMessage 等价必填校验（101000，"system message is invalid"）；遍历中出现 user 后再出现 system → 101000 "system message must be before user message"（校验与抛错同元素，Pydantic 先 validate 再 raise 的顺序保留）；无 user → 101000 "user message is required"
2. `validateResponseFormat`（:507-522）：type 字段正则校验（101001，报错含 response_format 原文，敏感模式等价脱敏语义随 §7 UserConfig）；type ∈ {text,markdown} 且 output_config 长度 ≠1 → 101001 "output config must contain exactly one parameter..."
3. `validateOutputConfig`（:475-504）：空 → 101002 "output config is empty"；type=="object" 字符串直通；否则逐字段——空参数名 → 101002；value 做 OutputParamConfig 等价校验（type 默认 ""、description 默认 ""、required 默认 false），失败 → 101002（敏感模式 "output config parameter's config value is invalid" vs 原文）

pydantic 校验 → Go 等价检查（必填字段存在性与类型断言），错误文案逐字保留。

## 5. invoke / stream 链路

### 5.1 invoke（llm_comp.py:524-572，十步一比一）

1. setSession/setContext
2. `prepareModelInputs` → `initializeIfNeeded` 懒初始化：`createLLMInstance`——model_id 为 nil 且 client/request config 任一 nil → 101003 "failed to create llm instance"；否则 `foundation/llm.NewModel`；model_id 非空 → `Runner.GetModel(id)`（初始化失败包装 101005 "failed to initialize llm if needed"）
3. `getModelInput`：`buildSystemPrompt`（模板优先：system/user 模板任一非 nil 时 system 缺省返回空；否则 template_content 头部连续 system 元素，**遇非 system 即 break**）→ `buildUserPromptContent`（模板优先：user 模板 nil → `[UserMessage(content="")]`；否则 PromptTemplate.Format(inputs).ToMessages()；template_content 取首个 user 元素）→ `insertHistoryToSystemAndUserPrompt`（enable_history 且 context 非 nil 时 context.GetMessages 拼在 system_prompt 后、user_prompt 前）→ `LLMPromptFormatter.formatPrompt`
4. WORKFLOW_COMPONENT_START 日志（component_id/component_type_str="LLMComponent"/session_id/metadata: model_name、has_inputs、sensitive_mode）
5. 写最后一条 user 消息进 context（`writeUserMessageToContext`：enable_history 且 context 非 nil，倒序找首个 role=user 且 content 非空）
6. `model.Invoke(messages)` → 取 content；异常 → 101003（敏感模式 "invoke llm failed" vs str(e)，`.Err` 记原始错误）
7. WORKFLOW_COMPONENT_END 日志（has_response、response_length）
8. `writeAssistantMessageToContext`
9. `createOutput` → OutputFormatter.formatResponse；捕获 101007 → 转 101004 重抛（error_msg 用 e.message），其他错误原样上抛
10. 返回 map[string]any

### 5.2 stream（llm_comp.py:574-752）

入口：setSession/setContext → cache_stream 时 state.Clear() → response_format type 分派：
- **json** → `invokeForJSONFormat`：prepareModelInputs → START 日志（response_format:"json"）→ 写 user 消息 → **整体 Invoke** → content → cache_stream 时 AccumulateContent → 写 assistant 消息 → createOutput → **一次性 yield 单帧**
- **其他** → `streamWithChunks`：prepareModelInputs → 写 user 消息 → 遍历 model.Stream 逐 chunk：extractContent → 空内容跳过 → cache_stream AccumulateContent + 局部累积 → **每 chunk 单独 OutputFormatter.formatResponse 后 yield**（Python 即逐帧过格式化器；json 分支不走此路，故 text/markdown 单字段包装天然可逐帧）→ 成功收尾写 assistant 消息
- 异常分支：cache_stream 时 state.Clear() 后重抛；外层统一包装 101003（敏感 "failed to stream" vs str(e)）
- `getStreamOutput`：cache_stream 且 session 非空时 BuildFinalResult（空结果返 nil）——供 8.14b 流式槽消费，契约复用既有 StreamReader/四槽形态，不新增通道形态

- D-18-1（✅ 兑现后 2026-11-21 审查二次收口）：初版在 llm_comp.go 包内落私有等价面，实施后审查发现仓库已存在完整共享实现 foundation/tool/schema_utils.go（显式对齐 Python SchemaUtils，含真 jsonschema 库），且 workflow.go 的 validateInputSchema 为降级版（仅顶层 required）——三处漂移违反共享单点。二次收口：①schema_utils.go(+test) 迁至 core/common/utils/schemautils（对齐 Python 老家目录 common/utils/）+ 补 ValidateWithSchemaMap（Python validate_with_schema dict 独立分支；pydantic 动态模型回退 Go 无对应物，jsonschema 全量校验承载，回收条件=Go 动态模型机制落地）②llm_comp.go 删私有 validateWithSchema/formatWithSchema 改调共享，校验错误按 Python 异常分类直传 SCHEMA_VALIDATE_INVALID/SCHEMA_FORMAT_INVALID（llm_comp.py:247-248 except BaseError: raise；初版吞成 101007 属偏差修正）③workflow.go 删降级版 validateInputSchema 改调共享 FormatWithSchemaMap（skip_inputs_validate 透传，校验行为向 Python 对齐变严）④额外字段语义收紧（2026-11-21 用户拍板「保持和 Python 一致」）：FormatWithSchemaMap 补齐 additionalProperties 三态——缺省 False→forbid 拒绝未声明额外字段（报 SCHEMA_FORMAT_INVALID）/显式 True→保留/非 bool 其他值→ignore 放行；空 schema + 非空数据同样拒绝（Python 动态模型同行为）；workflow skip_inputs_validate 语义同步澄清——skip 只跳过 jsonschema 约束级校验段，结构校验（required/额外字段）仍执行（Python model_validate 不受 skip_validate 影响）
- D-18-2（✅ 兑现）：UserConfig 单例锁语义（threading.Lock 双检）→ Go sync.Once + mutex 承载（user_config.go；含 IS_SENSITIVE env 短路一比一）；INI settings 对齐 configparser（实施修正：Python 读 INI 非 JSON，计划草稿误写 JSON 已纠正）

- D-18-4（✅ 兑现）：Python `LLMComponent.executable` property 懒初始化缓存 → Go `ToExecutableFn` 槽首调构造缓存（toExecutableCached）

- D-18-6（✅ 实施新增）：`_extractConfiguredFields` 缺失字段报错序 → required 排序保确定性（Go map 遍历无序，Python dict 插入序；报错文案字段列表排序）
- D-18-7（✅ 实施新增，**对齐断裂修复**）：ModelContext 全链透传断裂——Python `vertex.init(node_session, context=context)` 的 context 为 ModelContext，Go 侧三处丢失：①Vertex.ctx 误作 context.Context 断言（vertex.go:52→改为 modelContext any 原样持有）②BaseWorkflow.Compile 收 context 却传 nil（_workflow.py:312→kwargs["context"] 下发）③ExecuteSingleComponent vertex.Init 传 nil（_workflow.py:86→下发）；补 Workflow.streamInternal 漏掉的 context 形参（workflow.py:501 _stream(inputs, session, context)）。后果：enable_history 写回 context 恒 nil，此前所有组件 context 依赖静默失效，LLMComp 集成测试暴露

- json.dumps(ensure_ascii=False) → Go Encoder SetEscapeHTML(false)（8.9a D-9 同款先例）

- isIntegerFloat（json float64 整值判定）：**编码适配非 Python 语义助手，不迁 pythonsem**——pythonsem.IsInt 复刻 isinstance(x,int)（拒 float），而 Go json.Unmarshal 全部数字落 float64（Python json.loads("1") 得 int），直接换会把合法整数判假。与既有用户拍板先例同款：recommendation/topic_audit.go D-6「Go JSON 解码无 int/float 之分：整值 float 接受」。替代方案 json.Decoder.UseNumber() 会把数字改型 json.Number（string 底型），全仓 float64 断言面碎掉，否决。
