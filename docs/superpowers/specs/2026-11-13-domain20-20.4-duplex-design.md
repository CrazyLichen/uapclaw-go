## 一、流程位置与作用

process-cli 是「宿主（IDE/网关/脚本/用户终端）拉起的一次性子进程」，stdin/stdout 是两条方向相反的管道：

- stdout（出）：AI 的全部事件流与终态结果（OneShotWriter，20.2 已落）。
- stdin（入）：20.2 只用一次（递 run 记录）；20.4 起变成**常开控制通道**，接收三类控制帧：
  1. `answer` —— 回答 Runtime 挂起的交互卡（chat.ask_user_question / plan.approval_required / harness.activate_interaction）
  2. `cancel` —— 取消整个 run（退出码 130，状态 CANCELLED）
  3. `tool_result` —— 宿主工具回调结果（call_id + result/error 二选一）

在 agent 会话链路中，20.4 是 process-cli 从「一次性投喂」升级为「会话式通道」的部分；是 20.5（sessionLease）与 20.6（host_tools）的直接前置。Runtime 侧依赖（`StreamInteractionAnswer`、`InteractionAnswerInput`、`runtime.Control`）均已在 Go 侧存在（`internal/swarm/runtime/service.go:1159`、`interaction.go`、`events.go:55`、`processcli/client.go:285`）。

## 三、组件设计

### 3.1 duplex_protocol.go（对齐 duplex_protocol.py，一文件对一文件）

- `DuplexControl`：单一类型承载三类控制帧。字段 `Kind` / `RequestID` / `SessionID` / `InteractionID` / `Answers`（[]map[string]any）/ `CallID` / `Result` / `Error`。Python `__post_init__` 的按 kind 交叉校验落在构造函数 `NewDuplexControl`：
  - answer：session_id、interaction_id 必填非空，answers 非空数组
  - tool_result：session_id、call_id 必填；interaction_id/answers 必须为零值；error 与 result 恰好其一
  - cancel：interaction_id/answers/call_id/error 全零值；session_id 可空或非空
- `DuplexProtocolError`：`Code = "INVALID_CONTROL"`，带 `RequestID`（从损坏帧捞出的关联号）与 `Details`（复用 `protocol/schema` 的 `input_error_details` 等价物）。Go 用普通 error 结构体（同 `MachineInputError` 模式）。
- 字段白名单常量：`_CANCEL_FIELDS` / `_ANSWER_FIELDS` / `_TOOL_RESULT_FIELDS` / `_COMMON_REQUIRED` → Go 不可变集合（切片或 map 常量组）。
- `DecodeControl(line []byte)`：UTF-8 校验 → 复用 20.2 的 `DecodeMachineDocument`（错误消息 "run input" 替换为 "control input"，仅首次）→ `_validate_fields` 白名单/必填/schema_version → `NewDuplexControl`。
- 深拷贝防御（Python `_copy_json` / `_copy_answers` / `_validate_answer_fields`）：递归校验+拷贝，拒绝非 JSON 值、非有限 float、对象键非字符串；`question`/`custom_input` 必须字符串、`card_id` 非空、`selected_options` 必须字符串数组。Go 递归函数一比一对应；RecursionError → "answers nesting is invalid"（Go 用深度计数上限等价实现，登记偏差）。
- `ToDict()`：返回版本化新数据（schema_version/type/request_id/session_id + kind 专属字段），fresh copy。

### 3.2 duplex_input.go（对齐 duplex_input.py，一文件对一文件）

- 常量：`MaxDuplexLineBytes = 1024*1024`、`readChunkBytes = 64*1024`、Windows EOF 错误码 `(109, 232, 233)`。
- `DuplexInputError`：`Code = "INVALID_INPUT"`，安全诊断不回显内容与路径。
- 非阻塞读源接口 `duplexSource { readAvailable(size int) ([]byte, error) }`，三实现：
  - `memorySource`：测试桩（对齐 `_MemorySource`，单次读不超过 `size`，临时编码 buffer 有界）
  - `descriptorSource`：POSIX 共享实现——常规文件（`stat.S_ISREG` 等价判定）直接读；否则零超时 `select`/poll 探测，无可读返回 nil
  - `windowsPipeSource`（`duplex_input_windows.go`，build tag windows）：`PeekNamedPipe`，EOF 错误码返回空切片，其余报 OSError 等价
- `DuplexLineReader`：
  - `NewDuplexLineReader(stream, maxLineBytes, pollInterval)`：参数校验（整数/正数/有限正数，bool 排除）；默认 stream = os.Stdin
  - `ReadLine() ([]byte, error)`：返回去 LF/CRLF 的 UTF-8 行；None（Go 用 nil + EOF 语义）表示干净 EOF/Close；空行原样返回 `[]byte{}`；EOF 带未终结行报错；单行上限 1MB（CRLF 计入的 `max+1` 特判一比一）；行内非 UTF-8 报错；同时只允许一个活跃读；每次迭代让出调度（Python `asyncio.sleep(0)` → Go `runtime.Gosched()` 等价）
  - `ReadDocument() ([]byte, error)`：`--run-json -` 用，不要求结尾换行、内嵌换行计入 `MAX_RUN_INPUT_BYTES` 上限；与 ReadLine 不可混用；Close 提前关闭报 "run input closed before EOF"
  - `Close()`：唤醒 pending 读、丢弃 buffer，**不关借来的流/fd**
  - `Closed()` / `BufferedBytes()` 访问器
- Python `asyncio.Event` 唤醒 → Go 用 channel 广播或 sync.Cond（实施计划定案，登记平台偏差）。

### 3.3 duplex_control.go（对齐 duplex_control.py，一文件对一文件）

并发模型：Python 协程（owner + stdin 任务 + N 条流泵）→ Go goroutine。

- 常量：`_INTERACTIONS` / `_ACK_EVENTS` 事件集合、`_MAX_PENDING = 16`。
- `DuplexController` 状态：
  - `reader *DuplexLineReader`、`writer *OneShotWriter`、`unattended bool`
  - `failure *protocol.RuntimeErrorInfo`、`failureStatus`、`failureExitCode`（默认 FAILED/2；cancelled → CANCELLED/130）
  - `pending map[string]map[string]any`（deepcopy 的 payload；上限 16）
  - `pendingTools map[string]chan toolResult`（Python Future → 缓冲 1 channel，非阻塞哨兵投递）
  - `streams map[string]*streamPump` + 输出队列（`asyncio.Queue(maxsize=32)` → 缓冲 32 channel）
  - stopping_input / stopping_streams / input_closed 标志
- `Start()`：登记 owner，reader 非 nil 时启动 stdin 读取 goroutine
- `readControls()`（对齐 `_read_controls`）：循环 ReadLine → DecodeControl → request_id/session_id 匹配校验（不匹配终止 run）→ cancel 终止（CANCELLED/130）；tool_result 唤醒 pendingTool（缺失报 HOST_TOOL_NOT_PENDING）；answer：pending 取 payload（缺失报 INTERACTION_NOT_PENDING）→ `answerInput()` 构造 `InteractionAnswerInput`（payload 的 request_id/interaction_id/source/interrupt_id/approval_schema/evolution_meta + 原 request params 的 mode/work_mode/project_dir/cwd/trusted_dirs/run_permissions，Python :171-196 一比一）→ 新开 answer 流入 streams。stdin EOF 且有 pending/pendingTools → INPUT_CLOSED 终止。任何错误 → terminate(INVALID_CONTROL + details)
- `Consume(stream, client, request, observe) bool`（对齐 Python :315-381）：主循环从队列取事件：错误事件 → observe 后返回 false；交互事件 → `registerInteraction`（harness.activate_interaction 或 locator 缺失 → INTERACTION_UNSUPPORTED；超 16 → "Too many pending interactions."）→ unattended 分支：`permissionRejection`（仅权限卡 source=="permission_interrupt"，逐 question 校验存在 value=="reject" 选项，自动选 reject 并开 answer 流 + `interaction.auto_denied` 通知；非权限卡 INTERACTION_REQUIRED、无 reject 选项 INTERACTION_UNSUPPORTED）；attended 分支：发 `interaction.requested` 通知 + checkAnswerAvailable。普通事件：observe + 完成判定（`chat.final` 且无 pending / 根流 is_complete 且无交互历史 / `runtime_completion=="completed"` 且无 pending；`suspended` 不算完成；ACK 事件不参与判定）。队列空且流尽 → 返回 completed
- `CallHostTool(name, arguments) (any, string)`（对齐 `call_host_tool`）：reader 为 nil/已关/停收 → 返回错误 "Host tool callback is unavailable."；超 16 → "Too many pending host tool calls."；生成 call_id → 发 `host_tool.requested` 通知（arguments deepcopy）→ 等 tool_result 回填
- 终态：`Terminate`（幂等，只生效一次）、`StopInput`（停收 + **排空输出队列防生产者阻塞** + reader.Close + 取消全部 pendingTools + 取消 stdin goroutine）、`CloseStreams`（取消全部泵并等待，异常上抛）
- `notice`：`runtime.Control` 事件（channel_id="process_cli"）经 OneShotWriter 写 stdout
- 流泵 `pump`：把事件投队列；异常包进终项；Python finally aclose → Go 关流等价；stop 排空后异常仅上抛不入队
