## 1. 流程位置与作用

TeamScheduler 是 **leader 侧任务板驱动决策引擎**（F_62）：

- 只有 `dispatch_mode == "scheduled"` 且 host role 为 leader 的 kernel 才构造（Python `kernel.py` L91-97）；成员与 autonomous 模式的 scheduler 为 `None`。
- 唤醒链：事件总线（`asyncio.Queue` 单消费者串行 drain）→ `_build_wake_callback` 组合 = 协调层 dispatcher 先、`scheduler.on_event` 后（kernel.py:298）。`SCHEDULER_SCAN` 是 leader 本地改板时的自发布 echo。
- `on_event` 过滤表（scheduler.py:196）：`task_*`/`member_*` → 扫描；`POLL_TASK`/`SCHEDULER_SCAN` → 扫描；`TASK_COMPLETED`/`TASK_VERIFIED` → digest（+扫描）；`TASK_LIST_DRAINED` → 一次性 all-done（可 re-arm）；其余忽略。
- `_scan()` 五遍幂等扫描（最多 `_MAX_SCAN_PASSES` 轮到不动点）：`_reconcile_starts` / `_reconcile_handoffs` / `_reconcile_reviews` / `_reconcile_retirements` / `_reconcile_revisions`。
- 硬约束：scheduler 从不直接向成员轮注入输入——成员交接全走 leader 身份信箱行（`message_manager.send_message` + `meta=meta_task_start`，`content` 为空、收件方按当时任务行现场渲染，F_63）；只有 leader 自己接收直接注入（digest / escalation）。
- 崩溃恢复 = 同一扫描 + CAS 幂等（重放 no-op）。

概念事实（实施时不得偏离，均已在 brainstorming 中对源码核实）：

1. **start_task CAS**：`UPDATE ... WHERE status='pending'` 单语句语义，防"扫描 vs 工具写"竞争（事件总线本身串行，CAS 防的是不走总线并发写板的调用方：成员 claim/update_task、外部写库）。
2. **handoff scan 补的缺口**：`update_task` 改派不改状态（IN_PROGRESS 保持），start scan 永不触发、新 owner 从未收到 start 消息 → 对活跃任务检查"当前 owner 信箱无 start handoff"则补发。原 owner 不停轮：reassign 只发 `TASK_REVOKED`（steer 掉该任务上下文）+ `TASK_CLAIMED`（新 owner），其 in-flight 轮与其他 claim 完好（task_manager.py:1858）。
3. **review 轮来源**：仅 scheduled + `enable_task_verification` + 任务进入 IN_REVIEW。`task.reviewer` JSON 列 → reviewer 名单（verifier/challenger 二元池 + inspector 打分池）；每 reviewer 一个一次性临时 harness（build → run_once → dispose），带 `verify_task`+`view_task`；票写 db tally，`settle_review_tally` 纯函数裁决（verdict.py：一票否决 + inspector 平均 ≥0.85）；pass → `settle_review("pass")` + leader digest（**作者不被唤醒**，F_119，作者侧由 task-outcome rail 在下次输入折叠告知——Go 已有 `TaskOutcomeTracker`（tracker/team_context.go:1024）+ `rails/team_policy_rail.go:327` 折叠逻辑，25.2b 只需在结算点调 `Announce`）；fail → `meta_rework`+feedback 返工；轮次超限/停滞 → 升级 leader。
4. **任务拆分/顺序/防环**：leader 与成员都用 `create_task`（带 `parent_task_id`/`depends_on`/inline member F_118）；成员拆子任务走 `add_graph(suspend_parent=…)`，父任务同事务 BLOCKED（F_128）；顺序由状态机条件（依赖未清 → 不到 PENDING）保证，scheduler 只按"最早 PENDING"派发；防环在 DAO 层 `mutate_dependency_graph` 每次插边前 `detect_cycle_in_adjacency`（有环整个事务拒绝并报路径）。任务正文大时溢出落盘（`#file#` 占位）。
5. **deliverable 无自动追踪**：作者经 `member_complete_task(summary, note)` 自报（note 预期写 artifact 路径与关键决策）；评审请求模板全文渲染 summary+note；reviewer 深挖走 `view_task`（get：全量行+revision/change_notes+subtasks+upstream/downstream F_120；note：任意任务未截断 note；list/claimable/in_review：板面全局）。
6. **`_with_content` 两段式**：板面扫描 `list_tasks(with_content=False)` 轻量行；只有渲染评审请求/返工反馈两处才 `get(task_id)` 重读单条带正文。

## 3. 关键映射决策（实施前 spec 定稿逐条确认）

1. **依赖注入**：scheduler 是"使用协作方能力"方向（规则 10.2 允许窄接口）。Python 的 Protocol 参数（`AgentRoundController` 等）→ Go 窄接口，只覆盖 scheduler 实际调用面；TaskManager 扩展方法（CAS/settle_review/tally/unseen_revisions 等）直接挂 `TeamTaskManager`/`TeamBackend` 原类型，不另立接口债。
2. **临时 reviewer harness**：`_spawn_temp_reviewer` 走 25.1a `TeamHarness.build + run_once + dispose`；`asyncio.create_task` → goroutine，登记偏差：挂 scheduler stop 组，deactivate 时 cancel（回收条件=无）。
3. **on_event swallow**：Python `except Exception: logger.error` → Go recover + `logger.Error`（logComponent 规则 3），扫描失败不杀总线循环。
4. **CAS**：单条件 UPDATE 语义落 database 层，对齐 `complete_task`/`reassign_task` 既有先例，不引入新抽象。
5. **事件总线**：Go 侧已有 `coordination/event_bus.go` 串行 drain，保持；scheduler wake 组合函数对齐 `_dispatch_then_schedule`。
6. **review_feedback_evolution 承接面**：随 25.2b 全落（用户方案 B）；spec 阶段先核 Go 技能演进 rail 是否具备 `handle_review_feedback` 挂点，缺口登记到本节并按规则 13 提出。

## 7. 测试（用户要求：本设计讨论过的每个机制都要有用例）

### 7.1 单测

- `verdict`：bin/score 池矩阵 × UNDECIDED/PASS/FAIL、inspector 阈值 0.85 边界、两池并存。
- `render`：meta_* 模板名、escalation×4 文案、`_submission_body` 缺省段省略、review_request 占位符替换（含 per-reviewer instruction、previous_vote 段）。
- `scheduler`：on_event 过滤表逐项；五扫描逐遍状态机（CAS 竞争仅一胜者、幂等重放 no-op、`_MAX_SCAN_PASSES` 收敛、`_revision_pushed`/`_review_dispatched`/`_digested_tasks` 去重账本、all-done re-arm、retirement 三条件）；`_send_as_leader` 信箱行落库 + 惰性拉起 best-effort；`_with_content` 回退。
- `reviewer_spec`：从 teammate spec 收窄。
- `review_feedback_evolution`：反馈→演进 rail 的分发与格式。
- 防环：`mutate_dependency_graph` 插边环拒绝（报错含路径）、suspend_parent 同事务 BLOCKED。

### 7.2 集成（tests/integration/agentteams/，真实跨子系统）

用户明确要求：**必须真实覆盖 leader↔成员任务交接与任务状态转换**：

- I-1 全链派发：MockLLM scheduled 团队，leader create_task（带依赖）→ scheduler 派发 → 成员信箱收到 meta_task_start → 惰性拉起 → 成员认领并完成（PENDING→IN_PROGRESS→REVIEW/COMPLETED 状态迁移断言读 db）。
- I-2 依赖顺序：T2 depends_on T1，断言 T2 在 T1 完成前不可派发；防环用例：建环被拒且任务行未落。
- I-3 改派 handoff：reassign 后原 owner 收 TASK_REVOKED 且轮不停、新 owner 由 handoff scan 补发 start（缺口闭合）。
- I-4 review 链：作者完成 → IN_REVIEW → 临时 reviewer 投票（pass：作者不被唤醒、leader 收 digest、作者下次输入 task-outcome 折叠；fail：meta_rework 返工 → 轮次超限升级 leader）。
- I-5 幂等恢复：杀掉扫描后重放事件，板面无重复派发（CAS + 去重账本）。
- I-6 idle 链：板清 → debounce → `emit_team_idle`；新任务 → re-arm；pause 后 `refresh_idle_baseline` 不误报停滞。
- I-7 retirement：inline member（F_118）板清后走 shutdown 请求。
