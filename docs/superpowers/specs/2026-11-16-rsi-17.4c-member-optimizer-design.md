c1 的两个归因 agent、c2 的 planner/executor agent、c3 的 repair agent 全部复用 17.4b2 已打通的 DeepAgent 装配双轨（`BuildAgent` Rails / 换会话重试）与 `invoke_member_optimizer_agent_structured` 等价物；`members/operators` 输出解析（yaml-or-json / json-object / 提取文本）在 agents/output.go 对齐。

### 2.4 Python AST 技能安全扫描（c3 落地）

- **选型：gopapy v2**（`github.com/tamnd/gopapy/v2`，MIT、纯 Go、零依赖）——AST 节点按 CPython `Parser/Python.asdl` 生成，节点名/字段与 Python `ast` 一一对应，扫描逻辑可逐行对照 `_scan_python_skill_script`（Import/ImportFrom 根模块、Call 限定名、Attribute 链）。
- 否决：grove（early development）、tree-sitter 纯 Go 移植（节点形状需自写映射层）、正则简化扫描（嵌套写法漏报、保真度下降）。
- gopapy 若在实际使用中出现偏差（如某语法解析失败），按「已知偏差」段登记处理方式。

### 2.5 并发语义

Python 的 asyncio 并发点（逐 issue/逐角色 await、波内并行执行）在 Go 侧一比一：串行 await 保持顺序调用；真正的并发点（executor 波内 execute_role_group、verify_role 并发）用 errgroup 对齐，并发度与 Python 语义一致。任何调换须在 spec 偏差段登记。

### 2.6 波次调度与重启语义（架构问答结论，写入设计说明）

- 波次 = 纯内存拓扑排序（`depends_on` 由 LLM 在手术单声明；LLM 声明的 `action_waves` 与依赖重算不一致时以依赖为准）；收不出波 = 存在环，报错拒绝。
- 子波 = 角色内部按「声明写路径是否重叠」分组，防并行写冲突。
- 手术区 = 每动作独立 worktree 目录（`wt/{role_hash}/a/{n}/{action_hash}/`），子波结束合并进整合区 `wt/{role_hash}/i/`；`current_harnesses` / `current_harness_refs.yaml` / `.publish_tmp` 为禁写路径。
- 重启不恢复调度现场：靠「整轮重入 `optimize()` + `_find_reusable_pending_optimization` 目录复用」兜底，Go 一比一。

### 2.7 单/团队模式边界（架构问答结论）

- harness_refs.yaml 是中性角色档案清单，不携带模式；模式由评估器 `backend` 配置决定（单 agent 模式硬校验恰好一个 ref）。
- 轨迹采集与逐成员用量统计属于 17.6 evaluator 系列；17.4c 只消费 eval_ref.yaml / analysis_ref.yaml / harness_refs.yaml 三个文件契约。
- 「证据不足 → team_skill 改道」当前仅为选择报告记账元数据（`deferred_contract_route`），全仓无其他消费方，Go 照抄记账。

### 3.2 六步流水线的前三步算法要点（逐行对照清单）

1. **role_attributor.py（674 行）**：LLM-as-Judge 定责。证据包有界（BoundedEvidenceBundle）；输出校验（issue_id/decision/role∈候选/confidence∈[0,1]，错误进重试，默认 limit=2）；单角色别名表（solver/agent/assistant/default/single_agent/single_harness/worker）直接对号，不调 LLM；`_match_target_member` 把 analyzer 的 target_members 解析到唯一候选角色（含 aliases 与 member_id 匹配）。
2. **mechanism_attributor.py（523 行）**：只处理已定责问题；封闭分类法三枚举校验；联锁约束（`optimization_surface=none` 仅允许 `insufficient_role_evidence`）；factory.py:209-210 将枚举值注入提示词模板变量。
3. **member_selector.py（330 行）**：零 LLM。评分 `severity_weight和×10 + 平均confidence×5 + min(issue数,5)/5`；权重 critical=4/high=3/medium=2/low=1（未知=1）；排序 `score↓ → max_severity↓ → role↑` 稳定；取前 `max_roles_per_run`（默认 2）；落选者逐 issue 记入 `unselected_attributions`；证据不足问题剔除并记账（`filtered_insufficient_count` / `deferred_contract_issue_ids` / `deferred_contract_route="team_skill"`）。
4. **hypothesis.py（352 行）**：诊断结论 → 不可变、绑定案例的假设契约（version=4）；`require_usable`；单 harness 模式强校验每个 issue 都有契约。
5. **loader.py 补齐**：`resolve_candidate_roles`（直接路径 → eval_ref 回退 → team_skill 补充三级解析）、`_parse_harness_refs_file/_dir`（目录名即角色名）、`_validate_candidate_harness_refs`。
6. **agents/（factory 533 / output 219 / profiles 100）**：`load_member_optimizer_model`、factory.py 全文件一次对齐（含四类 agent 工厂：role_attribution / mechanism_attribution / action_planning / action_execution / verification_repair——文件归属 c1，planner/executor/repair 工厂依赖的执行细节随 c2/c3 消费方落地）、结构化输出解析与修复重试。
7. **lever.py（164 行）**：四种杠杆（instruction/action/control/configuration/unresolved）按 action_group 与 target 查表归类；`build_action_lever_decision` / `build_hypothesis_lever_policy` 供 c2 消费，本节一并落地（Python 同文件）。

### 3.3 数据流

```
17.4b 病历(analysis_ref.yaml) + 评估索引(eval_ref.yaml) + 角色档案(harness_refs.yaml)
```
