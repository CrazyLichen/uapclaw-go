## 二、逐项修复设计

### 问题 1：9.77 Trajectory 补齐全部缺失模块

**现状**：Go 只有 4 个文件（doc.go/types.go/json_safe.go/extractor.go仅接口），Python 有 7 个完整文件。缺失 5 个模块。

**修复方案**：补齐全部 5 个缺失模块，对齐 Python 全部 7 个文件。

#### 2.1.1 builder.go — TrajectoryBuilder

**对齐文件**：`openjiuwen/agent_evolving/trajectory/builder.py`（118行）

**核心逻辑**：
- `TrajectoryBuilder` 结构体：session_id/source/case_id/member_id/meta/max_steps/cost/steps
- `RecordStep(step)`：追加步骤 + max_steps 滑窗截断 + LLM 步骤 cost 累积（input_tokens/output_tokens）
- `Build()` → Trajectory：组装最终轨迹，cost 为零时设为 nil，生成 UUID execution_id

**Go 适配**：
- `NewTrajectoryBuilder(sessionID, source, ...)` 构造函数，用 functional option 处理可选参数
- `max_steps < 1` 校验：返回 error（Python 用 ValueError）
- `cost` 用 `map[string]int64`（Python 用 `Dict[str, int]`）
- `_generate_uuid` → `uuid.New().String()`（去掉 `-`，对齐 Python `uuid.uuid4().hex`）

#### 2.1.2 extractor.go — TracerTrajectoryExtractor 完整实现

**对齐文件**：`openjiuwen/agent_evolving/trajectory/extractor.py`（271行）

**当前状态**：extractor.go 只有 4 行接口定义，无具体实现。

**核心逻辑**：
- `TracerTrajectoryExtractor` 结构体：持有 `resourceManager`（用于查询 Tool 元数据）
- `Extract(session, caseID)` → Trajectory：从 Session.tracer() 获取 spans → 逐个 buildStep → TrajectoryBuilder 组装
- `_build_step(span)` → TrajectoryStep：classify_kind + build_detail + build_meta
- `_build_llm_detail(span)` → LLMCallDetail：从 on_invoke_data 提取 llm_params，解析 response/usage
- `_build_tool_detail(span)` → ToolCallDetail：从 resourceManager 获取 tool_description/tool_schema
- `_build_meta(span, baseMeta, kind, detail)` → meta：operator_id + agent_id + backup I/O + span_name/invoke_id/parent_invoke_id/child_invokes
- `_classify_kind(span)` → StepKind：plugin→tool, llm/workflow/memory→各自, 默认→agent
- `_get_operator_id(span, meta)` → operator_id：优先级链 operator_id > llm_call_id > meta.operator_id > name
- `_extract_inputs/_extract_outputs`：解包嵌套的 inputs/outputs 字典

**Go 适配**：
- `session` 参数类型：当前 TrajectoryExtractor 接口定义为 `*session.Session`，保持不变。Tracer 通过 `sess.Tracer()` 获取
- `span` 的 `Any` 类型：Python 用 getattr 动态访问，Go 需要定义 `Span` 接口或用 `map[string]any` + helper 函数
- `resourceManager`：用 `operator.ResourceManager` 接口（如果已定义），否则用 `any` + 类型断言
- `LLMCallDetail.response` 中的 `prompt_token_ids/completion_token_ids/logprobs` 提取：Python 用 `pop` 从 response 中移除，Go 需要手动从 map 中删除 key

#### 2.1.3 registry.go — TrajectorySink/Source + InMemoryTrajectoryRegistry

**对齐文件**：`openjiuwen/agent_evolving/trajectory/registry.py`（153行）

**核心逻辑**：
- `TrajectorySink` 接口：`PublishMemberTrajectory(snapshot)`
- `TrajectorySource` 接口：`GetTrajectory(teamID, sessionID, filterCollaborative) → *Trajectory`
- `MemberTrajectorySnapshot` 结构体：team_id/session_id/member_id/member_role/trajectory/recorded_at_ms + Make 工厂方法
- `InMemoryTrajectoryRegistry`：实现 Sink + Source，内部用 `map[[2]string]map[string]snapshotEntry` + sequence 排序 + `sync.RWMutex`
- `_should_keep_current`：recorded_at_ms 降序 + sequence 降序
- `now_ms()`：`time.Now().UnixMilli()`

**Go 适配**：
- `TrajectorySink`/`TrajectorySource` 定义为 Go 接口
- `MemberTrajectorySnapshot` 值类型（不可变）
- `InMemoryTrajectoryRegistry` 同时实现 Sink + Source
- `clear_session` 方法导出为 `ClearSession`

#### 2.1.4 aggregator.go — TeamTrajectoryAggregator

**对齐文件**：`openjiuwen/agent_evolving/trajectory/aggregator.py`（299行）

**核心逻辑**：
- `TeamTrajectory` 结构体：team_id/session_id/combined/members
- `TeamTrajectoryAggregator`：构造接受 TrajectoryStore 或 trajectories_dir，aggregate 方法
- `AggregateMemberTrajectories()`：独立函数，从成员轨迹列表构建合并轨迹
- `FilterMemberTrajectory()`：过滤协作相关步骤（跨成员 meta key + 协作工具名 + 团队技能文件访问）
- `CollaborativeTools` 常量：`view_task/claim_task/send_message/workspace_meta`
- `_is_collaborative_step` / `_is_team_skill_file_access` / `_is_leader_trajectory`
- `_build_combined_trajectory`：所有成员步骤按 start_time_ms 排序合并
- `_merge_member_trajectory`：同一成员多次快照的合并策略（前缀检测 + 追加）

**Go 适配**：
- `AggregateMemberTrajectories` 作为包级导出函数
- `FilterMemberTrajectory` 作为包级导出函数
- `CollaborativeTools` 作为包级 `map[string]bool`（替代 Python frozenset）
- `CrossMemberMetaKeys` 已在 types.go 中定义，aggregator 直接引用
- `TeamTrajectoryAggregator` 的 `trajectories_dir` 参数：Go 用 `string` 替代 `Path`

#### 2.1.5 store.go — TrajectoryStore + InMemoryTrajectoryStore + FileTrajectoryStore

**对齐文件**：`openjiuwen/agent_evolving/trajectory/store.py`（265行）

**核心逻辑**：
- `TrajectoryStore` 接口：`Save(trajectory, version)` / `Load(executionID, version)` / `Query(version, filters...)`
- `InMemoryTrajectoryStore`：`map[string]map[string]*Trajectory`，按 version 隔离，Query 用 reflect 过滤
- `FileTrajectoryStore`：JSONL 文件存储，按 version 分文件，`_trajectory_to_dict` / `_dict_to_trajectory` 互转

**Go 适配**：
- `TrajectoryStore` 接口：`Save` / `Load` / `Query`
- `InMemoryTrajectoryStore`：Query 用字段匹配函数（Go 不需要 reflect，用闭包或回调）
- `FileTrajectoryStore`：JSONL 读写，`trajectoryToDict` / `dictToTrajectory` 用 json.Marshal/Unmarshal
- `FileTrajectoryStore` 的 `_to_json_compatible`：Go 用 `json.Marshal` + `json.RawMessage` 递归处理，或直接用 `map[string]any` 中间表示

### 问题 2：9.70 ResumeIfNeeded 修复

**现状**：`ResumeIfNeeded(_ context.Context, agent TrainableAgent)` 缺少 progress 参数，恢复后 start_epoch/best_score 不更新，缺 updater.LoadState。

**修复方案**：

1. **修改方法签名**：
   ```go
   // 修改前
   func (t *Trainer) ResumeIfNeeded(_ context.Context, agent TrainableAgent) error

   // 修改后
   func (t *Trainer) ResumeIfNeeded(ctx context.Context, agent TrainableAgent, progress *Progress) error
   ```

2. **在方法内恢复 progress 字段**：
   ```go
   restored := t.checkpointManager.Restore(agent, ckpt)
   if progress != nil {
       if v, ok := restored["start_epoch"]; ok {
           progress.CurrentEpoch = int(toInt(v))
       }
       if v, ok := restored["best_score"]; ok {
           progress.BestScore = toFloat64(v)
       }
   }
   ```

3. **添加 updater.LoadState 调用**：
   ```go
   if t.updater != nil && ckpt.UpdaterState != nil {
       t.updater.LoadState(ckpt.UpdaterState)
   }
   ```

4. **修改 Train() 调用处**：
   ```go
   // 修改前
   _ = t.ResumeIfNeeded(ctx, agent)

   // 修改后
   if err := t.ResumeIfNeeded(ctx, agent, progress); err != nil {
       logger.Warn(logComponent).Err(err).Msg("[Trainer] 恢复检查点失败，从零开始训练")
   }
   ```

**辅助函数**：`toInt(v any) int64` 和 `toFloat64(v any) float64` 用于安全类型转换（对齐 Python 的 `int()` / `float()` 转换）。

### 问题 3：Updater 返回类型改为切片 + Trainer 候选列表分支

**现状**：`Updater.Update` 返回 `map[UpdateKey]any`，Python 返回 `Union[Dict, List[Dict]]`。Trainer 无法走多候选分支。

**修复方案**：

1. **修改 Updater 接口签名**：
   ```go
   // 修改前
   Update(ctx context.Context, trajectories []*Trajectory, evaluatedCases []*EvaluatedCase, config map[string]any) (map[UpdateKey]any, error)
   Process(ctx context.Context, trajectories []*Trajectory, signals []*EvolutionSignal, config map[string]any) (map[UpdateKey]any, error)

   // 修改后
   Update(ctx context.Context, trajectories []*Trajectory, evaluatedCases []*EvaluatedCase, config map[string]any) ([]map[UpdateKey]any, error)
   Process(ctx context.Context, trajectories []*Trajectory, signals []*EvolutionSignal, config map[string]any) ([]map[UpdateKey]any, error)
   ```

2. **修改所有现有 Updater 实现的返回值**（包裹成切片）：
   - `SingleDimUpdater.Update` / `Process`：返回 `[]map[UpdateKey]any{result}` 替代 `result`
   - `MultiDimUpdater.Update` / `Process`：同上
   - `InstructionOptimizer` 的 backward/step 不直接实现 Updater，但通过 SingleDimUpdater 间接影响

3. **修改 Trainer.train() 循环**：
   ```go
   if updateErr == nil {
       if len(updated) == 1 {
           // 单方案：直接 apply
           updates := normalizeUpdates(updated[0])
           ApplyUpdates(operators, updates)
           valScore, valEvaluated, _ = t.Evaluate(ctx, agent, valCases)
       } else if len(updated) > 1 {
           // 多候选方案：验证集评估每个候选，选最优
           valScore, valEvaluated = t.SelectBestCandidateOnVal(ctx, agent, operators, updated, valCases)
       }
   }
   ```

4. **清理 updater/protocol.go 的 2 处 ⤵️ 差异标注**：返回类型已改为切片，差异不再存在，删除注释。

5. **更新 Trainer.Forward 中对 Updater.Update 返回值的使用**：`updated` 类型从 `map[UpdateKey]any` 改为 `[]map[UpdateKey]any`，Forward 中取 `updated[0]` 使用。
