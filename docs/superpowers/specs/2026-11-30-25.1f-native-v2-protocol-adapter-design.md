### 1.3 `native_v2` 是什么（讨论修正后的准确表述）

**不是外部 CLI 支持，而是「用公开 harness protocol 托管一台进程内 L2」的 provider 选项。**

| provider | 后端 | 执行位置 |
|---|---|---|
| `claudecode` / `codex` | 外部 CLI 子进程 | 进程外（stdio + SDK） |
| `dsh` | DeepSeek Harness SDK | 进程外 |
| `native`（15.6） | plain **L1 DeepAgent** | **进程内** |
| **`native_v2`（本批）** | **L2 NativeHarness（继承 DeepAgent）** | **进程内** |

证据：
- `protocol_adapter.py:126` `return NativeHarness(spec, build_context=self._build_context)`，`native_harness.py:134` `class NativeHarness(DeepAgent)`。
- `factory.py:68` `_NATIVE_PROVIDERS = frozenset({"native", "native_v2"})`，与三方 provider 明确分开。
- `factory.py:415-419`：*"For `native` / `native_v2` the template itself is loaded by the harness, so only `extra_system_prompt` reaches the context; for third-party providers the persona prompt sections are rendered into `system_prompt` and the manifest MCP servers become `mcp_servers`"*。
- `external_harness_helpers.py:52` `_PROVIDER_TO_CLI_AGENT` 只有 `claudecode`/`codex` 两项，`native_v2` 不进 CLI 分支。函数名里的 "external" 指**会话由宿主以统一协议托管**，不是后端在外部进程。
- `native_v2` 在 jiuwenswarm 生产代码零命中：**已定义、已注册进工厂、生产消费者尚未接线**。

**一句话**：`native_v2` 与 `native`(15.6) 是同一条内部路线的两个版本——V1 只有基础 Turn，V2 多了六能力（steer / force-abort / graceful-abort / pause-resume / checkpoint / persistent-session），这些能力**全部来自 L2 内核**，adapter 只做协议翻译 + 快照值对象，不新增 agent 能力。

### 1.4 用户消息如何"路由"（讨论修正）

**默认情况框架不做按成员路由，也不猜收件人。** `team_agent.py:invoke/stream`（`:899-930`）：

```
_prepare_initial_input(inputs)
  ├─【A 显式结构化】GroupChatMessage / parse_interact_str 命中（@all / 定向指令）
  │    → _dispatch_initial_leader_route → TeamRuntimeManager.dispatch_payloads
  │      （注释原文 "without starting leader LLM"：连 leader 模型都不调）
  └─【B 默认普通文本】
       → coordination.enqueue_user_input(inputs)      kernel.py:680-700
         payload 只有 content + run_context，**无 recipient**
       → 绑定到 leader 那台 TeamAgent，leader 自己的 L2 起一轮
       → leader LLM 决策 send_message(to=X) / create_task(assignee=X)
       → Messager.publish → 成员 X 的 mailbox → 成员 X 的 L2 supervisor
```

`kernel.py:703-710` `enqueue_initial_mailbox_poll` 对 `role == LEADER` **直接 return**，只有非 leader 成员启动才 poll 自己邮箱。第三条不经过用户消息的派发是 25.2 的 `TeamScheduler` 按任务板状态自动派发（`scheduler.py:914/756`）。

**结论**：团队层做的是「① 把用户输入交给 leader（或按显式指令直投）② 提供消息总线/任务板让 leader 模型或调度器自己决定派给谁 ③ 成员各自 poll 邮箱」。`handlers/message.py:on_message_or_broadcast` 处理的是**已带收件人的** `team.message` 事件（leader 发出来之后那一跳），不是用户原始消息。25.1f 属旁链，**完全不碰这条路由**。

- **D-1 包归属**：Python `protocol_adapter.py`/`checkpoint.py` 在 `agent_teams/harness/`，Go 归 `harness_providers/native/`。理由：与 15.6 `DeepAgentHarness` 同包才能非导出复用 `turnState`/`consumeChunk`/`newTurnState`（§2.1 已核三者非导出同包）；factory 注册零跨包；adapter 语义本就是 provider 实现。回收条件 = 上游把这两文件搬进 `harness_providers/native/`。
- **D-2 vcs 包范围**：Python `vcs/` 13 文件 1418 行，Go 本批只落 `codec.go` 1 文件（68 行）。理由：其余 12 文件全仓零消费方（YAGNI）；但**子包目录先建并登记**，保证将来路径不返工。回收条件 = 出现 `backend/manager/delta` 的消费方。
- **D-3 组合替继承 + 虚派发规避**：见 §5 全节。
- **D-4（沿用 15.5 既有登记）**：Go `sync.Mutex` 线程级，`IDLE` 转移移到锁外发射；本批不改。
- **D-5 `stop_condition_state` 改名映射（自检复核后修订；层级无问题）**：Python `_capture_checkpoint:393` 显式 `deepagent["stop_condition_state"] = agent.loop_coordinator.get_state()`、`_open_session:211` 显式 `agent.loop_coordinator.load_state(restored.deepagent["stop_condition_state"])`，方法定义在 `harness/task_loop/loop_coordinator.py:153/172`；`deep_agent.py:3010/3857` 自身也把 `coordinator.get_state()` 写进 `state.stop_condition_state`。
  **Go 侧能力齐全、只是被改了名（见 D-6 纠正）**：`(*task_loop.LoopCoordinator).ExportState()`(`loop_coordinator.go:194`) / `ImportState()`(`:217`)，`LoopCoordinatorState`(`:16`) 四键 `iteration`/`token_usage`/`stop_reason`/`evaluator_states` 与 Python dict 逐字一致；`ImportState` 内 `startTime = time.Now()` 对齐 Python `_start_time = time.monotonic()`（从恢复点重新计时），逐 evaluator `ImportState` 亦齐（`stop_condition.go:23-27/169-249`）。**层级与 Python 一致**（`harness/task_loop/` ↔ `internal/agentcore/harness/task_loop/`），不存在能力缺失。

## 5. D-3：Go 虚方法派发陷阱与落地手法（讨论中提前核实）

### 5.1 陷阱判据

Go 嵌入 + 子类覆盖方法时，**基类方法体内 `t.xxx()` 静态绑定到基类版本**，子类覆盖永不生效（编译通过、无告警、功能静默失效）。本仓已 3 次实锤。修法 = 构造期注入接口/函数指针。

### 5.2 15.5/15.6 已用正确手法

`SerializedTurnHarness` 全部 14 处调用都经 `h.hooks.XXX(...)`（`providerHooks` 接口字段），**没有一处自调用**：

```go
// NewDeepAgentHarness 构造期注入（harness.go:728-742）
h.base = harness_providers.NewSerializedTurnHarness(harness_providers.HarnessOptions{
    Card: AgentFactoryCard(),
    Hooks: h,        // ← 把自己作为钩子实现注入
})
```

因此 15.6 覆盖 `ValidateContext`/`OpenSession`/`ExecuteTurn`/`Steer`/`InterruptTurn`/`CloseSession` 等是**真派发**。`base.go:290` 注释已明确「hooks 已构造期注入，无虚派发问题」。

### 5.3 残留风险：15.6 内部自调用链

```go
func (h *DeepAgentHarness) ExecuteTurn(...) {
    if err := h.runRound(ctx, agent, turn, state, query); err != nil { ... }   // ← 自调用
    return h.buildResult(turn, state, timing)                                  // ← 自调用
}
func (h *DeepAgentHarness) runRound(...) {
    if err := h.consumeChunk(ctx, turn, state, chunk); err != nil { ... }       // ← 自调用
}
```

若 adapter 嵌入 `*DeepAgentHarness` 后"覆盖" `runRound`/`consumeChunk`，Go 静态绑定到 15.6 版本，**adapter 覆盖完全不生效**。

### 5.4 落地手法（Q7 确认）

**不采用「嵌入 `*DeepAgentHarness` + 覆盖」**，分三类：

1. **5 个 providerHooks**（`ValidateContext`/`OpenSession`/`CloseSession`/`Steer`/`InterruptTurn`）：adapter 自己实现 `providerHooks` 全部 11 方法（8 个 optional 按 `UnsupportedHarnessCapabilityError` 或 15.6 同款默认），构造期 `NewSerializedTurnHarness(Hooks: adapter)` —— 与 15.6 完全同构，天然真派发。
2. **`ExecuteTurn`/`runRound`**：按 `protocol_adapter.py:234-294` **独立重写**，不复用 15.6 `ExecuteTurn`。Python adapter 的 `_run_round` 本就是独立重写（签名多 `agent: NativeHarness`、控制帧分流、L2 五态、`_dispatched`/`_paused_observed`），Go 独立写一份最忠实，且不给 15.6 加字段。
3. **`consumeChunk`/`emit`/公开方法**：⚠️ **§14 复核后修订** —— 初版写「同包具体类型直接调用 `(*DeepAgentHarness).consumeChunk`」，实测证明**不可行**：那会把事件投递到「那个实例自己的 `base`」，而 25.1f 的 active cycle 在 `a.base`（adapter 自己的 `SerializedTurnHarness`），Go 组合无继承、上下文带错，emit 报 `cannot emit ... outside an active cycle`。**正确落法**：adapter **自写** `consumeChunk` 八分支（对齐 `harness.py:369-469`），emit 走 `a.base.Emit`，构造期 `a.consumeFn = a.consumeChunk`；`a.deepAgentHarness` 空实例字段按规则 8 删除。`emit` 同样是 adapter 自写（`ProviderEvent` 改 `Provider="native_v2"` 后调 `base.Emit`）；`Card`/`Start`/`Stop`/`Pause`/`Send`/`Resume`/`ExportCheckpoint` 等 `HarnessProtocol` 面**显式委托或自实现**，照 15.6 `harness.go:287-350` 写法，不依赖嵌入自动转发。

**验收**：单测断言五个 hook 确实回调到 adapter（fake 打标）而非 15.6 默认；断言 `ExecuteTurn` 走 adapter 自己的 `runRound`；控制帧 FIFO 用例绿。

### 6.3 `_run_round`（`:234-294`）+ 控制帧 FIFO（`:219-232`）—— 方案 D 排除点

**生产侧**：`onNativeState`/`onNativeRound` 回调**只投帧，不转换**：

```go

    if a.base.ActiveTurn() != nil {
        a.session.WriteStream(ctx, OutputSchema{
            Type: "native_protocol.control", Index: 0,
            Payload: map[string]any{"state": new.Value()},

```

**为什么不能 callback 直触发（方案 D 被排除的理由）**：`NativeHarness.subscribe` 文档（`native_harness.py:545`）明确 *"Callbacks run inside the supervisor coroutine"*，而模型/工具输出由**另一个协程 `_forward_outputs`** 从 `session.stream_iterator()` 泵进 `outputs()`（`native_harness.py:381-385` 起两个独立 task）。若状态变化直接在回调里 `transition`/`return` 结束 Turn，它会**抢在 forwarder 剩余输出帧之前** → 用户丢掉本轮最后一段 answer/tool_result、Turn 提前终止。`protocol_adapter.py:228-229` 原注释：*"Use the same session FIFO as model/tool output. A callback alone can overtake the output forwarder and prematurely terminate a public Turn."* 把控制事件**写进同一条 session 流**，`async for` 按序读到「…最后一条 answer → control(IDLE)」，先消费完输出再结束 Turn。

Go `(*Session).WriteStream` 已落（`agent.go:395`），`OutputSchema` 已落；不能用 `agent.Outputs()` 直接塞（那是 forwarder 的产物，不排队）。

### 6.6 两层 supervisor 嵌套


`RoundPhase` 三态（`state.py:27-37`）是**一轮内部的子迭代相位**，与 `HarnessState` 五态（生命周期）不同维度：`BOUNDARY` 迭代间可直接停 / `MODEL` 模型调用中可硬取消回滚 / `TOOL` 工具执行中副作用不可逆、必须协作式等跑完。由 `PhaseSnapshotRail`（Go `snapshot_rail.go` 已落）在 `BeforeModelCall`/`BeforeToolCall`/`AfterReactIteration` 维护，`pause`/`abort` 据此选停止策略。**本批只读复用，不改。**

### 6.7 监督协程生命周期（`WithoutCancel` 专节）

`Send()` 同步返回 `SendReceipt` 后，调用方 request-scoped `ctx` 立即取消；若 supervisor 用该 ctx，第一轮未跑就被 cancel。故 `base.go:795` 用 `go h.superviseTurns(context.WithoutCancel(ctx), handle)`（Python 等价 `asyncio.create_task(self._supervise_turns())`，`:356`）。**`WithoutCancel` 只剥取消维、保留 ctx 值，不等于 `Background()`，更不等于"永不终止"。**

**4 条退出路径，全靠显式状态信号 + `Stop()`，不靠 ctx 取消：**

1. **队列跑空自然退出**（最常见）：`superviseTurns` 循环开头 `len(pending)==0 → return`（`base.go:920-930` / Python `:490`）；`defer clearSupervisor` 把 `h.supervisor = nil`（`:1002`）。**按需起、跑空即灭，非常驻协程**；下次 `Send` 再起新的。
2. **`Stop()`**（唯一会话级终止入口，`base.go:570-600` / Python `:309-325`）：`lifecycleLock` 去重 → `commandLock: h.stopping = true` → `active.requestStop()`（原子置 abort+stop）→ `go doStop()` → `<-handle.done`。`doStop`（`:863-898`）：`CancelPendingInteractions(HARNESS_STOPPED)` → `hooks.CloseSession()`（**为执行中轮次解阻塞**）→ `await supervisor`（等它自己 return）→ 清 `_pending/_active_turn/_supervisor` → `abortQueuedTurns`（补发 STARTED+ABORTED）→ `transition(TERMINATED)` → `eventBuffer.Close()` → `_cycleStarted=false`。`superviseTurns` 每轮首尾查 `stopping`（`:923`/`:977`），命中即 `abortQueuedTurns + return`。Python 用 `asyncio.shield(stop_task)`（"One cancelled waiter must not cancel the shared teardown"），Go 用 `stopHandle` 去重等价。
3. **`Abort`**：`active.requestAbort(mode)` + `hooks.InterruptTurn`，只让当前轮提前终态；supervisor 循环继续，最终仍归路径 1 或 2。**Abort ≠ 杀 supervisor**。
4. **轮次异常**：`runProviderTurn` 捕获 `hooks.ExecuteTurn` error → `crashResult` → emit FAILED → （可能 `tryAuthFallback` 重试一次）→ 继续循环。不泄漏协程。

**契约**：`Send` 调用方拿 receipt 即走、ctx 随便取消；supervisor 靠 `pending`/`stopping` 自决退出；**宿主（jiuwenswarm `stop_external_harness` / `HarnessIOAdapter.stop`）必须调 `Stop()`** 释放会话资源。宿主不调 `Stop` 且不再 `Send` 时 supervisor 早已路径 1 return，不存在协程泄漏，只是会话资源未释放。

与 L2 那个「从 `start` 活到 `stop` 的常驻 supervisor」**不同**：协议层这个是「来一批活起一次、活干完就散」。

### 14.2 真实根因（用 `consumeFn` 打标实测拿到确切 error）

`NewNativeV2Adapter` 把 `a.consumeFn` 绑到了 **`a.deepAgentHarness := NewDeepAgentHarness(nil)` 这个空实例**的 `consumeChunk`。该方法（`harness.go:942`，对应 `harness.py:369 _consume_chunk`）把事件投递到「**那个实例自己的 `h.base`**」，而那个 `base` 从未 `Start`（无 `harnessContext`/`eventBuffer`），于是 `base.Emit` 报：

```
cannot emit a deepagent event outside an active cycle
```

因果链：`runRound` 拿到 L2 forwarder 的第一帧普通 chunk → `consumeFn` → 15.6 `consumeChunk` → emit 报错 → `runRound` 返回 error → `base.runProviderTurn` 包成 `crashResult` → `TurnEventKindFailed` → `superviseTurns` 转 IDLE；而 L2 的 `startRound` 已转 RUNNING、因集成场景无真实模型（`task_failed: LLM 实例为 nil`）不 settle → **base=IDLE / L2=RUNNING 漂移**。

Python `:256` 的 `self._consume_chunk(...)` 虽同属 `DeepAgentHarness`，但靠**继承**作用在 `self`（adapter）上，emit 进 adapter 自己的 `SerializedTurnHarness`。Go 组合无继承，直接借用另一个实例的方法就带错了上下文 —— 这是 **D-3 ③「同包直调 consumeChunk」落地的真实缺陷**。

### 14.3 ack 与相位时序（澄清）

- `agent.Send()` **不是"仅入队即返回"**：Go `dispatch` 里 `ack(cmd.reply, h.onSend(...))`、Python `_on_send` 末尾 `self._ack(cmd.ack, seq)` —— 都是 **`onSend` 执行完（含 `startRound` + `transition(RUNNING)` + `emitRound`）之后**才 ack。
- 但实测 `a.Send()` 返回时两层仍 IDLE，原因是 **`a.Send()` 走的是 `base.Send()`（协议层）**，它只 append pending + `go superviseTurns(...)` 就返回 receipt；L2 的 `agent.Send()` 发生在**之后**异步的 `superviseTurns → runProviderTurn → ExecuteTurn` 里。所以「supervisor 还没消费」指的是**协议层** supervisor 尚未消费 pending，不是 L2 的 `cmdSend`。
- 正常态：`superviseTurns` 设 `activeTurn` → `base.transition(RUNNING)` → `ExecuteTurn` → `agent.Send` → L2 `onSend` → `transition(RUNNING)`。**两台 supervisor 同时 RUNNING 是正常态**，靠 `native_protocol.control` 帧把两层的相位转换串成 FIFO 因果链；IDLE 由同一帧驱动，协议层 IDLE 严格在 `_run_provider_turn` 返回之后。
