## 一、定位：这条流程在 agent 会话中的位置与作用

### 1.1 在链路中的位置

20.2 是**进程级入口 + 传输协议层**，位于「外部调用方」与「Runtime 公共 API（20.1）」之间，不触碰 Agent 内部推理循环。

```
外部 SDK / CI 脚本 / 父进程
   │  ① 写一份 JSON（type=run）到 stdin 或 --run-json FILE
   ▼
【20.2 本节】
   machine_entry.execute_source            一次性入口，读一份文档即退出
     ├─ protocol_stdout()                  fd1 dup 到 stderr，JSONL 独占 stdout
     ├─ command_signals()                  SIGINT/SIGTERM/SIGBREAK 唯一归属
     ├─ machine_io.read_run_input          1MiB 上限 / 严格 UTF-8 / 拒重复键 / 拒 NaN
     ├─ machine_io.OneShotWriter           逐条事件 write+flush，最后一条 result
     ├─ machine_entry.prepare_workspace    resolve 全部路径后 chdir
     └─ machine.run_with_signals → _MachineRun.execute
          ├─ machine_policy.validate_output_schema / RunLimits
          ├─ session_guard.SessionLease.acquire（跨进程互斥）      ⤵️ 20.5
          ├─ client.InProcessRuntimeClient.start()

          └─ client.stream / stream_agent（含 on_agent_ready 注入）
   │  ② 每条 RuntimeEvent → OneShotWriter.write_event（JSONL 一行）
   ▼

   ▼
```

### 1.2 四条作用（按重要性）

**① 把一次性执行变成可机器判读的契约**

一次性进程里唯一的可判读产物是「stdout 上的 JSONL」与「进程退出码」。20.2 定义这两者的完整规则：`event` 逐条流式发出，`result` 只能一条且必须最后（`validate_one_shot_records` 强制 `sequence` 从 0 连续、`request_id`/`schema_version` 全一致、`result` 在末尾）；退出码 5 档与 `status` 四态一一对应。没有这一层，SDK 只能靠正则抓 stdout 文本。

**② 把 stdout 污染隔离掉**

`protocol_stdout()` 把 fd1 `dup2` 到 stderr，同时 `os.dup` 出一份真实 fd 给 writer。依赖库、工具子进程、C 扩展的 print 全部落 stderr，stdout 只剩 JSONL。这是协议能成立的地基。

**③ 把「一个 Runtime 生命周期」的边界画死**

一次命令 = 一次 `start()` → 一次执行 → 一次 `close()`。清理顺序固定、每步 5 秒有界，宁可报 `SHUTDOWN_FAILED` 也不放弃清理。

**④ 给非交互场景兜住「不能问人」**

`RunLimits`（按 usage 事件数算 turn、按 `total_cost` 累加预算）与 `INTERACTION_REQUIRED`（交互事件出现即失败）保证一次性命令绝不会挂在那里等一个不存在的用户。

### 1.3 「非交互」的准确定义

**「非交互」= 协议里没有任何东西依赖「有一个人类坐在终端前」**，不是「只跑一次就退」。

| 它不是 | 它是 |
|---|---|
| 不是「只能跑一次请求」 | 一次进程 = 一个 Runtime 生命周期；`--run-jsonl` 可长连接跑完整个任务 |
| 不是「单向」 | 有反向通道：`type=answer` / `type=cancel` / `type=tool_result` |
| 不依赖 TTY | 不读终端尺寸、不画进度条、不等回车、不弹权限对话框 |
| 不等于「没人用」 | 它同时是 **20.8 SDK 的传输层**（Python/TS SDK 都跑在 `--run-jsonl` 上） |

对照 `repl.py`（读终端、画 UI、收键盘输入做 steer）——那才是「给人用的」，是 20.3/20.4 的范围。两者共用同一套 `protocol/`（`schema.json` 里 `run`/`query`/`control`/`event`/`result` 是一份 schema）。

### 1.4 与领域十五的关系（镜像，不是同类）

| | 领域十五 | 领域二十 |
|---|---|---|
| 谁是谁的宿主 | **我们是宿主**：启动 Claude Code / Codex 子进程，读它们的 stdout | **我们是外部 CLI**：别人启动我们，读我们的 stdout |
| 角色 | 我们当司机 | 我们当发动机 |

领域十五是「把别人的 CLI 拉进来当工具使」；领域二十是「把自己打扮成一个 CLI，让别人的程序把我们拉进去当工具使」。

3. `cleaning` → 返回（清理期不打断）
4. `task != nil && !task.done()` → `task.cancel()`；否则 `raise KeyboardInterrupt`

**Go 映射**：

| Python | Go |
|---|---|
| `signal.signal(SIGINT/SIGTERM/SIGBREAK, owner.interrupt)` | `signal.Notify(ch, syscall.SIGINT, syscall.SIGTERM)`（Windows 加 `SIGBREAK`） |
| `raise KeyboardInterrupt`（同步期信号） | 无法在 signal handler 里 panic 到主 goroutine；Go 用 `os.Exit(130)` 或关闭 done channel 让主流程退出 |
| `self._task.cancel()` | `context.CancelFunc` |
| `ContextVar _ACTIVE` | `context.Context` 携带（或包级 `atomic.Pointer`） |

**这是结构性偏差**：Python 的「同步期信号 → KeyboardInterrupt」在 Go 无法逐字复刻（Go 的 OS signal handler 不能 panic 到任意 goroutine）。等价实现：signal 到达时若尚未进入执行阶段，直接 `os.Exit(130)`；已进入执行则 cancel ctx。登记为 D-2。

**`finalize(result)`**（`:64-76`）：`settled = true`；若 `interrupted` 且 `result.Error == nil` → 改成 `CANCELLED` / exit 130 / error `{code: "CANCELLED", message: "Command interrupted."}`。

**`defer_command_signals()`**（`:101-105`）：置 `cleaning = true`，让清理阶段的 signal 不打断协作式资源释放。
