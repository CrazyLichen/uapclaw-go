### 1.2 三个方向的三套机制

本节是**双向适配层**，不是「只调用外部 CLI」。`SerializedTurnHarness` 同时服务进程内 provider（`native` / `native_v2`）与外部子进程 provider（`claudecode` / `codex` / `dsh`），因为它抽象的是「一次会话里输入串行执行」这个共同形状，与子进程/进程内无关。

三个调用方向由三套不同机制承担，这是本节最需要讲清的结构：

| 方向 | 机制 | 说明 |
|---|---|---|
| 宿主 → harness | `harnessprotocol.HarnessProtocol` 接口（14 方法） | 15.1 已定义，`SerializedTurnHarness` 实现它 |
| harness → provider 钩子 | `providerHooks` 接口字段（10 方法） | **本节新建**，构造期注入，动态派发 |
| provider → harness 能力 | **嵌入** `*SerializedTurnHarness`（静态方法提升） | `h.Emit(...)`，编译期确定 |

**为什么必须有第二套机制**：Go 的方法提升只能从外向内（provider 调基座 ✓），不能从内向外（基座调 provider ✗）。基座方法体内写 `h.ExecuteTurn(...)` 时 `h` 的静态类型是 `*SerializedTurnHarness`，会静态绑定到基座版本，provider 的覆盖永不生效——编译通过、无告警、功能静默失效。这是 `go-embedding-virtual-dispatch-trap`（2026-11-08 实施 25.0c 时踩到）的同一陷阱。

因此基座内部不能持「基座类型的 self」，必须持**接口字段**。

## 3. 设计决策

### Q1 · `SerializedTurnHarness` 的钩子机制

**裁决：方案 B —— 构造期注入 `providerHooks` 接口字段。**

基座持 `hooks providerHooks` 字段；provider 实现该接口、同时嵌入 `*SerializedTurnHarness` 以获得 `Emit`/`Transition` 等能力；构造期 `SetHooks(self)` 闭环。

**理由**：Go 的方法提升只能从外向内，基座方法体内的 `h.ExecuteTurn(...)` 会静态绑定到基座版本，provider 覆盖永不生效（`go-embedding-virtual-dispatch-trap`）。`hooks` 接口字段是唯一能让基座动态派发到 provider 的机制。

**被否方案**：
- 嵌入 + 覆盖方法：静默失效，编译通过无告警
- 独立 `hooks` 结构体持 `*SerializedTurnHarness`：可行但多一个对象，`ExecuteTurn` 里要写 `h.base.Emit(...)` 而非 `h.Emit(...)`，与 Python 的 `self._emit(...)` 不对应

### Q2 · `providerHooks` 的方法集

**裁决：3 个 required + 8 个 optional = 11 个方法。**

| 类别 | 方法 | Python 基类默认体 | 基类调用点 |
|---|---|---|---|
| required | `OpenSession(ctx, hc) (*string, error)` | 抽象方法 | `base.py:293` |
| required | `CloseSession(ctx) error` | 抽象方法 | `:302, :330` |
| required | `ExecuteTurn(ctx, turn) (TurnEventKind, TurnResult, error)` | 抽象方法 | `:535` |
| optional | `ValidateContext(ctx, hc) error` | `card.validate_host(...)` | `:277` |
| optional | `Steer(ctx, turn, content, messageID) error` | 报 `UnsupportedHarnessCapabilityError` | `:394` |
| optional | `InterruptTurn(ctx, turn, mode) error` | 报 `UnsupportedHarnessCapabilityError` | `:442` |
| optional | `ListModels(ctx) ([]ModelOption, error)` | 报 `UnsupportedHarnessCapabilityError` | `:463` |
| optional | `AuthFallbackPayload() (JsonObject, bool)` | 返回 `nil, false` | `:569` |
| optional | `ReconnectForAuth(ctx, fallback bool) error` | 报 `HarnessProtocolError` | `:573, :590` |
| optional | `OnAuthEndpointChanged(ctx, fallback bool) error` | no-op | `:594, :598` |

### Q4 · `BoundedEventBuffer` 的并发原语

**裁决：`sync.Mutex` + `sync.Cond`（broadcast 版）。**

直接对应 `asyncio.Condition.wait/notify_all`。`Peek` 天然支持（持锁读 `items[0]`）；`Close` 置 `closed=true` 后 `Broadcast` 唤醒全部。

**已知限制**：`sync.Cond.Wait()` 无 ctx 支持，`Put`/`Get`/`Peek` 无法因取消而返回。这与 Python 一致（`asyncio` 侧同样靠 `close()` 唤醒而非 task cancel），故语义忠实。

**被否方案**：
- `chan struct{}` 通知 + Mutex 保护 slice：可响应 ctx，但「唤醒一个还是全部」需仔细设计，且 `Put` 阻塞等待容量时不能持锁
- 纯 `chan HarnessEvent`：`Peek` 无法自然表达（需额外 `front` 暂存位），单消费者租约还要另加 atomic flag，状态分散三处最易出竞态

### Q5 · `BoundedEventBuffer.items` 的容器

**裁决：`[]HarnessEvent` + `items = items[1:]`，并在 `Get` 中清零已消费格子。**

```go
var zero harnessprotocol.HarnessEvent
b.items[0] = zero        // 切断对 payload 的引用，防切片前移泄漏
b.items = b.items[1:]    // 只移动 header，O(1)
```

**理由**：`items = items[1:]` 不复制数组，只移动 slice header，`Get` 是 O(1)，与 Python `deque.popleft` 对应。清零那行是 Go 处理切片前移内存泄漏的标准手法（标准库 `container/ring`、`net/http` buffer 同款），代价是一次约 100 字节的 struct 赋值，收益是零残留。

**被否方案**：
- 不加清零：长期运行会积累残留引用，最坏卡住 1024 个事件的 payload 不释放
- 环形缓冲（head/tail 索引）：零浪费但每个操作都要判满空、算模，对已经足够复杂的状态机不值得
- `container/list`：`popleft` 真 O(1) 且不浪费，但每元素多一次堆分配，`Peek` 要类型断言

### Q6 · `Get`/`Peek` 的「已耗尽」表达

**裁决：`(*HarnessEvent, error)`，耗尽返回 `nil, harnessprotocol.ErrEventStreamDone`。**

**理由**：`ErrEventStreamDone` 已在 15.2 定义为「观测游标到达末尾」（`harness_protocol/stream.go:23`）。buffer 层耗尽与游标层耗尽本质是同一件事，复用避免两套哨兵。调用方 `errors.Is(err, ErrEventStreamDone)` 判定。

**被否方案**：
- `nil, nil`：与 Python `None` 一一对应，但 Go linter 对 `(nil, nil)` 通常告警
- `nil, io.EOF`：语义是「流结束」，比该场景窄，且与已有哨兵重复

### Q7 · `Put` 在 `close` 后的返回值

**裁决：返回 `ErrEventBufferClosed` 哨兵 error，由 `Emit` 原样透传，最终由 `RunProviderTurn` 兜底转 FAILED。**

**理由**：Python 的 `EventBufferClosed` 全仓**零捕获点**（`grep -rn "EventBufferClosed" openjiuwen/ tests/` 只命中 `stream.py` 自身三处），实际靠 `_run_provider_turn` 的 `except Exception` 兜住转 `FAILED`。Go 忠实复制该链路。`errors.Is` 让调用方可判断。

**被否方案**：
- 静默返回 nil：制造「静默成功」假象，正是历史上反复出现的 `fake success` 坑
- `Emit` 内部捕获并忽略：Python 无此层，属新增行为

### Q8 · `ctx` 参数

**裁决：`Put`/`Get`/`Peek`/`Close` 全带 `ctx context.Context`。**

`sync.Cond.Wait()` 不响应 ctx，但保留参数便于将来改造、也让 `Emit(ctx, ...)` 的调用链上下文完整。实现上暂不消费，用 `_ = ctx` 显式标注「保留位，cond 不响应取消」。

### Q9 · `BufferedEventCursor.Close` 是否唤醒阻塞者

**裁决：`Close` 额外 `Broadcast` 一次，让阻塞在 `Next` 中的协程立刻醒来并返回 `ErrEventStreamDone`。**

**上游事实**：`stream.py:161-165` 的 `aclose` 只做 `self._closed = True; self._buffer.release_consumer()`，**不唤醒**。已阻塞在 `Get()` 的协程必须等 `buffer.close()` 才醒。上游唯一调用点 `io_adapter.py:470` 的 `finally` 发生在 `async for` 退出后（不阻塞时），故不触发该边界。

**为什么 Go 要改**：Go 的 `sync.Cond` 没有 asyncio 的 task 取消兜底，悬挂 goroutine 是真实泄漏（`-race` 的 goroutine 泄漏检测会抓到）。且 `Close(ctx)` 的语义就是「我要停止消费」，不唤醒就不自洽。

**偏差性质**：比上游更强，用 `errors.Is` 判定的调用方行为不变。登记为偏差 D3。

### Q10 · 持锁 `await` 的移植

**裁决：`base.py:516-526` 改成「锁内判状态、锁外发事件」。**

Python 在 `async with self._command_lock:` 内 `await self._transition(HarnessState.IDLE)`，而 `_transition` 会 `await _emit` → `await buffer.put`（可能阻塞）。这依赖「asyncio.Lock 是协程级的，等待会挂起协程而非线程」。Go 的 `sync.Mutex` 是线程级的，持锁等待必然死锁。

Go 版：锁内算 `needIdle := !h.stopping && len(h.pending) == 0`，出锁后 `if needIdle { h.transition(ctx, HarnessStateIdle) }`。语义等价（IDLE 转移仍是「最后一个轮次结束后且无排队」时发生）。

登记为偏差 D4「锁外发事件」。

**通用原则**：本节所有 `commandLock` / `lifecycleLock` 的临界区只包含状态字段读写，绝不包含 `Transition` / `Emit` / `hooks.ExecuteTurn` 等可能阻塞的调用。

### Q11 · `h.state` 的并发保护

**裁决：`state` 用 `atomic.Value` 或 `atomic.Pointer`。**

`State()` 是宿主高频繁调用（`Emit` 等路径也会读），而 `Transition` 在 supervisor goroutine 里写。若 `State()` 加锁会与 supervisor 抢锁；若都不加锁是数据竞争。

用 `atomic.Value` 存 `HarnessState`（同类型，合法），读时 `h.state.Load().(HarnessState)`。这样 `State()` 纯读零锁，`Transition` 原子写。

登记为偏差 D5（Python 无对应，asyncio 单线程）。

### Q12 · supervisor 自调用判断

**裁决：Go 侧省略 `if supervisor is not asyncio.current_task()` 判断。**

**核查依据**：`_do_stop` 只有一处调用点（`base.py:322`，由 `stop()` 创建 task）；`stop()` 的调用方是 `io_adapter.py:324` 与 15.6-15.9 的 provider 外部调用。supervisor 内部只读 `_stopping` 标志，**从不**调 `stop` / `_do_stop`（`sed -n '487,532p' | grep "stop\|_do_stop"` 只命中三处 `if self._stopping` 读取）。

故该判断是防御性冗余代码，Go 侧不写（规则 8：不写无调用方的壳）。

### Q13 · `_stop_task` 的 shield 语义

**裁决：Go 侧无需特殊设计。**

Python 的 `await asyncio.shield(stop_task)` 保证多并发 `Stop` 共享同一 teardown、任一调用者被取消不影响 teardown。Go 的 `<-stopHandle.done` 天然满足「多方等待同一完成信号」，ctx 取消只影响调用者自己是否继续等。

**`Next` 的完整逻辑**（1:1 复刻 `stream.py:106-159`，含 peek 防竞态）：

```
若 cursor.closed → 返回 ErrEventStreamDone

loop:
  if perTurn && selectedTurnID == nil:
      event = Peek()          // 防 pop-then-push 竞态
  else:
      event = Get()
  if err is ErrEventStreamDone (耗尽):
      Close()
      if perTurn && selectedTurnID != nil:
          return HarnessProtocolError("harness event stream closed before turn %q terminated")
      return ErrEventStreamDone

  if !perTurn: return event

  // per-turn 路径
  if selectedTurnID == nil:
      if 载荷不是 TurnLifecycleEvent（值或指针任一形态）或 kind != STARTED:
          Get()               // 丢弃非 STARTED
          continue
      if expectedTurnID != nil && event.TurnID != *expectedTurnID:
          Close()
          return HarnessStateError("requested turn is not the next unconsumed turn: expected %q, found %q")
      consumed = Get()        // 不会阻塞，依据见下
      if consumed == nil:
          Close()
          return HarnessProtocolError("harness event stream changed while selecting a turn")
      event = consumed
      selectedTurnID = &event.TurnID

  if event.TurnID == *selectedTurnID && IsTerminalTurnEventKind(载荷.kind):
      Close()                 // 终态自动释放租约
  return event
```

**为什么「兑现 Peek」处的 `Get` 不会阻塞**（实施时曾误判为偏差，2026-11-27 更正）：

`Peek` 返回到 `Get` 之间没有任何协程切换点，且队列长度只可能增加：

- 单消费者租约保证**只有本游标能消费**（`consumerActive` 互斥）
- 生产者（`Emit`）只做 `Put` 追加，**没有任何路径删除队列元素**

因此 `Peek` 看到的那条必然还在队首，`Get` 立即返回。**Python 的 `await peek()` 与 `await get()` 之间同样不会切换协程**（asyncio 只在 `await` 点调度），两者行为一致，无需特殊处理。

> 实施记录：曾一度引入非阻塞的 `dropHead` 作为「防御」，后经复核确认该路径不可达，已撤除（提交 `2885de58a`），改回与上游逐字对应的 `Get`。

#### 4.2.1 `Emit`

1:1 复刻 `base.py:673-716`，五个注意点：

1. **`provider_session_id or self._session_id` 的 or 语义**：Python 的真值判断对空串也 fallback，Go 必须显式展开（不能用 nil 判断）：

```go
func emitProviderSession(override *string, sessionID *string) string {
    if override != nil && *override != "" { return *override }
    if sessionID != nil { return *sessionID }
    return ""
}
```

2. **`causation_ids` 去重**：`((turn.message_id,) if turn else ()) + tuple(c for c in causation_ids if not turn or c != turn.message_id)` —— 有 turn 时排除等于 `turn.messageID` 的额外 cause。

3. **`timestamp` 的 nil 语义**：`*float64`，nil 表示用当前时间。不能用 0（0 是合法 Unix 时间戳）。

4. **`NewHarnessEvent` 的校验失败**：15.2 已落的构造器会做 `FreezeJsonObject` 等校验，失败返回 error。Python 对应 pydantic `ValidationError`，故 Go 返回 error 忠实。

5. **`buffer.Put` 的 `ErrEventBufferClosed`**：原样透传（Q7）。

#### 4.2.2 `doStop`

1:1 复刻 `base.py:327-353` 的 **9 个步骤，顺序不可调**：

```
1. cancelPendingInteractions(HARNESS_STOPPED)
2. hooks.CloseSession()          失败仅 Error 日志，继续
3. 等 supervisor 收敛              失败仅 debug 日志，继续
4. 锁内：取走 pending 队列、清 activeTurn、清 supervisor
```

**注意步骤 2 与 7 的顺序**：先 close_session（解除轮次阻塞）再 close buffer（解除消费阻塞）。反序会让轮次协程在已关闭的 buffer 上 `Put` 拿到 `ErrEventBufferClosed` 并转 FAILED，而 Python 的意图是让轮次自然收敛后再关流。

#### 4.2.3 `superviseTurns`

1:1 复刻 `base.py:487-531`。**Q10 的锁外发事件在此处落地**：

```go
for {
    h.commandLock.Lock()
    var active *PendingTurn
    var queued []*PendingTurn
    if h.stopping {
        queued = h.pending; h.pending = nil; active = nil
    } else if len(h.pending) == 0 {
        h.commandLock.Unlock()
        return
    } else {
        active = h.pending[0]; h.pending = h.pending[1:]
        h.activeTurn = active
    }
    selection := h.pendingModelSelection
    h.pendingModelSelection = nil
    h.commandLock.Unlock()          // ← 出锁

    if active == nil {
        h.abortQueuedTurns(ctx, queued)   // 锁外发事件
        return
    }

    h.transition(ctx, HarnessStateRunning)
    h.Emit(ctx, NewTurnLifecycleEvent(STARTED), EmitOptions{Turn: active})
    if selection != nil {
        h.applyDeferredModelSelection(ctx, selection, active)
    }
    terminalKind, result, _ := h.runProviderTurn(ctx, active)
    if terminalKind == TurnEventKindFailed && h.tryAuthFallback(ctx, result.Error, active) {
        terminalKind, result, _ = h.runProviderTurn(ctx, active)
    }
    h.Emit(ctx, NewTurnLifecycleEvent(terminalKind, &result), EmitOptions{Turn: active})

    h.commandLock.Lock()
    h.activeTurn = nil
    needIdle := false
    if h.stopping {
        queued = h.pending; h.pending = nil
    } else if len(h.pending) == 0 {
        needIdle = true             // ← 锁内判状态
    }
    h.commandLock.Unlock()

    if needIdle {
        h.transition(ctx, HarnessStateIdle)     // ← 锁外发事件（Q10）
    }
    if len(queued) > 0 {
        h.abortQueuedTurns(ctx, queued)
        return
    }
    if h.stopping { return }
```
