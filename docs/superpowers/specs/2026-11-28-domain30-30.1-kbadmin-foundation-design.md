# 30.1 地基：kb_admin 域 + 数据模型 设计

## 1. 范围

- 新包 `internal/swarm/server/kbadmin/`：五表 DAO、KBService/DocService/ChunkService/SearchService 骨架、E2A 分发入口
- 五张 SQLite 新表 + 领域七 Migrator 注册
- kb.* 方法族 E2A 分发全族注册
- kb.kb.create/delete 最小编排打通（DAO ↔ 向量库 collection）

## 2. 已拍板决策

| 决策点 | 结论 |
|---|---|
| 包落点 | **方案 A**：`internal/swarm/server/kbadmin/` 子包，比照 videotask 先例（doc.go + 域内自治）；server 侧一行接线，gateway 零改动 |
| E2A 注册范围 | **方案 A**：`handleMessage` 分发表一次注册 kb.* 全族（kb.kb.*/kb.doc.*/kb.chunk.*/kb.chunker.*/kb.search.*/kb.task.*）；未实现方法在分发处统一返回 `KB_NOT_IMPLEMENTED` 错误码 |
| 建表方式 | **方案 A（2026-11-28 修订）**：GORM AutoMigrate，kbadmin 包初始化时自建五表（比照 `agent_teams/tools/database/sql_engine.go` 业务表惯例）。原拍板「领域七 Migrator」作废——核查发现领域七迁移框架为记忆域专用（对齐 Python run_migrations，迁移对象是 memory store），非通用业务表 DDL 框架，经用户确认改拍板 |
| CRUD 真实性 | **方案 C**：DAO 全真 + create/delete 最小编排（DAO 写入 ↔ 向量库 collection 创建/删除，SimpleKB 单类型先行）；list/get/update 纯 DAO |
| 实施顺序 | **换序拍板**：领域三十实施序调整为 **30.1→30.5→30.2→30.3→30.4→30.6→30.7→30.8→30.9**（编号不动，仅改顺序注记）；理由：30.5 分帧通道是纯通信基础设施且 30.2/30.6 都依赖它，提前后 30.2 直接吃真上传文件，全链端到端最早打通 |

## 3. 数据分层（职责切分）

- **SQLite（kbadmin 私有台账，全局一份）**：`kb_info`（一行一 KB）/ `kb_doc`（一行一文档）/ `kb_chunk_meta`（一行一分块）/ `kb_chunk_revision`（一行一编辑版本）/ `kb_task`（一行一解析任务）。行级 kb_id/doc_id 外键区分归属，单用户全局共享无隔离
- **向量库（retrieval 内核所有）**：每 KB 一个 collection，chunk 正文 + embedding 存此；kbadmin 仅在 create/delete 时调工厂编排，检索测试调 Retrieve
- 两边靠 kb_id/doc_id/chunk_id 对齐；retrieval 包本批零改动

## 4. 依赖方向

```
internal/swarm/server（一行接线）
    └─ internal/swarm/server/kbadmin
          ├─ DAO（GORM 结构体映射，比照 9.65a-2 TaskDao 惯例）
          ├─ Service 骨架 ×4
          ├─ handle_kb.go 分发入口（E2AEnvelope → AgentRequest → switch kb.*）
          └─ core/retrieval（工厂 + KnowledgeBase 接口，13.26/13.27/13.28 既有）
```

不穿过 gateway；不依赖 30.2 worker / 30.5 分帧 / 30.3 locators。
