## 1. 背景与流程位置

`api_mode=responses` 的 OpenAI 系模型需走 `/v1/responses` 协议（Chat Completions 之外），带来三项能力：

1. **reasoning 跨轮持久化**：`include=["reasoning.encrypted_content"]` 回传，工具调用历史带 `response_item_id`，下轮按 Responses 语义重建 `function_call` item；
2. **流式 function arguments 增量**：长工具调用逐 delta 流出（TTFT / 流空闲超时可观测），`output_item.done` 只补未流出的 remainder；
3. **usage reasoning_tokens**：思考 token 用量归一上报。

调用链位置（一次 agent 会话）：

```
Harness/ReAct 循环 → ModelClient.Invoke / Stream        ← 23.2 分流点
  ├─ api_mode=""（默认）   → Chat Completions（openai/client.go 现路径）
  ├─ api_mode=responses    → [23.2 新增] /v1/responses transport
  └─ provider=Anthropic    → [23.1 已完成] Messages API
```

分流点对齐 Python `openai_model_client.py:1878`（invoke）与 `:2060`（stream）。

### 3.2 关键语义

- 分流判定读 `config.APIMode == APIModeResponses`（Go 零值 "" 等价 Python None）。
- `_resolved_api_key()` 对应 Go 现有 api_key 解析；bearer 即 api_key（OAuth access token 待 23.6）。
- transport 默认 base_url：内联 Python `DEFAULT_OPENAI_ACCOUNT_BASE_URL` 常量值，注释标注 23.6 归属。
- Go 无 httpx：transport 用 net/http + 自实现 SSE 逐行读取（对齐 buffer 空行结算语义）；client 复用与 is_closed 重建语义用 `http.Client` + 空闲连接池等价实现，偏差在 spec 登记。
- chunk 相加复用 `AssistantMessageChunk.Add`（已含 response_id/response_model/provider_metadata/provider_content 合并逻辑，23.1 已验证）。
- 事件回调（LLM_INPUT / RESPONSE_STARTED / RESPONSE_RECEIVED / OUTPUT / CALL_ERROR）复用 Go 现有 callback trigger 位置，字段逐条对齐 Python。
- 错误包装对齐 `MODEL_CALL_FAILED` + `format_provider_exception`（复用 `providererror` 包）。

## 4. 错误处理

- HTTP ≥400：`raiseForHTTPError` 等价物（error.message → detail → summarize_provider_error_text → 固定文案，带 status_code）。
- transport/请求异常：`emitResponsesError`（LLM_CALL_ERROR 回调 + Error 日志含 event_type/model_provider/is_stream/exception）→ 上抛 `MODEL_CALL_FAILED` 包装。
- 流内 `response.failed`/`error` 事件：抛 `ResponsesError`，在 stream 循环中走同一条 emit + 包装路径。
- 解析失败：非流式 Warn 日志 + parser_content=None；流式静默清空累积。
