## 严重（5 条）

### S-1 每次 HTTP 请求都泄漏一个 outbound 对象，从不注销
- 位置：`internal/swarm/channel_manager/web/web_http_routes.go:647-665` → `web_http_dispatch.go:158`
- Python 原版在请求结束时（`finally`）一定会把这次请求注册的 outbound 注销掉（web_http_routes.py:732-738）。Go 侧注册了但 unary 链路（全部 130 条路由 + CORE unary）**没有任何一处注销**。每个请求漏一个对象（含通道和 session 条目），而且没关闭，死的对象还会继续收到消息投递。用得越久内存越涨，路由表也被垃圾污染。
- 修法：对齐 Python 的 finally 语义，请求结束统一注销。

### S-2 用户中途断开 SSE 连接，后台生产任务永久卡死泄漏
- 位置：`web_outbound_http.go`（iterSSEFrames）+ `web_http_routes.go:722-731`（handleStream）
- Python 是异步生成器，客户端断开后框架会自动关掉它。Go 这边客户端断开后不再读数据，生产数据的 goroutine 下一次发送就永远阻塞，每次聊天中途断开都漏一个 goroutine。
- 修法：发送失败/断开时主动终止生产端（带缓冲通道 + 退出信号，或 ctx 取消），并登记这条 asyncio→Go 偏差。

### S-3 演进提交的写入链丢了 subject_kind 分类标签（读写不对称）
- 位置：`internal/openuapclaw/agent_evolving/checkpointing/types.go:116-135`、`experience/common.go:23-37,69`、`experience/submission.go:217`
- 前几天修过一次这个问题（72c23a9a9），但只修了**读**这一半；**写**的时候 pending 快照里根本没带 kind 字段，落盘时也不知道自己是谁。结果：团队技能的演进提交会写到个人技能的目录里，存错地方。
- Python 对照：`PendingChange.subject_kind`（experience/types.py:50）、`append_record(..., subject_kind=...)`（common.py:95）。
- 这个漏项没有登记在任何回填批次里，属回填漏项。

### S-4 workflow 中断提交失败被吞掉，系统误以为任务正常完成
- 位置：`internal/openuapclaw/core/single_agent/agents/react_invoke.go:1218-1226`
- 提交中断状态出错时（写 ToolMessage 失败、存上下文失败），错误既不上报也不记日志，循环直接当成"没发生中断"收尾，外层可能把任务判成"已完成"。Python 原版异常是直接往外抛的（react_agent.py:3227-3235）。
- 同文件里 `savedInvokeInputs == nil` 也是什么都不做就 break。

### S-5 团队技能演进 rail 丢了"防自续循环"的抑制门
- 位置：`internal/openuapclaw/harness/rails/evolution/team_skill_evolution_rail.go:1935-1955`
- Python 版往队列里排"下一轮跟进"之前，必先检查一个"是否被抑制"的门（后台定时任务、已经是跟进轮的情况不许再排，skill_evolution_rail.py:600-635）。单 agent 版的 Go 实现有这个门，团队版**漏了**。后果：后台定时轮可能不断给自己排下一轮，形成自我续命的循环。
- 同一文件还配套两个一般问题（见 M-1/M-2），建议一次改完。

## 一般（15 条）

### M-1 团队完成通知的触发开关漏了 review_trigger 分支
- `team_skill_evolution_rail.go:728`：Python 是"signal_trigger 或 review_trigger 任一开就放行"，Go 只判了 signal_trigger。配了 review_trigger 的用户，外部完成通知被静默忽略。

### M-2 RunEvolution 失败被报成"完成"，且进度文案是中文
- `team_skill_evolution_rail.go:697-712, 640-646`：Python 失败时会发 `status: failed` 的后台结果事件 + failed 进度；Go 只记一条 Warn 然后照常发"completed"。另外进度文案写成了中文"团队技能演进因意外错误失败"，违反"协议字符串不得本地化"约定（这是进事件 payload 的）。

### M-3 下载校验大面积缺失：坏数据静默产出损坏文件
- `container_file_http_download.go:98-145`：Python 对每个分块校验五项（偏移对不对、块大小对不对、有没有超限、有没有越界），任何一项不对返回 502（container_file_http.py:466-481）。Go 只查了两项最基础的。spec 里明明登记了"校验 offset/limit"，登记了但没做。

### M-4 下载响应缺两个安全响应头 + 丢了图片内联预览
- 同文件 147-206：Python 恒带 `X-Content-Type-Options: nosniff` 和 `Content-Security-Policy: sandbox`；Go 都没设。另外 `?inline=1` 的图片/音视频内联预览分流也丢了，Go 恒当附件下载。

### M-5 verified 下载丢 user_id + 错误码映射漂移
- `container_file_http_download.go:60,112-119`：Python 把请求者 user_id 传给 AgentServer 做用户域校验，Go 直接丢弃（`_ = uid`）；出错时 Python 透传原始错误码（400 类），Go 一律 500。

### M-6 requestext 扩展透传链只修了前半段，后半段是死链
- `requestext.go:227`：分发面把扩展信息写进了 metadata，但 AgentServer 入口没人把它取出来（Python 在 agent_ws_server.py:2779 有 lift_from_metadata），下游也没人消费（mcp_dynamic_token_patch.py:539）。链路接了半截。这属于"缺失项"，应向用户提报裁决（规则 13.2）。

### M-7 多模态图片消费语义失效：图片会被反复带上
- `internal/openuapclaw/harness/deep_agent.go:427,524,3368-3374,3593-3597`
- Python 用 `inputs.pop` 把图片附件一次性消费掉（下一轮不再带）。Go 的 pop 删的是一份临时拷贝，真正的数据存在 `Extra` 里永生，之后每一轮都会被重新塞回去。后果：后续每轮请求都多带一份 Python 没有的图片数据，重复投递。

### M-8 中断恢复轮的图片附件没有写入点，恢复时图片静默丢失
- `internal/swarm/server/adapter/deep_adapter.go:2054-2058`：c9ba02f0c 删了原来的直写，注释说"恢复轮图片由 resume inputs 携带"，但全仓搜下来 resume 链路**没有任何地方写这个键**。Python 中断路径是有 set 的（真相源树缺该文件，标待核实）。

### M-9 WorkflowOutput 序列化字段名大写，和 Python 线协议不一致
- `core/workflow/workflowbase/workflowbase.go:24-29`：`Result`/`State` 没有 json tag，序列化成大写开头；Python 输出 `result`/`state`。这次类型强化后这个对象第一次真正流向适配器/前端，大小写漂移变得可达。待核实消费方后定级。

### M-10 workflow 组件 ID 缺键时收集成字面量 "<nil>"，还被测试钉死
- `react_workflow_interrupt.go:109,123`：Python 缺属性是跳过不收集（WorkflowOutput 分支）或取空串（list 分支）；Go 收集成了字符串 `"<nil>"`，污染组件列表。更糟的是 8fe11c5dd 的覆盖率测试把 `"<nil>"` 断言成期望值，假等价被测试锁死。

### M-11 多 workflow 轮转选取顺序不确定（map 随机序）
- `react_workflow_interrupt.go:366-377`：Python 按插入序决定"下一个恢复哪个 workflow"，Go 遍历 map 顺序随机。双 workflow 场景下恢复顺序每次运行都可能不同。

### M-12 演进提交部分失败时错误明细被硬编码成空

### M-13 审查子代理任务描述里 subject 行永远不会插入 + nil 会 panic
- `tools/skill.go:602-603`：map 入参时取不到 subject，该行被跳过；Python 是无条件插入（必填）。

### M-14 演进工具错误处理一处全错误报、多处吞错
- `tools/skill.go:405-408`：任何错误都被包装成 "unknown evolution_review_ref"；Python 只有查无此 ref 才是这个文案，其他错误原样上抛。真实根因被吞。
- `tools/skill.go:415`：`_ = ConsumePreparedSubmission(...)` 错误直接丢弃，吞错后仍报成功。

### M-15 TeamSignalDetector 是 699 行死代码，注释里的 Python 锚点是虚构的
- `agent_evolving/signal/team.go:18-141`：Python 的 team.py 里**不存在** TeamSignalDetector 这个类；Go 全仓 0 个生产调用方（只有测试用）。注释宣称 "Python: team.py TeamSignalDetector" 是虚构锚点。2a9580260 说清理了注释/doc.go，但 `team_skill_evolution_rail.go:39`、`evolution/doc.go:14`、`team_skill_evolution_rail.go:976-977` 三处旧流程描述漏了。按规则 8 应删除或经确认登记。
