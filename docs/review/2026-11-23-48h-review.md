### M-1 external harness 的"退出路径"不存在：StopExternalHarness 全仓无生产调用方

- **提交**：5507a4c93 / a0e333906 / 8058df778（15.18 主体）
- **Go 侧**：`external_harness_helpers.go:715` 的 `StopExternalHarness` 只有测试调用；`deep_adapter.go:2434` 的 `Cleanup()` 和 `deep_adapter_sessions.go:344` 的 `CleanupSessionAdapter`（子适配器空闲淘汰的唯一路径）都只做交互停止和内存清理，**完全不碰 CLI 子进程和 checkpoint**。而 `external_harness_helpers.go:713-714` 的偏差注释说"Go 子适配器没有 cleanup() 对应物"——这个前提是错的，`DeepAdapter.Cleanup()` 就在那儿。

- **大白话**：external harness 会话空闲超时被淘汰、或整个进程收尾时，claude/codebuddy 这些 CLI 子进程会变成没人管的孤儿继续活着；正在等用户回答（ask_user）的挂起状态也永远存不下来，重启后没法续上。Python 里这条退出链是完整的，Go 侧等于"零件都造好了但没装上车"。**这属于规则 13.2 的缺失项，实施时用错误前提登记了偏差，应回填接线。**

## 提示（6 项）

### T-1 StreamTurnOutput 两处 Python debug 日志没同步

- `external_harness_helpers.go:881`、`:884` 用注释"Python debug 日志同义"替代了真正的日志调用；Python `external_harness_helpers.py:591-596` 有对应输出。规则 3 是明文要求，排查问题时这两处日志有用。

### T-2 错误文案每次全量读盘+全量配置归一化

- `external_harness_helpers.go:304-315` 的 `preferredLanguageEnglish` 每次调用都 `config.New + Load`；Python 的 `get_config()` 是进程内缓存单例。批量绑定冲突这类错误风暴场景，每条消息两次磁盘 IO。功能没错，但和 Python 的行为形态不一致且有性能浪费。

### T-3 懒启动存在双启动竞态窗口

- `external_harness_helpers.go:1256-1281` 的 `ensureExternalHarness` 读状态→启动→回写没有锁；同一会话并发两条 chat.send 可能拉起两个 CLI 子进程，前一个的引用被覆盖后泄漏。Python 的 await 也有类似间隙（不算单方缺陷），但 Go 没有事件循环串行化，窗口实际更大。建议纳入会话已有的 guard 互斥。

### T-4 llm_output 空内容时置位标志与 Python 步骤顺序不严格一致

- `deep_adapter_parse_stream_chunk.go:90` 在内容为空时也置位 `hasStreamedContent`；Python `interface_deep.py:20290-20295` 是先算增量、空则直接跳过（不置位）。当前两种写法输出结果等价，无实际行为差，但步骤顺序与 Python 不严格对应，记录备查。

### T-5 取消哨兵分支当前只有测试可达（已登记 17.9 回填，属防御性）

- `iterative.go:3472` 的 `errors.Is(err, ErrTaskCancelled)` 分支：全仓唯一生产该错误的地方（`RaiseIfCancelled`）只在 ctx 已取消时才返回哨兵，所以"ctx 没取消却冒出哨兵"的形态现在生产上产生不了。提交自述"17.9 前防御性对齐"且 af73d3ba7 已在计划 17.9 行登记了回填指针，测试防假覆盖设计到位（前置断言 ctx 未取消）。不算问题，但 17.9 实施时须按登记收敛。
