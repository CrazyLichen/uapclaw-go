## 严重（3 项）

### S-1 27-A B2：unary 请求的 outbound 从不注销，长跑内存持续泄漏
- 提交：aa897a31a / 610fce446
- 位置：`internal/.../web_http_routes.go:647-664`（runUnaryInternal）
- Python 对照：web_http_routes.py:738 `_unary` 的 finally 里有 `unregister_request_outbound`
- 说明：Python 每次请求结束都会把本次注册的 outbound 注销掉；Go 的 unary 路径 dispatch 完成后没有任何注销动作（对照同文件 SSE/history 路径都有 defer 注销，唯独 unary 漏了）。所有 mapped unary 路由每来一个请求就往 registry 里塞一个 outbound，只有别人查询时才顺带清一下。服务长时间跑，内存会一直涨。

### S-2 27-A B2：SSE 客户端一断开就泄漏一个 goroutine
- 提交：9d29eea90 / b895cd126
- 位置：`web_http_routes.go:711-772` + `web_outbound_http.go:393-479`（handleStream × iterSSEFrames）
- Python 对照：Python 用 async generator，客户端断开时框架取消任务、生成器自动关闭
- 说明：客户端断开后 handler 直接退出循环，但后台往无缓冲 channel 发帧的 goroutine 会永远卡在发送处（没人收了），哨兵关闭信号永远收不到。每断开一次漏一个 goroutine，高并发断连场景会积累。

### S-3 15.24 演进：经验提交落盘时 subject_kind 丢失，team 经验会写错目录
- 提交：72c23a9a9（只补了读半区）
- 位置：`experience/common.go:23-36`（MakePendingChange）、`common.go:74`（CommitPendingChange→AppendRecord）、submission.go:217
- Python 对照：experience/common.py:24-33 `make_pending_change(subject_kind=...)`、common.py:95 逐条 `append_record(..., subject_kind=pending.subject_kind)`
- 说明：审查时补齐了 store 四个查询方法的 subject_kind 过滤（读半区），但**写半区没补**：PendingChange 结构体没有该字段，提交落盘时传 nil。后果是 team 类型的经验会落到默认的技能目录里，数据归错类。

## 一般（12 项）

### M-1 27-A B2：下载 "verified" 校验链只移植了一半
- 提交：9d29eea90 / b895cd126
- 位置：container_file_http_download.go:98-141、147-205
- Python 对照：container_file_http.py:466-495 `_decode_verified_chunk`、`_stream_verified_download`
- 说明：Python 每收一块数据要校验 offset 对不对、块大小对不对、有没有超过总大小、流式下载逐块文件名/类型有没有中途变化（"AgentServer file changed"）；这些校验 Go 全缺。AgentServer 返回错位或重复的块时，Go 会一声不吭把坏文件写出来——"verified 链"名不副实。
