## 一般

### M-1 skipRetiredOwner 重构改变了去重语义，搁浅任务会重复给 leader 发升级消息

- 位置：`internal/agent_teams/agent/coordination/scheduling/scheduler.go:442-464`（提交 7038a6418）
- 事实：原实现是两段判断：非 policy 退役 → 跳过；已升级过（`strandedEscalated` 含该 pair）→ **跳过**。重构合并成 `if !byPolicy || alreadyEscalated { return !byPolicy }` 后，当「policy 退役 + 已升级过」时返回 **false**（不跳过），继续走 `DeliverInput(RenderLeaderEscalationRetiredOwner...)`。
- 后果：`strandedEscalated` 对这一组合的去重失效——只要搁浅任务还在板面上，每轮扫描都会给 leader 重发一条「成员已关停」升级消息（邮件刷屏级）。非 policy 退役分支行为不变。
- 建议：恢复该组合返回 true；或确认 Python 上游就是允许重复升级再改（需对照 scheduler.py 原文，当前 diff 显示改前 Go 代码是跳过，疑为对齐前行为）。

### M-2 评审反馈等待原语 48 小时内三次换形，最终 WG 的安全性依赖无保护的推演不变量

- 位置：`scheduler.go:186-200、893-897`；`scheduler_review.go:219-260`（提交 740281a94 → 9a423ec8b → 7038a6418）
- 事实：同步形态依次为 slice 遍历 → Cond 三件套 → WaitGroup。提交注释自己承认「CI race 实证 WaitGroup 形态会漏等」，最后又依据「ReviseTask 的 IN_REVIEW CAS 保证板清时无在途新派发」的**推演**改回 WG。
- 风险：该论证依赖「dispatchReviewFeedback 只对 IN_REVIEW 任务可达」这一跨模块不变量，没有任何编译期或运行时保护。一旦 follow-up goroutine（`followUpUnvotedReviewer → scan`）存活跨过板清时刻、或未来新增派发入口，就会撞上 Go 明令禁止的「Add 与 Wait 并发」，直接 panic。
- 建议：至少加一条防御性测试（模拟 follow-up goroutine 与板清聚合赛跑），或保留 inflight 计数兜底并在注释中说明这是防回归护栏而非设计冗余。

### M-3 SetReviewFeedbackHandler 无锁写字段，后台 goroutine 无同步读

- 位置：`scheduler.go`（`reviewFeedbackSessionID`/`reviewFeedbackHandler` 字段，提交 740281a94）
- 事实：两个字段直接赋值无锁；`dispatchReviewFeedback`（扫描线）与 reviewer follow-up goroutine 都会读。当前依赖「装配先于 Activate」的隐式时序，没有断言也没有注释声明这一约束。
- 建议：装配期注入的性质写进注释；或在 Set 时加锁/原子，消除对调用顺序的沉默依赖。

### M-4 账本「查-发-记」跨 IO 窗口未闭环

- 位置：`reconcileRevisions`、`reconcileHandoffs`、`reconcileReviews`（提交 7038a6418 加锁后的形态）
- 事实：加锁只护住了 map 读写本身，但「锁内查 → 锁外发消息（IO）→ 锁内记」的模式下，两条线（事件总线扫描 + follow-up 重扫）可在发送间隙都通过检查，造成重复派发/重复邮件。Python 单线程事件循环在 await 间隙也可能交错，但 Go 侧 goroutine 是真并行，触发概率显著更高，且 `-race` 查不出这种逻辑竞态。
- 建议：对「查重+登记」要么合并进单次持锁段（登记先于发送、发送失败回滚），要么明确接受重复并记录到偏差台账。当前注释只说「锁内只包账本段不包 IO」，未讨论跨 IO 一致性。
