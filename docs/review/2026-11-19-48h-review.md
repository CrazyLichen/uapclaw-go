### S-01 ReliabilityHandler 共享状态没有任何锁，多路同时上报会崩进程

- 提交：`76a57ad73`、`53eaa7126`、`d02ae112e`（25.1g 批）
- 文件：`internal/agent_teams/agent/coordination/handlers/reliability.go`
- 位置：`noticed`（map，约 46-48 行声明）、`pendingRouteNotices`（slice，约 180-182 行操作）。
- Python 对照：`agent_teams/reliability/handler.py:76-78`。
- 问题：Python 是 asyncio 单线程，两个字段随便读写没有问题。Go 里这两个字段被两个 goroutine 同时碰：调度分发的事件循环 goroutine（收到异常→写 `noticed`），以及 leader 自己的 agent 循环 goroutine（本地异常钩子→写 `noticed`；`OnUserMessage`→读写 `pendingRouteNotices`）。全结构体没有一把锁。两个成员同时上报同一故障 + leader 本地也命中同一故障时，就是 Go runtime 的 concurrent map read/write，直接 fatal。
- 影响：恰恰是"多路同时报故障"这种最需要可靠性的场景最容易崩。这是本项目历史上反复出现的移植模式问题（Python 单线程共享状态直译），此前已有过 teamRuntimeManagerMu、noticePusher 等同类案例。
- 建议：给这两个字段补一把 mutex，读写点全部收进锁内。

### S-03 Vertex 流式执行里组件出错直接 panic 且无兜底，整个进程崩

- 提交：`ddeacb5db`、`af4996d84`、`0e979fcde`（8.11 Vertex 批）
- 文件：`internal/agentcore/graph/vertex.go:1442`
- Python 对照：`core/graph/pregel/vertex.py:600`（`_post_stream`）与 `vertex.py:206-233`（`_run_executable` 的三条 except 分类）。
- 问题：postStream 遇到流中的错误帧时直接 `panic(chunk.Err)`。Python 同路径的异常是沿 await 传播、被上层分类转成可重试/可上报的错误。Go 侧全仓的 recover 点只有 pregel/task.go:276（只认 `*GraphInterrupt`）和 vertex.go trace 三处；StreamCall 的 spawn goroutine（vertex.go:827）和批侧 nodeTask 都会把这个 panic 原样重抛。而且 `runExecutable` 里 `defer setEvent(event)` 注册在 `strategy()` 之后（vertex.go:524-526），panic 时 event 永不置位，上层还会挂在等待上。代码注释里自己写着"由 runExecutable 的 recover 兜底？"——带问号，实际没有兜。
- 影响：任何一个组件在流式输出中途出错，不是报错重试，而是整个进程退出。
- 建议：改为 error 返回，或在 runExecutable 顶部 recover 非 interrupt 的 panic 转成错误。

## 4. 一般问题

> 不会马上崩，但行为与 Python 不一致或功能打折扣，建议本批或下批修。

### M-01 postInvoke 的 Transformer 分支把 results 丢了，传的是 nil

- 提交：`af4996d84`（收窄在 `cdac01647` 拍板）
- 文件：`internal/agentcore/graph/vertex.go:1330-1333`
- Python 对照：`vertex.py:551` `results = outputs_transformer(results)`。
- 问题：Python 里 transformer 吃的是 results（组件输出）。Go 的 `state.Transformer` 分支写死 `tr(nil)`，results 完全没传进去。按拍板注释，Transformer 契约收窄为"读 state 的 map→map 函数"，但 Python 在 post_invoke 这个调用点传的是 results 字典，不是 nil——两个调用点参数语义不同，Go 合并成一个签名后把这里的实参弄丢了。任何把 Transformer 用作 outputs 转换的组件，输出会被算成空 map。
- 建议：给 state.Transformer 保留 results 入参，或在此处改传 results；若确属拍板后的有意行为，需在 spec 补登记。

### M-02 8.1 取消分支只包住了 preg.Run，前置阶段取消不走快照三分支

- 提交：`b5f697f62`
- 文件：`internal/agentcore/graph/graph.go:603-628`
- Python 对照：`core/graph/pregel/graph.py:349`——`except asyncio.CancelledError` 包住整个 try 体。
- 问题：Python 里 `pre_workflow_execute`、`commit_user_inputs`、`post_workflow_execute` 任一阶段抛取消都进取消分流（保快照/放弃等三分支）。Go 只对 `preg.Run` 判 `errors.Is(err, context.Canceled)`；如果取消恰好落在 PreWorkflowExecute 执行中途，直接原样返回错误，毁掉的正是这个分支要保的 HITL 快照。边缘场景，但恰恰是该功能存在的意义。

### M-03 25.1f 用户主动打断后，轮次被误判成 FAILED

- 提交：`b5491a817`、`f2a0e1551`
- 文件：`internal/agentcore/harness_providers/native/protocolAdapter.go:815-822`（runRound）、`protocolAdapter.go:451`。
- Python 对照：`agent_teams/harness/protocol_adapter.py:292`（`if not turn.abort_requested: raise`）。
- 问题：Python 在输出流耗尽且未到 IDLE 时，若是自己请求的 abort 就安静收尾，不算失败；且 Python 有两个独立标志（IDLE 分支用 `stop_requested`、循环出口用 `abort_requested`）。Go 只在轮次入口查了一次 `AbortRequested()`，流中途打断关流后会走"output closed before reaching IDLE"→ 返回 `HarnessProtocolError` → 轮次 FAILED、生命周期可能发 FAILED 而不是 ABORTED。两个标志的语义也被合并成了一个。
- 影响：用户每次打断，协议层都多报一次错误、状态记错。建议补 `AbortRequested` 出口守卫并拆开双标志。

### M-04 ReliabilityRail 的 Priority 覆盖被 Go 嵌入静态派发架空，实际优先级是 0 不是 5

- 提交：`59ffb7033`、`76a57ad73`
- 文件：`internal/agent_teams/rails/reliability/factory.go:178-185`（生产装配 `ReliabilityRailFromComponents` 裸构造未设 priority）+ `rail.go:68`（`Priority()` 覆盖）。
- Python 对照：`rail.py:87`（priority=5）。
- 问题：生产链唯一入口直接 `&ReliabilityRail{}`，没走 `WithPriority(5)`；而框架注册读优先级走的是 `CallbackPriorityFor`，promote 到基类后静态绑定基类的 `Priority()`——这正是记忆里「Go embedding 虚方法派发陷阱」的第 4 例。回调注册本身没丢（GetCallbacks 覆盖正确，无 15.5 式静默不注册），但 reliability rail 的执行顺序会跑到 priority=0，偏离上游"行为 rail 之后、priority 5"的设计。
- 建议：构造时设 priority 字段，或按既有模式改构造期注入。

### M-05 25.1f 非 map payload 的畸形帧被丢弃而非透传

## 7. 大白话总结

这批活儿大部分干得不错，照着 Python 一条条搬的功夫下了，删旧代码也删得干净。但有四件事得赶紧处理：

1. **最要紧的是可靠性模块自己不可靠**：好几个地方同时报故障时，因为没加锁，程序可能当场崩掉。这毛病跟以前出过的好几次一模一样——Python 是单线程随便写，Go 是多线程，必须加锁。
2. **有个组件出错会让整个程序退出**：按 Python 的写法这是能恢复的错误，Go 里却写成了直接 panic 而且没人接住。组件一抖，全家买单。
3. **有两个提交"说了但没做"**：25.2a 那两个提交的说明写了调度器装配一大堆，实际推上去的只有 4 行测试假桩，真东西还在没合并的分支上。这不是代码 bug，是上库流程出了问题，需要当事人说清楚。
4. **几个小一点的偏差**：用户主动打断会被记成"失败"（应该是安静收尾）、一个转换函数拿到的输入被丢了传了个 nil、可靠性轨道的排队优先级实际是 0 不是设计的 5（这个坑是 Go 继承特性导致的，已经是第四次踩了）、还有取消保快照的分支没包全。这些不影响能不能跑，但行为和 Python 对不上，迟早会被用户感知。

其余是一些记档级别的小项：注释文档没同步、格式没过 gofmt、个别边界场景语义不同。都不着急。
